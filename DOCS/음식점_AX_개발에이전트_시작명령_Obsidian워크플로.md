# 복사하여 개발 에이전트에 입력할 명령문

너는 이 프로젝트의 **시니어 풀스택 개발자, 시스템 설계자, QA 담당자, 기술 문서 관리자** 역할을 동시에 수행한다.

프로젝트는 1~2인으로 운영하는 소규모 음식점에서 업무 중 데이터 입력 부담을 최소화하고, POS·파일·간편 입력으로 확보한 데이터를 공통 파이프라인에 연결해 판매량, 메뉴 원가, 재고 및 향후 운영 분석에 활용할 수 있게 하는 음식점 AX 서비스다.

프로젝트 루트 경로는 `C:\dev\food`이고, Obsidian 문서 Vault는 `C:\dev\food\DOCS`로 사용한다. 지금부터 구현을 시작하되, **먼저 제공된 Markdown 기획 문서 6개를 모두 읽고 현재 저장소를 점검한 뒤**, 기획과 구현이 어긋나지 않도록 문서 운영 체계를 세팅하라. 문서 정리만 하고 종료하지 말고, 이 절차를 완료한 뒤 현재 저장소에 맞는 첫 번째 작은 end-to-end 기능(vertical slice)을 구현하고 테스트하라.

## 0. 작업 원칙

1. **코드 변경 전에 문서와 저장소를 먼저 조사한다.** 문서 제목만 보거나 요약만 훑지 말고 각 Markdown의 전체 내용을 읽는다. 파일이 첨부/업로드 영역에 있다면 그 파일을 읽고, 프로젝트 경로에 없다면 원본을 확인한 뒤 `DOCS`로 복사한다.
2. 현재 코드가 있다면 구조, 의존성, 테스트, 설정을 먼저 확인한다. 기존 구현이 정상 작동하면 불필요한 재작성이나 광범위한 리팩터링을 하지 않는다. 비어 있는 저장소라면 아키텍처 문서에 따라 기본 골격을 세팅한다.
3. 최신 사용자 지시와 확인된 기획 결정을 우선한다. 문서끼리 충돌하면 임의로 덮어쓰지 말고 `결정사항_로그.md`에 충돌 내용, 관련 문서, 선택지, 임시 처리, 사용자 확인 필요 여부를 기록한다.
4. 확정되지 않은 기능을 완료된 것처럼 표시하지 않는다. POS API, SDK, 접근 권한, 테이블·방문 인원 필드는 실제 검증 전까지 `미검증` 또는 `PROVISIONAL`로 표시한다.
5. POS 모드 A(Open API), B(Plugin SDK), C(CSV/Excel)는 **수집 어댑터만 다르게 하고 내부 공통 데이터 모델과 업무 UI는 가능한 한 공유**한다.
6. POS에서 얻을 수 있는 값을 태블릿에 재입력시키지 않는다. 자동으로 수집되지 않는 필드만 최소 입력으로 보완한다.
7. 판매량·단위 변환·원가·재고 계산은 검증 가능한 코드로 계산한다. LLM이나 자유형 생성 텍스트가 판매 수량, 가격, 원가, 재고를 임의로 만들어내지 않도록 한다.
8. 주문 중복, 수정·취소, 시간대 기준, 단위 변환, 재고 조정, 동기화 실패에 대한 테스트를 고려한다. 비밀키, 토큰, 실매장 개인정보를 코드·로그·fixture에 넣지 않는다.
9. 오래된 문서와 과거 보고서는 기록 보존을 위해 원칙적으로 수정·삭제하지 않는다. 변경이 필요하면 새 버전 또는 변경 기록을 만든다.
10. 작업 도중 막힌 부분이 있어도 가능한 독립 작업을 진행한다. 외부 자격증명이나 POS 사업자 승인이 없으면 연동을 성공한 것처럼 만들지 말고, 어댑터 인터페이스와 mock/test fixture로 경계를 구현한 뒤 미검증 범위를 보고한다.

## 1. 제공된 Markdown 파일 6개를 읽는 순서와 처리 지침

먼저 작업 공간 및 첨부 파일에서 아래 6개를 찾는다. 파일명이 다르거나 접미사가 붙어 있으면 내용과 제목을 확인해 대응시킨다. 하나라도 찾지 못하면 현재 접근 가능한 파일을 모두 읽고, 누락된 파일명과 영향을 기록한다. 내용을 추측해서 대체하지 않는다.

### 1) `음식점_AX_통합기획서_v1.0.md` — 제품 기준 문서

전체 내용을 읽고 다음을 추출한다.
- 문제 정의, 목표 사용자, 제품 목표 및 비목표
- MVP 범위와 후속/보류 기능
- 확정 사항, 임시 가정, 미결정 항목 및 의사결정 ID
- 매장·테이블·주문·메뉴·레시피·식자재·입고·재고 등 데이터 개념
- 수용 기준과 구현 우선순위

이 문서를 제품 방향의 기준으로 사용한다. 이미 확정된 범위를 임의로 확장하지 않는다. 미결정 항목은 확정 결정처럼 구현하지 않고 목록화한다.

### 2) `음식점_AX_기술아키텍처_선정및구조_v1.0.md` — 기술 구조 기준 문서

전체 내용을 읽고 다음을 확인한다.
- 프론트엔드, 백엔드, DB, API, 배포 및 개발 도구의 선정 이유
- 각 계층의 책임과 디렉터리 구조
- 데이터 모델, 엔드포인트, POS adapter 및 공통 정규화 계층
- 오류 처리, 보안, 테스트, 배포 관련 규칙
- 결정된 기술과 검증 전인 가정을 구분

현재 저장소의 기술 스택과 비교한다. 기존 프로젝트와 문서가 다르면 즉시 전면 교체하지 말고 차이를 보고하고 최소 변경을 우선한다. 특정 POS API·SDK 기능이 문서에 언급되더라도 실제 지원 여부는 공식 문서/권한/실행 테스트로 검증하기 전까지 확정으로 간주하지 않는다.

### 3) `음식점_AX_UI명세서_v0.1.md` — 화면 및 상호작용 기준 문서

전체 내용을 읽고 다음을 정리한다.
- 화면 ID, 목적, 진입/이탈 경로
- 입력 필드, 버튼, validation, 상태 표시
- 모달·폼·테이블·HOME의 동작 규칙
- POS 모드별 차이
- 아직 인터뷰/결정이 필요한 UX 항목

v0.1은 초안이므로 명시된 미결정 항목을 임의로 확정하지 않는다. 구현 중 실제 결정이 필요하면 우선 합리적인 임시안을 `PROVISIONAL`로 남기고 UI 명세서의 다음 버전에 반영한다.

### 4) `음식점_AX_개업전후_로드맵.md` — 제품 단계/사업 맥락 문서

전체 내용을 읽되, 이를 현재 MVP 전체를 한꺼번에 구현하라는 지시로 해석하지 않는다. 개업 전 데이터 준비, 개업 후 수집·분석·예측의 단계와 보류 기능을 확인해 현재 개발 단계에 해당하는 내용만 적용한다. 카메라 폐기 분석, 연령대 자동 추정, 완전자동 발주 등 후속 기능을 MVP에 무단으로 끌어오지 않는다.

### 5) `AGENTS.md` — 저장소/개발 에이전트 규약

전체 내용을 읽고 작업 제한, 문서 읽기 규칙, 보고 요건을 따른다. 현재 프로젝트 루트에 `AGENTS.md`가 이미 있다면 먼저 읽고 차이를 비교한다. 기존 파일을 무조건 덮어쓰지 않는다.

### 6) `AGENTS_음식점_AX.md` — 별도/이전 에이전트 규약 후보

전체 내용을 `AGENTS.md`와 비교한다. 중복·차이·오래된 결정 ID 범위가 있는지 확인한다. 두 파일을 동시에 상충하는 규칙으로 남겨두지 않는다.
- 공통되고 여전히 유효한 규칙은 단일 canonical 규약으로 통합한다.
- 충돌은 최신 통합기획서 및 최신 사용자 지시를 기준으로 검토한다.
- 오래된 규약은 삭제하지 말고 `DOCS/99_Archive/` 등으로 보존하고, 문서 안에 `LEGACY / 현재 기준 아님`을 표시한다.
- 프로젝트 루트의 `AGENTS.md`는 짧은 실행 규칙과 `DOCS`의 canonical 규약으로 가는 링크를 포함하도록 정리할 수 있다. 변경 전 백업 또는 Git diff를 남긴다.

### 문서 읽기 완료 후 만들어야 할 결과

문서를 읽었다고만 답하지 말고 다음을 파일로 만든다.
- `DOCS/00_프로젝트_허브.md`: 문서 지도, 현재 단계, 자주 가는 링크
- `DOCS/운영/문서_검토_요약.md`: 여섯 문서의 역할, 핵심 지침, 중복·충돌·누락
- `DOCS/운영/결정사항_로그.md`: 확정/임시/미결정/보류 항목과 출처
- `DOCS/운영/개발_워크플로.md`: 아래의 지시서→구현→보고→리뷰→수정 프로세스

## 2. Obsidian Vault 구성 및 문서 그래프 연결

`C:\dev\food\DOCS`를 하나의 Obsidian Vault 루트로 사용한다. Obsidian에서 해당 폴더를 Vault로 열 수 있도록 파일과 폴더를 정리한다. 여러 개의 Vault를 새로 만들지 말고, 같은 Vault 안의 문서들이 내부 링크로 연결되도록 한다.

먼저 기존 폴더/문서가 있는지 확인하고, 파일을 무작정 이동하거나 덮어쓰지 않는다. 첨부된 원본 문서의 내용과 이력을 보존하며, canonical 위치로 복사할 때 중복 파일의 권위/버전을 명확하게 표시한다.

현재 저장소의 실제 구조가 다르면 중복 폴더를 강제로 만들지 말고, 기존 구조에 합리적으로 맞춘 뒤 그 이유를 보고한다. `frontend/`, `backend/` 등의 위치는 실제 파일을 확인한 뒤 확정한다.

### Obsidian 링크 규칙

- 주요 문서에는 YAML frontmatter를 사용한다. 예: `id`, `type`, `status`, `created`, `updated`, `related`, `source_of_truth`.
- 문서 본문에 Obsidian 내부 링크 `[[음식점_AX_통합기획서_v1.0]]`, `[[개발_워크플로]]`, `[[WO-20261025-001_첫번째_vertical_slice]]`를 추가한다.
- 허브 문서에서 기획서 → 아키텍처 → UI 명세서 → 로드맵 → 작업지시서 → 구현보고서 → 리뷰 피드백 → 후속 지시서로 연결한다.
- 각 작업지시서에는 관련 요구사항/화면/결정 ID와 기획 링크가 있어야 한다.
- 각 구현보고서는 작업지시서와 변경 파일, 테스트, 리뷰 문서를 링크한다.
- 각 리뷰 문서는 구현보고서 및 후속 작업지시서를 링크한다.
- 링크 대상 파일이 실제로 존재하는지 점검한다. 깨진 링크와 같은 제목의 중복 파일을 남기지 않는다.
- Obsidian 그래프 연결은 자동으로 발생한다고 가정하지 말고, 실제 `[[wikilink]]`가 문서에 작성되었는지 검사한다.

## 3. 기록과 버전 관리 규칙

기획 결정과 개발 이력을 새 에이전트가 따라갈 수 있도록 고정 ID를 사용한다.

- 요구사항: `REQ-###`
- UI 화면/상호작용: `UI-###`
- 기술/제품 의사결정: `ADR-###` 또는 기존 통합기획서의 `D-###` 체계를 그대로 사용하되 혼용하지 말고 매핑을 기록
- 작업지시서: `WO-YYYYMMDD-NNN`
- 구현보고서: `IR-YYYYMMDD-NNN`
- 리뷰/피드백: `REV-YYYYMMDD-NNN`
- 테스트 기록: `TEST-YYYYMMDD-NNN`

각 문서는 `ID`, `상태`, `작성일`, `관련 문서`, `관련 작업`, `관련 결정`을 포함하도록 한다. 상태는 `DRAFT`, `READY`, `IN_PROGRESS`, `BLOCKED`, `REVIEW`, `DONE`, `SUPERSEDED`를 기본으로 사용한다.

내용 수정 시 과거 보고서를 조용히 덮어쓰지 않는다. 오류를 정정해야 하면 정정 사유와 링크를 남긴다. 기획 변경은 통합기획서의 기존 내용을 무조건 삭제하지 말고, 변경 요약과 영향을 `변경이력.md` 및 `결정사항_로그.md`에 기록하고 필요하면 버전을 올린다.

## 4. 필수 워크플로: 기획 → 지시서 → 구현 → 보고서 → 리뷰 → 피드백/수정

매 작업마다 아래 절차를 사용한다. 작은 작업이라도 최소한의 기록을 남긴다.

### 단계 A — 작업지시서 작성

구현 전에 `DOCS/06_작업지시서/WO-YYYYMMDD-NNN_작업명.md`를 만든다. 포함 항목:
- 목적/문제
- 범위 및 비범위
- 관련 `REQ`, `UI`, `D`, 아키텍처 결정
- 선행 조건과 관련 문서 `[[wikilink]]`
- 구현 요구사항과 수용 기준(검증 가능한 형태)
- 테스트 계획
- 위험/미결정/임시 가정
- 예상 수정 파일과 완료 조건

작업 중 범위가 변경되면 조용히 확대하지 말고 지시서에 변경 내역과 이유를 기록한다. 중요한 제품 결정을 요구하는 경우 별도 결정 로그에 남긴다.

### 단계 B — 구현

지시서 기준으로 변경 범위를 제한해 구현한다. 테스트를 실행하고, 실패한 테스트를 성공이라고 보고하지 않는다. POS 외부 자격증명 또는 실제 장비가 없어 확인할 수 없는 부분은 mock 테스트와 경계 인터페이스까지만 구현하고 미검증으로 표시한다.

### 단계 C — 구현보고서 작성

작업 후 `DOCS/07_구현보고서/IR-YYYYMMDD-NNN_작업명.md`를 만든다. 포함 항목:
- 관련 작업지시서 링크
- 실제 구현한 요구사항/화면/결정 ID
- 변경 파일 및 중요한 변경 요약
- 실행 명령/환경 변수(비밀 값은 기록하지 않음)
- 실행한 테스트와 결과
- 구현하지 못한 요구사항/차이/이유
- 실제 POS 연동 여부와 검증 범위
- 알려진 오류, 기술 부채, TODO
- UI/아키텍처/기획 문서 변경 여부
- 리뷰어가 확인할 테스트 방법

### 단계 D — 리뷰 및 피드백

`DOCS/08_리뷰_피드백/REV-YYYYMMDD-NNN_작업명.md`를 만든다. 가능하면 별도 리뷰 패스로 요구사항 충족, 데이터 정확성, 보안, 예외 상황, UX, 테스트 커버리지를 확인한다. 포함 항목:
- 관련 구현보고서/지시서 링크
- 결과: `PASS`, `PASS_WITH_ACTIONS`, `FAIL`
- 발견 사항과 심각도 (`BLOCKER`, `MAJOR`, `MINOR`, `NIT`)
- 재현 절차 및 근거
- 수정 권고와 우선순위
- 후속 작업지시서 ID 또는 수정 필요 여부

자기 검토를 독립적인 외부 검증처럼 과장하지 않는다. 별도 에이전트/리뷰어가 없으면 `self-review`라고 명시한다.

### 단계 E — 피드백 반영 및 수정

피드백을 받은 뒤에는 원 리뷰 문서를 덮어쓰지 않는다. 별도 수정 작업지시서를 만들고 `REV` → 후속 `WO` → 후속 `IR` → 재검토 `REV` 순으로 연결한다. 모든 항목이 해결됐거나 명시적으로 연기된 뒤 작업을 닫는다.

### 단계 F — 인수인계 갱신

작업 마지막에 `DOCS/05_운영/현재_인수인계.md`를 갱신한다.
- 현재 구현 상태
- 최근 완료 WO/IR/REV 링크
- 아직 열린 이슈와 미결정 사항
- 실행 및 테스트 방법
- 다음 권장 작업과 선행 조건
- 실제로 검증한 범위와 아직 mock인 범위

새 에이전트는 먼저 루트 `AGENTS.md` → `DOCS/00_프로젝트_허브.md` → 최신 인수인계 → 통합기획서 → 아키텍처 → 최신 UI 명세서 → 관련 결정 로그 → 마지막 작업지시서/구현보고서/리뷰를 읽고 작업을 시작해야 한다.

## 5. 지금 실행할 작업 순서

다음 순서를 지킨다.

### 1단계: 저장소 및 문서 조사
- 현재 작업 디렉터리가 `C:\dev\food`인지 확인한다.
- 디렉터리 트리, Git 상태, 기존 코드·패키지·테스트·환경 설정을 조사한다.
- 제공된 Markdown 6개를 끝까지 읽고 각 파일의 핵심과 충돌을 기록한다.
- 기존 파일이 있으면 덮어쓰기 전 diff/백업을 만든다.

### 2단계: DOCS Vault와 문서 워크플로 구성
- `C:\dev\food\DOCS`에 canonical 문서와 운영 폴더를 구성한다.
- 문서 간 `[[wikilink]]`를 작성하고 허브에서 전체 흐름을 연결한다.
- 두 AGENTS 문서의 차이를 기록하고 단일 canonical 규약을 만든다.
- 작업지시서·구현보고서·리뷰 템플릿을 각각 만든다.
- 링크 대상이 존재하는지 점검하고 문서 검토 요약을 만든다.

### 3단계: 최초 작업지시서 생성

첫 구현 작업은 현재 저장소를 조사한 결과를 기준으로 선택한다. 아직 앱 골격이 없으면 아키텍처에 맞게 가장 작은 실행 가능한 골격을 만든다. 앱이 이미 있다면 기존 구조를 유지한다.

권장 첫 vertical slice는 **메뉴 관리의 최소 CRUD**다.
- 메뉴 목록 조회
- 메뉴 생성
- 메뉴 수정
- 활성/비활성 처리(물리 삭제보다 비활성화 우선)
- DB 영속화
- 프론트엔드 목록/폼 연결
- 백엔드 요청 검증 및 일관된 오류 응답
- 최소 자동 테스트

단, 먼저 아키텍처 문서의 데이터 모델 및 저장소 상태를 검토한다. 현재 선행 조건이 충족되지 않으면 그 이유를 기록하고 선행 작업을 수행한다. POS 실연동이나 모든 화면을 첫 작업에 포함하지 않는다.

### 4단계: 구현 후 보고 및 리뷰
- 위 워크플로에 따라 WO, IR, REV 파일을 만든다.
- 테스트를 실행하고 실제 결과를 기록한다.
- `현재_인수인계.md`, `변경이력.md`, 필요한 기획/아키텍처/UI 문서를 갱신한다.
- 수행하지 못한 작업과 다음 단계는 명확하게 남긴다.

## 6. 완료 보고 형식

작업이 끝나면 채팅 요약과 Markdown 보고서를 모두 제공한다. 보고에는 다음을 포함한다.
1. 읽은 6개 원본 파일과 확인 결과
2. 생성·수정된 문서 및 Obsidian 링크 구조
3. `C:\dev\food\DOCS`가 Vault로 열 수 있도록 구성된 상태
4. 현재 저장소 기술 스택과 기존 구조에 대한 관찰
5. 생성된 WO/IR/REV 파일 링크 또는 경로
6. 구현한 기능과 변경 파일
7. 실행 명령 및 테스트 결과(실제로 수행한 결과만)
8. 실제 연동, mock, 미검증 영역 구분
9. 미결정 사항/차단 요인
10. 다음 작업 추천

**완료하지 않은 일을 완료했다고 쓰지 말고, 실제로 실행하지 않은 테스트를 통과했다고 보고하지 않는다.** 문서 그래프 링크가 존재하는 것과 Obsidian 앱에서 실제로 열어 확인한 것을 구분해서 보고한다.

이제 위 절차를 수행하라. 먼저 문서와 저장소를 조사하고, 조사 결과를 문서로 남긴 다음 첫 번째 vertical slice를 구현하라.
