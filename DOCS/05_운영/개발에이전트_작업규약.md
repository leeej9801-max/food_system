# 개발 에이전트 작업 규약 (canonical)

> 이 문서는 다음 세 출처를 하나로 통합한 **단일 기준 규약**이다. 서로 다른 규칙이 남지 않도록, 에이전트 규칙 변경은 이 문서에서만 한다.
> - [[AGENTS]] (원본 규약, DOCS 루트 — 사용자 확인: 시작 명령의 `AGENTS_음식점_AX.md`와 동일 문서로 간주, [[결정사항_로그#C-01|C-01]])
> - [[음식점_AX_통합기획서_v1.0]] §16 (AI/개발 에이전트 작업 규약)
> - [[음식점_AX_기술아키텍처_선정및구조_v1.0]] §15 (에이전트 구현 지침)
> - [[음식점_AX_개발에이전트_시작명령_Obsidian워크플로]] §0, §3, §4
>
> 루트 `C:\dev\food\AGENTS.md`는 이 문서로 연결하는 짧은 진입점이다.

## 1. 작업 전 필수 읽기

1. 루트 `AGENTS.md` → [[00_프로젝트_허브]] → [[현재_인수인계]]
2. [[음식점_AX_통합기획서_v1.0]] (제품 기준)
3. [[음식점_AX_기술아키텍처_선정및구조_v1.0]] (기술 기준)
4. [[음식점_AX_UI명세서_v0.1]] 또는 최신 UI 명세서
5. [[결정사항_로그]], [[요구사항_ID_매핑]]
6. 마지막 WO / IR / REV, 저장소의 `README.md`, `.env.example`, 기존 코드·테스트

## 2. 제품 원칙 (변경 금지)

- 1차 목표는 1~2인 운영 음식점의 **데이터 입력 부담 최소화 데이터 수집 파이프라인**이다. 범용 AI 비서나 POS 대체 제품으로 방향을 바꾸지 않는다.
- POS 모드 A(Toss Open API), B(Toss Plugin SDK), C(CSV/Excel)는 **수집 어댑터만 다르고** 내부 데이터 모델·업무 UI는 공통이다.
- POS에 존재하는 값을 다시 수기 입력하게 만들지 않는다. 자동으로 수집되지 않는 정보만 최소 입력으로 보완한다.
- 판매량·단위 변환·원가·재고는 **결정론적 코드**로 계산한다. LLM이 수치를 생성하지 않는다.
- 폐기 카메라 분석, 연령대 카메라 추정, 완전자동 발주는 MVP 범위가 아니다.
- 고객 개인정보(이름·전화·얼굴)는 수집하지 않는다.

## 3. 구현 원칙

1. **코드 변경 전 문서·저장소 조사.** 기존 구현이 정상이면 불필요한 재작성·광범위 리팩터링 금지.
2. 최신 사용자 지시 > 확인된 결정([[결정사항_로그]]) > 통합기획서 > 아키텍처 > UI 명세 > 로드맵 순으로 우선한다.
3. 문서 충돌은 임의로 덮어쓰지 않고 [[결정사항_로그]]에 `C-xx`로 기록(충돌, 관련 문서, 선택지, 임시 처리, 사용자 확인 필요 여부).
4. 미결정 항목(D-01~D-08)은 임의 확정 금지. 임시안은 코드·문서에 `PROVISIONAL`로 표시하고 로그에 남긴다.
5. POS API/SDK/권한/테이블·방문 인원 필드는 실제 검증 전까지 `미검증`. mock 데이터를 실연동처럼 표시하지 않는다(UI·로그에서 mock/real 구분).
6. 외부 자격증명이 없으면 어댑터 인터페이스 + mock/fixture까지만 구현하고 미검증 범위를 보고한다.
7. 중복 이벤트, 주문 수정·취소, 시간 기준, 단위 변환, 재고 조정, 동기화 실패에 대한 테스트를 둔다.
8. 금액·수량은 decimal/numeric, 시각은 timezone-aware UTC 저장 / 매장 timezone(기본 `Asia/Seoul`) 표시.
9. 업무 이력은 물리 삭제보다 비활성화·보존 우선. `ON DELETE CASCADE`로 과거 근거를 지우지 않는다.
10. 스키마 변경은 Alembic migration. 운영 DB를 임의 재생성하지 않는다.
11. 비밀키·토큰·실매장 개인정보를 코드·로그·fixture·문서에 넣지 않는다. `.env`는 커밋하지 않는다.
12. 수기 입력을 추가하기 전에 POS/파일에서 가져올 수 있는지 먼저 확인한다.

## 4. 기록·버전 규칙

- ID 체계: `REQ-###`, 화면 `S00~S07`(=UI ID, [[요구사항_ID_매핑]]), 제품 미결정 `D-##`(통합기획서 기준), 기술 결정 `ADR-###`(아키텍처 기준), 충돌 `C-##`, 임시 가정 `P-##`, 작업 `WO-YYYYMMDD-NNN`, 보고 `IR-…`, 리뷰 `REV-…`, 테스트 `TEST-…`.
- 아키텍처 문서 §14의 `D-01~D-11`은 통합기획서 `D-xx`와 **번호 의미가 다르다** → `ARCH-D-xx`로 표기하고 매핑은 [[결정사항_로그#D-ID 매핑]]을 따른다.
- 상태: `DRAFT`, `READY`, `IN_PROGRESS`, `BLOCKED`, `REVIEW`, `DONE`, `SUPERSEDED`.
- 과거 보고서·리뷰를 조용히 덮어쓰지 않는다. 정정은 사유와 링크를 남긴다.
- 원본 기획 문서는 DOCS 루트에 그대로 둔다(사용자 결정, [[인터뷰_기록]] 1회차). 변경 시 [[변경이력]]·[[결정사항_로그]]에 기록하고 필요하면 새 버전 파일을 만든다.

## 5. 필수 워크플로

모든 작업은 [[개발_워크플로]]의 **WO → 구현 → IR → REV → (후속 WO) → 인수인계** 절차를 따른다. 자기 검토는 `self-review`로 명시한다.

## 6. 작업 완료 보고 (채팅 + IR 문서)

1. 구현한 요구사항/화면 ID
2. 변경 파일
3. 실행 방법(비밀 값 제외)
4. 테스트 결과 — **실제로 실행한 것만**
5. 실제 연동 여부와 mock/미검증 범위
6. 남은 제약 및 TODO
7. 갱신한 기획/운영 문서

## 7. 사용자 인터뷰

필요한 결정은 사용자에게 질문한다(사용자 요청: "필요시 계속 인터뷰"). 이미 확정된 문서 내용은 다시 묻지 않는다. 질문·답변·반영 위치는 [[인터뷰_기록]]에 남긴다.
