# 인증 설계 — 2026-11-10

상태: **승인됨 (2026-11-10, U-41).** 결정 결과는 §12.1. D-A5는 보류다. 구현(⑦)은 사용자가 따로 시작을 지시한 뒤에 한다.

## 0. 범위
| 대상 | 이번 설계 | 구현 시점 |
|---|---|---|
| 점주 로그인(카카오 + 쿠키 세션), 매장 소속 검사 | 확정 수준 | ⑦ (11월) |
| 운영자 스크립트(매장 생성, 초대) | 확정 수준 | ⑦ |

| 손님 익명 쿠키 보강(`Secure`), 손님 전용 DB 역할 | 확정 수준 | ④(쿠키), ⑦(역할) |
| 직원 기기 등록, 출퇴근 기록 | 구조만. 법적·운영 요건 `미확인` | 이번 범위 밖(요건 확인 뒤 별도 WO) |
| 손님 카카오 등록(전역 계정) | 구조만 | 12월 초 이후, 이번 범위 밖 |

표·열 이름, 경로는 제안이다. ID는 ⑤에서 UUID v7로 바뀐다.

## 1. 구성 한눈에
```
브라우저 ──쿠키(세션 ID)──▶ nginx ──▶ FastAPI
                                        │ 1. Origin 검사 (상태 변경 요청)
                                        │ 2. 세션 조회 → user_id
                                        │ 3. store_members에서 (user_id, URL의 store_id) 확인
                                        │ 4. 확인된 뒤에만 RLS 범위 설정
                                        ▼
                                   PostgreSQL (RLS, 역할별 권한)
```
토큰은 브라우저 저장소(`localStorage`, `sessionStorage`)에 두지 않는다 (U-39). 브라우저가 갖는 것은 `HttpOnly` 쿠키의 세션 ID 하나다.

## 2. 새 표
모두 **전역 표**다(매장 `store_id` 정책 없음, ADR-013 결정 1). 대신 §8의 권한과 사용자 단위 정책으로 막는다.

| 표 | 주요 열 | 용도 |
|---|---|---|
| `users` | `id`, `created_at`, `disabled_at` | 점주(나중에 직원 카카오) 계정. 이름·이메일 열 없음 |
| `user_identities` | `user_id`, `provider`(`KAKAO`), `provider_user_id`, unique(`provider`, `provider_user_id`) | 카카오 회원번호 연결. 카카오 토큰은 저장하지 않는다 |
| `store_members` | `store_id`, `user_id`, `role`(`OWNER`), `created_at`, `revoked_at`, unique(`store_id`, `user_id`) | 매장 소속 (D-3: 다대다) |
| `store_invites` | `id`, `store_id`, `code_hash`, `expires_at`, `used_at`, `used_by_user_id` | 운영자가 발급한 일회용 초대 (D-2) |
| `auth_sessions` | `id_hash`(SHA-256), `user_id`, `created_at`, `last_seen_at`, `idle_expires_at`, `absolute_expires_at`, `revoked_at` | 서버 세션. 세션 ID 원문은 저장하지 않는다 |
| `oauth_states` | `state_hash`, `created_at`, `expires_at`(10분), `next_path` | 로그인 시작~콜백 사이의 일회용 값 |

세션을 서명 쿠키(JWT)가 아니라 DB 표로 두는 이유: 서버에서 즉시 폐기할 수 있어야 한다(로그아웃, 계정 정지, 탈취 대응). Redis는 쓰지 않는다. 지금 규모에서 요청마다 인덱스 조회 1번이면 충분하고, 새 구성 요소가 늘지 않는다. 부하는 `미검증`이다.

## 3. 점주: 카카오 OAuth + 쿠키 세션

### 3.1 흐름
1. `GET /api/auth/v1/kakao/start?next=/…` — `state`(`secrets.token_urlsafe(32)`)를 만들고 해시를 `oauth_states`에 저장한다. 같은 값을 짧은 수명의 `HttpOnly` 쿠키로도 준다. 카카오 인가 주소로 302.
2. 카카오에서 로그인·동의.
3. `GET /api/auth/v1/kakao/callback?code=…&state=…`
   - `state`가 쿠키 값과 같고, `oauth_states`에 있고, 만료 전이고, 처음 쓰이는지 확인한다. 쓰면 바로 지운다. 하나라도 틀리면 400 (위협분석 O-1).
   - **서버가** `code`를 카카오 토큰 주소로 보내 교환한다. 클라이언트 비밀값은 서버 설정에만 있다.
   - 카카오 사용자 정보에서 **회원번호만** 읽는다. 카카오 토큰은 버린다.
   - `user_identities`에서 찾고, 없으면 `users`를 만든다.
   - **새 세션 ID를 발급한다.** 요청에 실려 온 이전 세션 ID가 있으면 폐기한다 (O-2, 세션 고정).
   - `next`로 302.
4. `POST /api/auth/v1/logout` — 세션을 `revoked_at`으로 폐기하고 쿠키를 지운다.
5. `GET /api/auth/v1/me` — 사용자 ID와 소속 매장 목록.
6. `POST /api/auth/v1/invites/accept` `{code}` — 로그인한 사용자를 그 매장의 `OWNER`로 넣는다. 일회용, 만료 있음.

### 3.2 규칙
| 항목 | 설계 |
|---|---|
| 리다이렉트 URI | 설정값 하나(`KAKAO_REDIRECT_URI`)로 고정한다. 요청의 `Host`나 파라미터로 만들지 않는다. 카카오 콘솔에 등록한 값과 글자 그대로 같아야 한다 |
| `next` | `/`로 시작하는 앱 내부 경로만 허용한다(`//`, `\`, 스킴 포함 거부). 아니면 기본 화면으로 보낸다(오픈 리다이렉트 방지) |
| 세션 ID | `secrets.token_urlsafe(32)`(256비트). DB에는 SHA-256 해시만 |
| 쿠키 | `HttpOnly; Secure; SameSite=Lax; Path=…`. `Domain`은 지정하지 않는다. 이름·경로는 D-A7에 따라 정한다 |
| 유휴 만료 | 마지막 요청 뒤 일정 시간 지나면 만료 (D-A1) |
| 절대 만료 | 로그인 시각부터 일정 시간 지나면 무조건 만료 (D-A1) |
| `last_seen_at` 갱신 | 요청마다 쓰지 않고 5분에 한 번만 (쓰기 부하) |
| 로그아웃 | 서버에서 폐기. 쿠키 삭제만으로 끝내지 않는다 |
| 계정 정지 | `users.disabled_at`이 있으면 모든 세션 거부 |
| 만료·폐기된 세션 | 401. 본문에 이유를 구분해 주지 않는다 |
| 소속 없는 로그인 | 로그인은 되지만 매장 화면은 없다. 초대 코드 입력 화면만 보인다 |

`SameSite=Lax`를 `Strict`로 하지 않는 이유: `Strict`면 카카오에서 돌아오는 콜백과 외부 링크로 들어온 첫 요청에 쿠키가 실리지 않는다.

### 3.3 CSRF
쿠키로 인증하면 다른 사이트가 점주 브라우저로 요청을 보낼 수 있다 (O-3). 세 겹으로 막는다.
1. `SameSite=Lax` — 다른 사이트에서 보낸 `POST`·`PATCH`·`PUT`·`DELETE`에는 쿠키가 실리지 않는다.
2. **`Origin` 검사** — 상태를 바꾸는 요청(`GET`, `HEAD`, `OPTIONS` 제외)은 `Origin` 헤더가 설정된 허용 출처와 같아야 한다. 다르거나 없으면 403. `Sec-Fetch-Site`가 오면 `same-origin`인지도 본다.
3. **`GET`은 사용자가 의도한 상태 변경을 하지 않는다.** 지금 `GET`이 DB에 쓰는 곳은 두 종류다(확인).
   - `GET /stores/{store_id}/tables`, `GET …/visits`: 영업일이 지난 세션을 자동으로 닫는다(`backend/app/services/tables.py:91`, `:315`). 시각으로 정해지는 정리라 공격자가 결과를 고를 수 없다. 그대로 둔다.
   - `GET /api/guest/v1/qr/{token}`: 처음 온 기기에 `guest_devices` 행과 쿠키를 만든다. 익명 식별자 발급이다. 그대로 둔다.
   새 경로는 `GET`에서 쓰지 않는다.

CSRF 토큰은 넣지 않는다. 위 세 가지로 충분하고, 토큰은 프론트 전 요청에 헤더를 붙이는 일을 만든다. 단 D-A7에서 호스트를 분리하지 않으면 이 판단은 약해진다(§11).

CORS: 운영은 화면과 API가 같은 출처다. 운영에서는 CORS 미들웨어를 등록하지 않는다. 지금의 `allow_credentials=True` + 메서드·헤더 `*`는 필요 없다. 로컬 개발(`localhost:5173`)에서만 켠다.

## 4. 운영자 (D-2, D-6)
- 앱에 운영자 역할과 HTTP 경로가 없다. `backend/scripts/`의 스크립트를 서버에서 실행한다.
  - `create_store.py` — 매장 생성.
  - `issue_invite.py` — 초대 코드 발급(원문은 한 번만 출력, DB에는 해시).
  - `revoke_member.py` — 소속 해제(그 사용자의 세션도 폐기).
  - `fetch_holidays.py`(있음) — 공휴일 적재.
- 스크립트는 소유자 계정이 아닌 전용 DB 역할(`food_admin`)로 접속한다(§8).
- 실행할 때마다 `audit_events`에 `actor = "operator:<실행자가 넘긴 이름>"`으로 남긴다. 실행자 이름은 자기 신고라 증거력은 약하다. 서버 접근 통제에 의존한다(위협분석 P-1, `미확인`).
- 매장이 늘어 수동 운영이 부담되면 운영자 콘솔을 **별도 앱**으로 만든다(별도 인증·배포·권한표).
- `POST /api/v1/stores`, `POST /api/v1/holidays`는 라우트를 제거한다. `seed-western-demo`는 `APP_ENV=production`에서 등록하지 않는다(D-4).

## 5. S-2 해결: 세션의 소속을 확인한 뒤에만 RLS 범위를 건다

### 5.1 지금
`backend/app/db/session.py:17`의 `bind_request_scope`가 URL의 `store_id`를 그대로 RLS 범위로 건다. `authorize()`는 비어 있다.

### 5.2 바꾼 뒤
```
get_db(request)            # 세션만 연다. 매장 범위를 걸지 않는다
  └ current_user(db)       # 쿠키 → auth_sessions 조회 → user_id. 없으면 401
      └ owned_store(store_id, user, db)
            # 1. store_members에 (store_id, user_id, revoked_at IS NULL)이 있는지 조회
            # 2. 없으면 404 STORE_NOT_FOUND  ← 남의 매장인지 없는 매장인지 구분해 주지 않는다
            # 3. 있으면 그때 bind_store_scope(db, RequestContext(store_id, actor=user_id))
```
- `/api/v1/stores/{store_id}/…` 라우터 전체에 `dependencies=[Depends(owned_store)]`를 **라우터 단위로** 건다. 엔드포인트마다 붙이지 않으므로 빠뜨릴 수 없다.
- `get_db`는 `request.path_params`를 읽지 않는다. 매장 범위는 `owned_store`만 건다. **`owned_store`를 거치지 않은 요청은 범위가 비어 있고, RLS가 fail-closed라 매장 표에서 0행이 나온다** (ADR-013 결정 2). 검사를 빠뜨리면 누출이 아니라 빈 결과가 된다.
- `tenancy.authorize()`는 지운다. 검사는 의존성 한 곳에만 둔다.
- `GET /api/v1/stores`는 `store_members`로 조인해 본인 매장만 돌려준다(S-1).
- 손님 경로는 지금처럼 QR 토큰에서 서버가 매장을 정한다(ADR-013 결정 6). 점주 세션 쿠키가 같이 와도 권한을 더 주지 않는다.

### 5.3 DB에서 한 번 더
앱 검사가 틀려도 DB가 막도록 두 번째 설정값을 쓴다.
- `owned_store`가 `app.current_user_id`도 같이 건다(트랜잭션 단위).
- `stores`의 정책을 바꾼다. 지금은 `food_app`이 **전 매장을 읽을 수 있다**(매장 선택 화면용). 바꾼 뒤: `stores`는 `store_members`에 본인이 있는 행만 보인다.
- `store_members`, `auth_sessions`는 `user_id = app.current_user_id`인 행만 보인다.
- 로그인 전에는 `user_id`를 모르므로 세션 조회는 `SECURITY DEFINER` 함수 `app_resolve_session(p_id_hash)`로 한다(QR의 `app_resolve_table_qr`와 같은 방식).

이 절의 정책 SQL은 구현 때 격리 테스트로 확정한다. 지금은 방향만이다.

### 5.4 테스트 (⑦과 같은 묶음, AC-6·AC-7)
- 로그인 없이 호출 → `공개` 경로가 아니면 401. `app.routes` 전부를 돈다.
- 점주 A의 세션으로 매장 B의 경로 → 404. 지금 있는 19개 경로 테스트를 세션 기반으로 바꾼다.
- 만료·폐기 세션 → 401. 소속 해제 직후 → 404.
- `Origin`이 다르거나 없는 `POST` → 403.
- `owned_store`를 일부러 뺀 테스트용 라우트 → 매장 표 0행(PostgreSQL 격리 테스트).
- 로그인 전후 세션 ID가 다르다. `state`가 틀리거나 재사용되면 400.

## 6. 직원: 기기 등록과 출퇴근 (구조만, 이번 구현 범위 밖)

### 6.1 인증 방식 비교
| | (a) 개인 폰 기기 등록 | (b) 직원도 카카오 로그인 | (c) 매장 공용 기기 + 개인 PIN |
|---|---|---|---|
| 직원이 할 일 | 처음 한 번 코드 입력 | 카카오 로그인·동의 | PIN 기억 |
| 본인 확인 강도 | 기기를 가진 사람 | 카카오 계정 주인 | PIN을 아는 사람(대리 입력 쉬움) |
| 우리가 저장하는 개인정보 | 점주가 붙인 표시 이름, 기기 토큰 해시 | + 카카오 회원번호 | 표시 이름, PIN 해시 |
| 기기 교체 | 점주가 다시 승인 | 다시 로그인하면 끝 | 영향 없음 |
| 매장에 있다는 증거 | 없음(따로 필요) | 없음(따로 필요) | 있음(기기가 매장에 있다) |
| 카카오 심사 영향 | 없음 | 동의 항목·심사 대상이 늘 수 있음(`미확인`) | 없음 |

**추천: (a)를 기본으로 한다.** 직원에게 계정을 요구하지 않고, 저장하는 개인정보가 가장 적다. (b)는 기기를 자주 바꾸는 직원을 위한 선택 사항으로 나중에 붙일 수 있게 `staff_devices`와 `users`를 분리해 둔다. (c)는 "매장에 있다는 증거"가 법적·운영상 필요하다고 확인되면 다시 본다(D-A4, `미확인`).

### 6.2 기기 등록
1. 점주가 화면에서 **일회용 등록 코드**를 만든다(6~8자리, 10분, 1회, 직원 표시 이름과 함께). 코드 없이 등록을 요청하는 경로는 없다(위협분석 A-4).
2. 직원이 자기 폰에서 코드를 입력한다. 서버가 기기 토큰을 만들어 `HttpOnly; Secure; SameSite=Lax` 쿠키로 준다. DB에는 해시만. 상태는 `PENDING`.
3. **점주가 승인**해야 `ACTIVE`가 된다. 승인 전에는 출퇴근을 찍을 수 없다.
4. 점주는 기기 목록을 보고 언제든 **폐기**(`REVOKED`)한다. 퇴사 처리 시 그 직원의 기기를 모두 폐기한다.

### 6.3 토큰 탈취 대응
- 기기 토큰은 쓸 때마다(또는 하루에 한 번) **새 값으로 바꾼다**. 바뀌기 전 값이 다시 오면 탈취로 보고 그 기기를 즉시 폐기하고 점주에게 알린다.
- 기기 토큰으로 할 수 있는 일은 **본인 출퇴근 기록과 본인 기록 조회뿐**이다(D-1). 매장 데이터는 못 읽는다. 훔쳐도 피해가 작다.
- 일정 기간 안 쓴 기기는 자동 만료한다(기간은 D-A1과 함께).
- 한계: 쿠키 기반 토큰은 기기에 묶이지 않는다. 쿠키를 복사하면 다른 기기에서 쓸 수 있다. 회전과 재사용 감지로 **알아챌** 뿐이다. 기기에 묶으려면 WebAuthn(패스키)이 필요하다. 지금은 넣지 않고 선택지로 남긴다.

### 6.4 출퇴근 기록과 수정 이력
- `attendance_events`: `id`, `store_id`, `staff_id`, `device_id`, `kind`(`IN`/`OUT`), `occurred_at`(**서버 시각**), `created_at`. 기기 시각은 믿지 않는다.
- `attendance_corrections`: `id`, `store_id`, `event_id`(고치는 대상, 누락 추가면 null), `corrected_kind`, `corrected_at`, `reason`(필수), `corrected_by_user_id`, `created_at`.
- **원본은 고치지도 지우지도 않는다.** 정정은 새 행으로만 쌓는다. 화면은 "원본 + 마지막 정정"을 보여 주고 이력 전체를 펼쳐 볼 수 있다.
- DB 권한으로 강제한다: 두 표 모두 앱 계정에 `INSERT`, `SELECT`만 준다. `audit_events`와 같은 방식(§8).
- 정정은 점주만 한다. 직원은 자기 기록을 읽기만 한다.

### 6.5 미확인 (추측으로 채우지 않는다)
- 출퇴근 기록의 법정 보관 기간과 필수 항목.
- 위치 또는 매장 네트워크 확인이 필요한지.
- 직원이 자기 기록을 열람·정정 요구할 권리의 범위.
- 직원 식별 정보(이름 등)를 어디까지 받아야 하는지.
- 이 기록이 급여 계산의 근거로 쓰일 때 요구되는 요건.

### 7.1 지금 유지 (익명)
- QR 토큰으로 테이블을 찾고, 익명 기기 쿠키 `food_guest_device`로 "같은 기기"만 구분한다(P-15). 로그인 없음.

- 호출 횟수 제한은 출시 준비 점검(감사 §7)에서 다룬다.

### 7.2 캐릭터 저장 시 카카오 (전역 계정, 12월 초 이후)
- 손님 계정은 점주 계정과 **다른 표**다: `guest_profiles`(전역, `provider`, `provider_user_id`). `users`와 합치지 않는다. 같은 카카오 계정이 점주이면서 손님일 수 있지만, 한쪽 세션이 다른 쪽 권한을 주면 안 된다.
- 세션도 분리한다: 손님 세션 쿠키는 이름·경로가 다르고 `/api/guest/` 아래에서만 유효하다.
- **등록하기 전에는 아무것도 저장하지 않는다 (U-23).** 등록할 때 받는 것은 카카오 회원번호뿐이다(닉네임·이메일·전화 안 받음).
- 등록 시 익명 기기에 묶여 있던 캐릭터를 `guest_profile_id`로 옮긴다. 동의 기록은 `consents`에 남긴다.
- 카카오 앱을 점주용과 손님용으로 나눌지, 한 앱에서 동의 항목만 다르게 할지는 `미확인`(D-A5).
- 이번 범위 아님. 표 구조가 점주 쪽 설계와 충돌하지 않는지만 확인했다: 충돌 없음.

## 8. DB 역할과 권한 (S-8 포함)

### 8.1 지금
- `food`(소유자): 마이그레이션.
- `food_app`(런타임): `backend/scripts/ensure_runtime_role.py:37`이 **모든 표에** `SELECT, INSERT, UPDATE, DELETE`를 주고, `ALTER DEFAULT PRIVILEGES`로 **앞으로 만들 표에도 자동으로** 같은 권한을 준다.

### 8.2 바꾼 뒤
| 역할 | 누가 쓰나 | 권한 |
|---|---|---|
| `food` | 마이그레이션만 | 소유자 |
| `food_app` | 점주 API | 매장 표 DML. `audit_events`·`attendance_*`는 `INSERT`, `SELECT`만 |
| `food_guest` | 손님 API (§8.4) | 아래 표의 최소 권한 |
| `food_admin` | 운영자 스크립트 | `stores`, `store_members`, `store_invites`, `holidays` DML, `audit_events` `INSERT` |

- `ALTER DEFAULT PRIVILEGES … GRANT … ON TABLES`를 **없앤다**. 새 표는 권한이 0에서 시작하고, 마이그레이션에서 표마다 명시해 준다. 권한을 빠뜨리면 기능이 안 돌아가 바로 드러난다. 지금 방식은 빠뜨리면 조용히 과한 권한이 생긴다.
- 테스트: "모든 매장 표에 RLS 정책이 있다"와 "역할별 권한이 이 표와 같다"를 격리 테스트에 넣는다(위협분석 S-7).

### 8.3 S-8: `audit_events`를 앱 계정이 고치거나 지우지 못하게
두 겹으로 한다.
1. **권한 회수**: `REVOKE UPDATE, DELETE, TRUNCATE ON audit_events FROM food_app, food_guest, food_admin`. 남는 것은 `INSERT`, `SELECT`.
2. **트리거**: `BEFORE UPDATE OR DELETE`와 `BEFORE TRUNCATE` 트리거가 예외를 던진다. 권한을 실수로 다시 줘도 막힌다.

- 코드 영향 없음: 앱은 `audit_events`에 `INSERT`만 한다(확인, `backend/app/services/menus.py:32`).
- `actor`를 고정값 `local_operator`에서 `user:<id>`, `guest`, `staff:<id>`, `operator:<이름>`으로 바꾼다.
- **한계**: 소유자 `food`와 DB 슈퍼유저는 트리거를 끄고 고칠 수 있다. 여기까지 막으려면 로그를 DB 밖(추가만 되는 저장소)으로 내보내야 한다. 지금은 하지 않는다. 출시 준비 점검의 백업 항목과 함께 본다.
- 보관 기간이 정해지면 삭제는 소유자 계정의 별도 절차로만 한다(`미확인`: 기간).

### 8.4 손님 전용 DB 역할 `food_guest`: 가능
**가능하다.** 조건이 하나 있다: 별도 로그인 역할 + 별도 연결 풀이어야 한다.

- 안 되는 방식: `food_app`으로 접속해 `SET ROLE food_guest`. SQL 주입이 생기면 `RESET ROLE` 한 줄로 풀린다. 경계가 되지 못한다.
- 되는 방식: `food_guest`가 직접 로그인한다. 백엔드가 엔진을 두 개 만든다(`DATABASE_URL`, `GUEST_DATABASE_URL`). 손님 라우터는 `get_guest_db`만 쓴다.
- 비용: 연결 풀이 하나 늘고, 설정값이 하나 는다. 프로세스는 그대로 하나다.
- 얻는 것: 손님 경로(인터넷에 로그인 없이 열려 있는 유일한 쓰기 경로)에 SQL 주입이나 로직 버그가 있어도 메뉴·원가·재고·매출·세션 표를 **읽을 권한 자체가 없다**.

`food_guest` 권한 (코드에서 읽은 것, 구현 때 격리 테스트로 확정):
| 표 | 권한 | 쓰는 곳 |
|---|---|---|
| `table_qr_tokens` | 없음. `app_resolve_table_qr(text)` 실행 권한만 | 토큰 → 매장·테이블 |
| `store_tables` | `SELECT` | 테이블 이름·좌석 수 |
| `stores` | `SELECT` (필요한 열만: 이름, 영업 마감 시각) | 세션 자동 닫기 계산 |
| `visit_sessions` | `SELECT`, `INSERT`, `UPDATE` | 세션 열기, 목적·관계 |
| `session_slots` | `SELECT`, `INSERT`, `UPDATE`, `DELETE` | 슬롯 추가·차지·삭제 |
| `guest_devices` | `SELECT`, `INSERT`, `UPDATE` | 기기 등록, `last_seen_at` |
| `audit_events` | `INSERT` | 감사 기록 |
| 그 밖의 모든 표 | **없음** | 메뉴, 식자재, 레시피, 재고, 주문, 수집, `users`, `auth_sessions`, `store_members` 등 |

`stores`를 열 단위로 줄지(열 권한 또는 뷰)는 구현 때 정한다. RLS 정책은 지금 것을 그대로 쓴다(역할이 달라도 `app.current_store_id` 기준은 같다).

## 11. 발견: `/food`가 다른 앱과 같은 출처다
`https://lci.leejblab.site/food/`는 LCI 앱과 **호스트가 같다**(`deploy/README.md`, 경로 규칙으로만 나뉜다). 브라우저의 보안 경계는 경로가 아니라 출처(스킴 + 호스트 + 포트)다.
- LCI 앱에 XSS가 하나 있으면, 그 스크립트가 로그인한 점주의 브라우저에서 `/food/api/…`를 **같은 출처로** 호출할 수 있다. `HttpOnly`는 쿠키를 읽지 못하게 할 뿐, 요청에 실리는 것은 막지 못한다. `SameSite`와 `Origin` 검사도 같은 출처라 통과한다.
- 쿠키 `Path=/food`는 보안 경계가 아니다.
- CSRF 토큰을 넣어도 같은 출처의 스크립트는 토큰을 가져올 수 있다.

**해결은 호스트 분리뿐이다**: 전용 호스트(예: `food.<도메인>`)로 옮기면 `__Host-` 접두사 쿠키(`Secure`, `Path=/`, `Domain` 없음 강제)를 쓸 수 있고 `/food` basename(P-14)도 없앨 수 있다. LCI 쪽 코드는 이번에 보지 않았다(`미확인`). → D-A7.
