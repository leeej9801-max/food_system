# 요구사항 로드맵 (2026-11-11)

사용자가 2026-11-11에 다시 확인한 요구사항을 적고, 구현 단계로 나눈다. 단계마다 WO를 따로 쓰고 확인을 받은 뒤 구현한다.

## 1. 요구사항 원문 (사용자 정리)
1. 누구랑 방문했는지는 직원이 선택한다. 손님이 고르면 불편한 상황이 있을 수 있다.
2. 테이블은 일단 전부 4인석으로 한다.
3. 결과로 볼 값: 연령 객층, 시간대별 테이블 회전 수, 방문 목적. 평일과 주말을 나눠 볼 수 있어야 한다.
4. 날씨, 매출 목표(직접 설정)와 실적, 객수 목표와 실제 객수, 객단가 목표와 실제 객단가, 오늘의 베스트 메뉴, 오늘의 워스트 메뉴(재료가 남아 버려지는 메뉴). 주별과 월별로도 확인한다.
5. 인건비 관리 화면
6. 직원 출퇴근 화면 연결
7. 사업이익 관리 화면
8. 캘린더 일정 조율 관리 화면
9. 마케팅 관련 화면
- 관리자 모드와 직원 모드를 나눈다.

## 2. 지금 상태
| 번호 | 상태 |
|---|---|
| 1 | 부분 구현. 방문 목적과 관계는 손님이 넣으면 손님 값이 우선하고, 직원은 바꿀 수 없다(`app/services/visit_profile.py:61`, U-31). 요구사항과 반대이므로 바꿔야 한다. |
| 2 | 도면 프리셋(`meal_love`)과 배치 초기화는 4인석으로 만든다(`app/services/floor.py:64`). 이미 만든 테이블은 초기화를 눌러야 바뀐다. |
| 3 | 데이터(연령대, 인원, 착석·종료 시각, 목적)는 쌓이고 있다. 분석 화면은 없다. 평일·주말 구분 함수(`app/services/holidays.py:48 day_type`)는 있다. |
| 4 | 메뉴별 매출 분석만 있다. 목표, 객수 연결, 날씨는 없다. |
| 5~9 | 없다. 7(사업이익)은 손익 화면(WO-20261111-002, -003)과 겹친다. 범위를 정해야 한다. |
| 모드 분리 | 로그인(⑦)이 있어야 한다. ⑦은 보류 중이다(점주 지정 방식은 U-44 초대 링크로 결정, 동시 세션 수와 직원 출퇴근 방식은 미결정). |

## 3. 단계 (제안)
| 단계 | 내용 | 선행 조건 |
|---|---|---|
| 1 | 분석·손익 통합, 지출 관리 모달, 지급일 알림 (WO-20261111-003) | 없음 |
| 2 | 요구 1·2·3: 관계는 직원 입력으로 바꾸고, 기존 테이블을 4인석으로 바꾸고, 객층·회전 수·목적 분석(평일/주말)을 만든다. | 없음 |
| 3 | 요구 4: 일·주·월 목표와 실적(매출, 객수, 객단가), 베스트·워스트 메뉴, 날씨 | 날씨는 기상청 API 키가 필요하다(사용자가 발급). 워스트 메뉴 기준을 정해야 한다. |
| 4 | 로그인 ⑦과 관리자·직원 모드, 직원 출퇴근(요구 6), 인건비 관리(요구 5) | 동시 세션 수, 직원 출퇴근 방식 결정 |
| 5 | 요구 7·8·9: 사업이익, 캘린더 일정 조율, 마케팅 | 각 화면의 범위 인터뷰 |

## 4. 정해야 할 것
- 단계 2: 손님 화면에서 관계 선택을 없앨지, 손님은 목적만 고르게 할지.
- 단계 3: 워스트 메뉴의 기준. 제안은 "팔린 양이 적고 재고 재료의 유통기한이 가까운 메뉴"다. 지금은 재료 유통기한 데이터가 없다.
- 단계 5: 사업이익 화면이 손익 화면과 무엇이 다른지. 예를 들어 연간 누적, 목표 이익, 대출·감가상각 같은 것이 들어가는지.
