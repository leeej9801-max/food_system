# 영수증·거래명세서 OCR 리서치 (2026-11-18)

> 이 문서는 조사 결과와 제안이다. 제공자 선택, 보관 기간, 비용 상한 같은 항목은 **확정하지 않았다**. 결정이 필요한 항목은 §7에 모았다. 외부 서비스 정보는 모두 **확인일 2026-11-18 기준**이다. 실제 키와 실제 거래명세서로 검증한 것은 하나도 없으므로 연동 관련 서술은 전부 `PROVISIONAL`이다.

## 0. 요약

- **레포 현황:** 입고(`InventoryReceipt`)는 1행 = 1식자재 구조이고 단가는 `total_cost / base_quantity`로 결정론적으로 계산된다. 파일 업로드, 이미지 저장소, 외부 AI 호출, 유통기한 필드, 멱등키는 없다. CSV 미리보기 → 확정(`ImportBatch` + sha256 중복 경고) 패턴은 재사용할 수 있다.
- **추천(안 A):** 비전 LLM에 JSON 스키마를 지정해 "읽기"만 시키고, 계산·검증·매칭·입고 생성은 결정론적 코드로 한다. 장당 비용은 1원 안팎으로 추정된다. 단 국외 이전 고지가 필요하다.
- **대안(안 B):** Upstage Information Extract(국내 업체, 문서 특화, 페이지당 약 $0.04). 데이터 보관 위치와 정책은 미확인이다.
- **비추천:** AWS Textract AnalyzeExpense는 영어 전용이다. CLOVA Document OCR의 영수증 모델에는 거래명세서가 없고 월 기본료가 있다. 자체 호스팅 OCR(PaddleOCR)은 ARM 성능 미검증, 표 구조 파싱 부담, 운영 부담 때문에 1단계에서 제외한다.

### A-2. CSV/Excel 수집 어댑터(POS 모드 C)와 파일 저장

- `POST /imports/sales-csv/preview`는 **JSON 본문의 `csv_text`** 를 받는다. multipart 파일 업로드가 아니다. `POST /imports/{batch_id}/commit`으로 확정한다 (`backend/app/api/v1/endpoints/imports.py:51-72`).
- 서비스: BOM 제거 → sha256 `file_hash` → `find_committed_by_hash`로 같은 파일을 이미 확정했는지 경고 (`backend/app/services/imports.py:191-199`, `backend/app/repositories/import_batches.py:9`). 확정은 `preview_json`에서 다시 만든다 (`backend/app/services/imports.py:356`). `source_mode="CSV_UPLOAD"` (`:410`).
- `ImportBatch`: `file_name`, `file_hash`(64, index), `status PREVIEWED|COMMITTED`, `duplicate_file_warning`, 행 수 집계, `preview_json` Text (`backend/app/db/models/__init__.py:380-401`).
- **파일/이미지 저장소 없음.** `UploadFile`도, `python-multipart` 의존성도 없다 (`backend/pyproject.toml`).

**시사점:** "미리보기 → 확정" 2단계와 해시 중복 경고는 그대로 따른다. 이미지를 받으려면 `python-multipart`와 저장 위치(로컬 볼륨 또는 OCI Object Storage)가 새로 필요하다.

### A-3. 유통기한

- 백엔드와 프런트엔드 어디에도 expiry·유통기한 필드가 없다(grep 결과 0건).
- 문서: "지금은 재료 유통기한 데이터가 없다" (`DOCS/10_설계/요구사항_로드맵_20261111.md:52`). 유통기한이 지나 폐기하는 것은 `SPOILAGE` 조정으로 처리한다 (`DOCS/07_구현보고서/IR-20261115-003_재고입고_작업화면_개선.md:41`). 로드맵에 유통기한 언급이 있다 (`DOCS/음식점_AX_개업전후_로드맵.md:175`).

**장당 비용 추정(계산식, 실측 아님):** 이미지 약 1.5K 토큰 + 지시문 약 1K + 출력 약 1K(라인 20개 기준).
- Haiku 5.5: 2.5K×$0.10/1M + 1K×$0.50/1M ≈ **$0.0008/장**(약 1원).
- Gemini 3.1 Flash-Lite: 2.5K×$0.25/1M + 1K×$1.50/1M ≈ **$0.0021/장**(약 3원).
- 매장당 월 60장이면 월 수십~수백 원 수준이다. 비용보다 **실패 재시도 폭주와 악용(무한 업로드)** 이 더 큰 위험이다.

**장점**
- 영수증과 거래명세서(표)를 같은 경로로 처리한다.
- 우리가 정한 스키마(품목명, 규격, 수량, 단위, 단가, 금액, 과세/면세)로 바로 받는다.
- 손글씨 수정이나 구겨진 사진에 비교적 강하다(일반론, 실측 **미확인**).

**위험**
- **환각:** 흐릿한 숫자를 그럴듯하게 채우거나, 줄을 합치거나 빠뜨린다. 스키마 강제는 "형식"만 보장하고 "값"은 보장하지 않는다.
- 모델이 스스로 매긴 신뢰도는 신뢰할 수 없다. 검토 여부는 §B-4의 결정론적 검증 결과로 판단한다.
- 국외 이전: 공급처 상호, 사업자번호, 카드번호 일부, 담당자 이름 등이 들어갈 수 있다. 개인정보 처리방침 고지 대상인지 판단이 필요하다(§7).
- 모델 교체(deprecation)가 잦다. 실제로 Gemini 2.5 Flash는 2026-12-01에 전환되고, Upstage receipt 모델은 Deprecated 상태다. 어댑터에 `model` 버전을 기록하고 교체할 수 있게 둔다.

### B-4. 안정성 기법(결정론적 코드로 구현)

1. **줄 검증:** `|수량 × 단가 − 금액| ≤ 허용오차`. 허용오차는 원 단위 반올림 1원 또는 0.5%. 거래명세서는 단가가 공급가 기준이고 세액 칸이 따로 있는 경우가 많으니 두 가지 모두 시험한다. 실패한 줄은 빨간색으로 표시한다.
2. **합계·부가세 검증:**
   - `Σ라인금액 = 공급가액` (또는 합계).
   - `공급가액 + 세액 = 합계`.
   - 과세분 세액 ≈ `round(과세 공급가액 × 0.1)`, 줄마다 반올림한 경우 ±10원 허용.
   - 부가세 포함 영수증은 `세액 = 합계 × 10/110`(절사·반올림 둘 다 허용).
   - **식자재는 면세(미가공 농·축·수산물)가 섞인다.** 면세 줄을 0으로 두고 과세분만 비교한다. 면세 여부를 추출 스키마의 필드로 받는다.
3. **검토 판정은 우리가 계산한다:** 위 검증 실패, 단위 파싱 실패, 매칭 점수 미달, 필수값 누락 가운데 하나라도 있으면 그 줄은 `NEEDS_REVIEW`다. 1단계에서는 **자동 확정을 하지 않는다**(기획서 `:686`, R365의 "Always Require OCR Verification" 패턴[23]).
4. **중복 업로드 차단:**
   - ① 파일 sha256: 기존 `ImportBatch` 방식으로 `(store_id, file_hash)` 유니크.
   - ② 같은 종이를 다시 찍은 경우: `공급처 + 문서일자 + 합계`가 일치하면 경고. 지각 해시(pHash)는 의존성이 늘어나니 보류.
5. **품목명 매칭(LLM 미사용):**
   - 정규화: NFC → 공백·괄호·규격 제거 → 소문자.
   - 순서: ① `ingredient_alias` 정확 일치 → ② 식자재명 정확 일치 → ③ `rapidfuzz` `token_set_ratio`. 한글은 `unicodedata.normalize("NFD")`로 자모를 분해한 뒤 비교한다(표준 라이브러리로 처리, 추가 의존성 없음).
   - 점수가 임계값 이상이면 "추천"만 하고, 사장이 확인하면 `ingredient_alias`에 저장해 다음부터 정확 일치시킨다. 국내 오픈소스 사례도 같은 "확인한 것을 학습" 구조다[24].
6. **단위 문자열 파싱:**
   - 정규식으로 `10kg×2박스`, `1.8L*6`, `500g`, `20입`, `1BOX(10kg)`, `2kg x 3`를 `(수량, 단위 ∈ kg|g|L|ml|ea, 포장수)`로 바꾼다.
   - 예: `10kg×2박스` → 20kg → `factor_to("kg","g")` → 20,000g. 이미 있는 `backend/app/core/units.py`를 쓴다.
   - `박스/봉/팩/포/입`처럼 무게를 모르는 포장 단위는 **추측하지 않는다.** 식자재의 `conversion_factor`나 별칭에 저장된 환산값이 있을 때만 쓰고, 없으면 `NEEDS_REVIEW`로 둔다.
7. **재시도와 타임아웃:**
   - 외부 호출 타임아웃은 30초.
   - 429, 5xx, 타임아웃만 지수 백오프로 최대 2회 재시도한다.
   - 스키마 위반 JSON은 1회 재요청한 뒤 `FAILED`로 둔다.
   - 4xx(인증, 용량)는 재시도하지 않는다.
   - 실패해도 원본 이미지와 수동 입력 경로는 남긴다(데이터 유실 없음).
8. **작업 상태:**
   - `UPLOADED → EXTRACTING → EXTRACTED | NEEDS_REVIEW | FAILED → CONFIRMED | DISCARDED`.
   - 확정은 상태 검사로 멱등하게 만든다. 이미 `CONFIRMED`면 409를 돌려준다. 라인↔입고 링크에 유니크를 둔다.
9. **입력 방어:**
   - 업로드 크기는 10MB 이하로 제한하고, MIME은 jpeg/png/pdf(HEIC는 결정 필요)만 받는다. nginx `client_max_body_size`도 맞춘다.
   - EXIF 회전을 적용하고 **GPS 메타데이터를 제거**한다.
   - 긴 변을 약 2,000px로 줄인다(토큰 절감).
   - 영수증 안의 문구가 지시문처럼 작동하는 프롬프트 주입에 대비해, 도구 호출 없이 스키마 출력만 받는다.

### C-2. 어댑터 인터페이스(초안)

POS 모드 A/B/C처럼 **수집 어댑터만 바꾸고** 내부 모델과 화면은 공통으로 쓴다. 어댑터는 "읽기"만 하고 계산하지 않는다.

```python
# backend/app/integrations/purchase_ocr/base.py (제안, 미구현)
from typing import Protocol
from pydantic import BaseModel

class ExtractedLine(BaseModel):
    raw_name: str
    raw_spec: str | None = None          # "10kg×2박스" 원문 그대로
    quantity_text: str | None = None     # 숫자도 문자열로 받아 우리가 파싱
    unit_price_text: str | None = None
    amount_text: str | None = None
    tax_exempt: bool | None = None       # 면세 표시(있으면)

class ExtractedDocument(BaseModel):
    doc_type: str                        # RECEIPT | STATEMENT | UNKNOWN
    supplier_name: str | None = None
    document_date_text: str | None = None
    supply_amount_text: str | None = None
    vat_amount_text: str | None = None
    total_amount_text: str | None = None
    lines: list[ExtractedLine]

class ExtractResult(BaseModel):
    document: ExtractedDocument | None
    raw: dict                            # 제공자 원문 응답(보관용)
    adapter: str                         # "llm_vision" | "upstage_ie" | "manual"
    model: str                           # 제공자 모델 버전
    latency_ms: int
    input_tokens: int | None = None
    output_tokens: int | None = None
    error_code: str | None = None        # TIMEOUT | RATE_LIMIT | SCHEMA_INVALID | PROVIDER_ERROR

class PurchaseDocumentExtractor(Protocol):
    def extract(self, image: bytes, mime: str) -> ExtractResult: ...
```

- 숫자를 문자열로 받는 이유: 쉼표, "₩", 소수점 오인식을 우리 코드에서 같은 규칙으로 정규화하고 검증하기 위해서다.
- 설정 키(제안, 이름만): `purchase_ocr_mode`(`off|llm_vision|upstage_ie`), `purchase_ocr_api_key`, `purchase_ocr_model`, `purchase_ocr_timeout_s`, `purchase_ocr_monthly_cap`. 기본값은 `off`.
- 테스트는 고정 응답을 돌려주는 `FakeExtractor`로 한다. 실제 키는 테스트 fixture에 넣지 않는다.

### C-3. 테이블 초안 (모두 `store_id` + RLS `store_isolation`, PK는 UUID v7)

| 테이블 | 주요 컬럼 |
|---|---|
| `purchase_document` | `store_id`, `file_hash`(64) **UNIQUE(store_id, file_hash)**, `storage_key`, `mime_type`, `size_bytes`, `doc_type`, `status`, `supplier_name`, `document_date`, `supply_amount`, `vat_amount`, `total_amount`, `check_summary`(Text JSON), `attempt_count`, `last_error_code`, `uploaded_at`, `extracted_at`, `confirmed_at` |

| `purchase_document_line` | `document_id`, `line_no`, `raw_name`, `raw_spec`, `parsed_quantity`, `parsed_unit`, `pack_count`, `unit_price`, `amount`, `tax_exempt`, `line_check`(OK/MISMATCH/MISSING), `matched_ingredient_id`, `match_score`, `match_method`(ALIAS/EXACT/FUZZY/MANUAL), `status`(PENDING/CONFIRMED/SKIPPED), `inventory_receipt_id` **UNIQUE** |

- 금액 컬럼 이름에 `_amount`를 쓰는 것은 기존 `total_cost`와 이름이 다르다. 확정 전에 용어를 통일한다.

### C-4. 실패·재시도·비동기

- **1단계(최소):** 동기 `def` 엔드포인트에서 추출한다(threadpool). 타임아웃은 30초다. 실패하면 `FAILED`로 두고 "다시 추출" 버튼으로 수동 재시도한다. 1~2인 매장 규모에서는 threadpool 40개로 충분하다고 판단한다(추정).
- **2단계(필요할 때):** `status=UPLOADED`인 행을 `SELECT … FOR UPDATE SKIP LOCKED`로 가져가는 DB 폴링 워커 프로세스. Celery·Redis 없이 재시도와 가시성을 얻는다. ADR-014(동기 유지)와 충돌하지 않는다.
- `BackgroundTasks`는 쓰지 않는다. 재시도가 없고 워커가 죽으면 작업이 사라진다(상위 AGENTS 표 기준).

### C-5. 비용 상한

- 매장별 월 추출 건수 상한(`purchase_ocr_monthly_cap`)을 둔다. 상한을 넘으면 429와 "수동 입력" 안내를 보낸다. 집계는 `purchase_document_extraction` 행 수로 한다.
- 전체 월 예산은 제공자 콘솔의 예산 알림으로 이중 방어한다.
- 같은 문서의 재추출은 하루 3회로 제한한다(제안).
- 숫자 값(상한, 횟수)은 **결정 필요**(§7).

### C-6. 옵션 비교와 추천

| 기준 | **A. 비전 LLM + JSON 스키마** | B. Upstage Information Extract | C. 자체 PaddleOCR(ARM) + 규칙 파서 |
|---|---|---|---|

**추천: A안.** 근거는 다음과 같다.
- 장당 비용이 가장 낮다.
- 영수증과 거래명세서를 같은 경로로 처리한다.
- 결과를 우리 스키마로 받으므로 파싱 코드가 가장 적다.
- 정확도 위험은 §B-4의 결정론적 검증, 자동 확정 금지, 사장 확인으로 막는다. 이는 AGENTS 규칙("계산은 LLM에 맡기지 않는다")과도 맞는다. LLM은 글자를 옮겨 적기만 하고, 계산은 하지 않는다.

**대안: B안.** 국외 이전을 피해야 한다는 결정이 나오면 B안을 쓴다. 어댑터만 바꾸면 된다.

**C안**은 2단계에 무료·오프라인 옵션으로 실측해 본다.

**채택 전 검증(필수):**
- 실제 거래명세서와 영수증 사진 30장 이상(다양한 공급처, 감열지, 구겨짐, 손글씨 포함)으로 A, B를 같은 스키마에 넣어 비교한다.
- 지표는 라인 단위 정확도, 줄합계 검증 통과율, 장당 시간과 비용이다.
- 이 실측 전까지 모든 연동은 `PROVISIONAL`이다.

## 7. 결정이 필요한 항목 (임의로 정하지 않음, `결정사항_로그.md` 등록 대상)

1. OCR 기능의 우선순위: 제품전략 논의(10-30)의 "부가 기능"과 인수인계의 "P1 후보"가 충돌한다.
2. 제공자: A(비전 LLM, 국외) vs B(Upstage, 국내). 어떤 모델로 할지.
3. 국외 이전 고지와 동의: 개인정보 처리방침, 위탁 고지 문구(`개인정보_처리설계_초안.md`에 추가할지).
4. 원본 이미지 저장 위치(VM 로컬 볼륨 vs OCI Object Storage)와 보관 기간, 삭제 정책.
5. 매장별 월 추출 상한과 재추출 제한 값.
6. 매칭하지 못한 품목을 확인 화면에서 새 식자재로 등록할지(자동 생성은 하지 않는 것을 제안).
7. 면세와 과세 구분을 입고에 저장할지. 현재 `InventoryReceipt`에는 세액이 없고, D-05 원가 단가 산정과 연결된다.
8. 공급처를 문자열로 둘지 엔터티(`supplier`)로 만들지. 별칭 학습 범위가 달라진다.
9. 유통기한 필드를 도입할지(OCR 범위 밖으로 두는 것을 제안).
10. HEIC 업로드를 지원할지(iPhone 기본 포맷, 변환 의존성 필요).
11. 새 의존성 승인: `python-multipart`(업로드), `Pillow`(EXIF·리사이즈), `rapidfuzz`(매칭), 제공자 SDK 또는 `httpx` 본 의존성 승격.

| Mistral OCR 4.x | 쪽(평균·최소), 블록(4.1부터), 단어 단위. `confidence_scores_granularity`[F19] | 가능. 단 구조화 어노테이션 필드별 점수가 나오는지는 **미확인**. Azure 호스팅판은 이 파라미터를 지원하지 않음[F19] |
| CLOVA OCR | 응답 필드별 `inferConfidence`가 있다고 알려져 있으나 이번에 공식 문서로 **확인하지 못함** | 미확인 |
| Gemini (무료·유료) | 모델이 주는 신뢰도 없음. logprobs는 Vertex AI 일부 모델에서만 됐고, 3.x·최신 모델은 미지원이라는 사용자 보고가 다수[F20] | **불가.** 모델이 스스로 말하는 신뢰도는 쓰지 않는다(§B-2) |
| 로컬 VLM(llama.cpp) | 토큰 확률은 로컬에서 꺼낼 수 있음. 숫자 토큰 확률을 필드 점수로 바꾸는 코드는 직접 작성 | 이론상 가능, 실측 **미확인** |

**제안 기준(결정론적, 임계값은 실측 후 확정):**
1. **검증 실패(강조):** 수량×단가≠금액(허용 오차 ±1원 또는 반올림 규칙), 행 합계≠공급가액·합계, 단위 변환 실패, 날짜 파싱 실패. 이 신호는 모든 엔진에서 같게 쓴다. **Gemini처럼 점수가 없는 엔진은 이것만으로 노란 표시를 한다.**
2. **인식 저하(노랑):** OCR 점수가 있는 엔진에서 셀 최소 점수 < 임계값(초기값 0.80 제안, 미검증).
3. **매칭 불확실(노랑):** 임베딩 1위 유사도 < 임계값이거나 1위와 2위 차이가 작음(§9-3).
4. 어떤 경우에도 자동 확정하지 않는다. 노랑은 "먼저 보세요" 순서 표시일 뿐이다.

**한계:** 위 벤치마크는 문장·문서 검색 기준이다. **"깐마늘 1kg", "대파(국산)" 같은 짧은 품목명 매칭 근거는 찾지 못했다(미확인).** 짧은 이름은 철자 변형·약어·규격 표기가 많아서 임베딩만으로는 불안하다.

**제안:**
- 1차: **multilingual-e5-small(ONNX) + fastembed**. 품목명은 `query: ` 접두어로 넣는다(e5 계열 권장 방식).
- 매칭 점수는 결정론적 조합으로 만든다. 순서: 공급처별 별칭 사전 일치(최우선) → 정규화한 문자열 비교(규격·괄호·숫자 제거 후 `rapidfuzz` 문자 n-gram 유사도) → 임베딩 코사인.
- 실측 계획: 실제 매장 식자재 목록과 영수증 품목명 100쌍 이상으로 e5-small, e5-small-ko-v2, MiniLM의 Top-1 정확도를 비교한다. 한국어 미세조정판이 확실히 나으면 ONNX 변환 비용을 감수한다.
- **pgvector는 초기에 쓰지 않는다.** 매장당 식자재가 수백 개면 384차원 float32 기준 1,000개도 약 1.5MB다. 매장 식자재 임베딩을 DB(예: `bytea`)나 프로세스 메모리 캐시에 두고 numpy 행렬곱으로 코사인을 계산하면 밀리초 단위다(계산 추정). pgvector는 확장 설치·마이그레이션·RLS 검증 부담만 늘린다. 매장 수 × 품목 수가 수십만을 넘거나 매장 간 공용 카탈로그 검색이 필요할 때 다시 검토한다.
- 모델 버전(모델 이름 + 파일 해시)을 임베딩과 함께 저장한다. 모델을 바꾸면 전체를 다시 계산한다.
- 메모리: e5-small 세션 1개 상주 시 수백 MB(추정). A1 12GB에서 여유가 있다.

### 9-4. 이미지 저장 용량과 HEIC 변환

**장당 크기(추정):** WebP, 긴 변 2000px, 품질 80 기준 일반 사진 사례는 약 160~340KB였다[F27]. 영수증·명세서는 흰 바탕이 많아 **약 100~250KB/장**으로 추정한다(미실측). 글자 선명도를 위해 품질을 85~90으로 올리면 더 커진다.

| 매장당 월 장수 | 90일 보관 장수 | 매장당 용량(100~250KB/장) | 매장 100곳 |
|---|---|---|---|
| 30장 | 90장 | 약 9~23MB | 약 0.9~2.3GB |
| 100장 | 300장 | 약 30~75MB | 약 3~7.5GB |

- 썸네일(긴 변 400px, 장당 약 15~30KB 추정)을 따로 두면 10~15% 정도 늘어난다.
- OCI Always Free 블록 볼륨 총량(약 200GB)과 Object Storage 무료 용량(약 20GB)은 **이번 조사에서 출처를 다시 확인하지 못했다(미확인).** 위 추정치로는 매장 100곳까지 VM 볼륨으로도 충분하다. 저장 위치 결정은 §7-4에 남긴다.

**HEIC(iPhone 기본 포맷) 변환:**
- `Pillow`: EXIF 회전 보정(`ImageOps.exif_transpose`), 리사이즈, WebP 저장을 맡는다. 라이선스는 MIT-CMU(HPND 계열, 상업 이용 가능)로 알고 있으나 이번에 재확인하지 않았다(기억 기반).
- `pillow-heif` 1.8.1(2026-10-11): 소스는 BSD-3-Clause다. aarch64 manylinux 휠이 있다[F28].
- **주의: pillow-heif 바이너리 휠은 x265(GPLv2), libheif·libde265(LGPLv3)를 함께 담고 있어 휠 자체는 GPLv2다**[F29]. 서버 안에서만 쓰고 배포하지 않으면 GPL 배포 의무가 생기지 않는다는 것이 일반적인 해석이다. 그러나 법률 판단이므로 **결정 필요 항목**으로 둔다(§7-10, §7-11과 연결).
- 대안: 브라우저가 업로드 전에 JPEG로 바꾸게 한다. iOS Safari가 `<input type="file" accept="image/*">`에서 HEIC를 JPEG로 자동 변환해 올리는 경우가 많다고 알려져 있으나 **이번에 확인하지 못했다(미확인)**. 실기기 확인 후 서버 HEIC 지원 여부를 정한다.

### 9-5. 추천 조합과 대안

| 기준 | **추천: Gemini 3.1 Flash-Lite 유료 등급 + 결정론적 검증 + e5-small 매칭** | **대안: PaddleOCR 한국어 로컬 + 규칙 파서 + e5-small 매칭** |
|---|---|---|
| 정확도 | 영수증과 거래명세서 표를 우리 스키마로 바로 받는다. 환각은 수량×단가·합계 검증과 사장님 확인으로 막는다. 실측 **미확인** | 글자 인식은 합성 문서에서 좋다(CER 1~4%)[F3]. 하지만 영수증 검출과 표→행 재구성을 우리가 짜야 해서 행 오류가 더 많을 것으로 추정 |
| 비용 0원 여부 | 0원 아님. 장당 약 1~3원, 매장당 월 100장이면 월 약 100~300원(추정). 무료 등급은 실데이터에 쓰지 않음 | **0원**(VM 안에서 처리) |
| 개인정보 | 국외 전송. 유료 등급은 학습 미사용[F5]. 위탁·국외 이전 고지 필요 | **외부 전송 없음(최선)** |
| 신뢰도 점수 | 없음. 노란 표시는 검증 실패·매칭 불확실 기준만 쓴다 | 줄 단위 `rec_scores` 있음. 인식 저하 노랑 가능 |
| ARM 운영 부담 | 낮음(HTTP 호출만). 모델 교체 주기 대응 필요 | 높음. paddlepaddle aarch64 휠, 메모리 2~3GB, 장당 2~5초(추정), 일괄 처리 시 API와 CPU 경합 |
| 장당 시간(추정) | 수 초(네트워크 포함, **미확인**) | 2~5초 + 파싱(**미확인**) |

**추천 이유:** 사장님이 정한 "아주 싸게" 범위에 들어간다. 우리 코드 양이 가장 적다. 거래명세서 표까지 같은 경로로 처리한다. 무료 등급 대신 유료 등급을 쓰는 이유는, 약관상 무료 등급 입력이 제품 개선에 쓰이고 사람이 읽을 수 있기 때문이다[F5]. 무료와 유료의 월 비용 차이는 매장당 수백 원 이하로 추정된다.

**대안을 쓰는 경우:** "외부 전송 금지" 또는 "API 비용 0원"이 확정될 때. 어댑터 인터페이스(§C-2)는 그대로 두고 엔진만 바꾼다.

**보조 옵션(베타 비교 실험용):** Upstage Document OCR은 신규 $10 크레딧으로 약 6,600쪽을 무료로 실험할 수 있고, 단어 신뢰도를 준다[F8][F9][F10]. 추천안의 결과 숫자를 Upstage 단어와 대조해 "인식 저하" 노랑을 보강하는 2중 구성도 가능하다(장당 약 2원 추가). 실측 후 판단한다.

**공통 흐름:** 업로드 → Pillow(+HEIC) EXIF 보정·리사이즈·WebP 저장 → 작업 큐(매장별 동시 1건, 장 단위 재시도 상한) → OCR 엔진 → 결정론적 정규화·검증 → 'AI 정리하기'에서 별칭 사전 + 문자열 + e5-small 매칭 → 노랑 표시 → 사장님 확인 → 입고 확정.

### 9-6. 결정 필요 항목 추가(§7에 이어서)

12. 베타에서 Gemini **무료 등급**을 실매장 영수증에 쓸지. 이 리서치는 약관을 근거로 쓰지 않는 것을 제안한다.

### 9-7. 미확인 항목(이 절)

- 모든 후보의 **한국어 영수증·거래명세서 실측 정확도**. PaddleOCR 수치는 일반 한국어 텍스트와 합성 문서 기준이다.
- PaddleOCR·Qwen3-VL의 **Oracle A1(aarch64) 실제 속도와 메모리**. 이 절의 A1 시간은 x86·Raspberry Pi 수치에서 추정했다.
- Gemini 무료 등급 정확한 한도(공식 페이지는 AI Studio 안에서만 보여 줌), Gemini 3.x 이미지 토큰 산정 방식, 유료 등급 실제 응답 시간.
- Google Cloud 신규 크레딧을 Gemini API 유료 등급에 쓸 수 있는지.
- CLOVA General OCR 무료 구간(100건 vs 1,000건)과 응답의 신뢰도 필드 형식.
- Upstage $10 크레딧 만료 기간·카드 등록 필요 여부, 처리 리전·학습 이용 정책.
- Mistral OCR 공식 단가(제3자 자료만 확인), 어노테이션 필드별 신뢰도 제공 여부, 데이터 학습 정책.
- Qwen3-VL-2B의 한국어 OCR 지원 여부.
- multilingual-e5-small·bge-m3·Pillow 라이선스(기억 기반), e5-small-ko-v2 ONNX 제공 여부, **짧은 한국어 품목명 매칭 품질**.
- OCI Always Free 스토리지 한도, iOS Safari HEIC 자동 변환 동작.
- WebP 장당 크기는 일반 사진 사례에서 추정했다. 실제 영수증 사진으로 측정해야 한다.
