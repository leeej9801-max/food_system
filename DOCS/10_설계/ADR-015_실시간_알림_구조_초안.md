# ADR-015 (초안) — 실시간 알림 구조

## 상태
초안. **설계 문서만 있고 구현은 없다.** 사용자 결정을 기다린다.

## 배경
- 요구 사항(사용자 확정, 2026-11-11): 여러 테이블이 동시에 요청한다. 요청이 매장 화면에 실시간으로 반영되어야 한다. 웹소켓 알림이 필요하다.
- ADR-014는 async 전환을 보류하면서 다시 정할 조건을 적었다. 그중 "긴 연결(SSE 등)이 확정된다"가 충족됐다. 그래서 다시 정한다.
- 지금 구조: 라우트 전부 동기 `def`, 동기 `Session` + psycopg, uvicorn 워커 1개(`compose.yaml:51`), 매장 격리는 RLS(ADR-013). 프론트는 TanStack Query이고 주기 조회(`refetchInterval`)는 쓰지 않는다. 앞단 nginx(`frontend/nginx.conf`)의 `/food/api/`에는 웹소켓 업그레이드 헤더 설정이 없다.

## 규모 가정
전부 **가정**이다. 측정값이 아니다. 실제 매장 수치가 나오면 이 표부터 고친다.

| 항목 | 값 | 구분 |
|---|---|---|
| 매장 수(출시 1년 안) | 50 | 가정 |
| 매장당 테이블 | 15 | 가정 |
| 매장당 직원·점주 화면(웹소켓 연결) | 3 | 가정 |
| 동시 웹소켓 연결(매장 화면) | 50 × 3 = 150 | 가정 |
| 손님 폰도 연결할 경우 추가 연결 | 50 × 15 × 2명 = 1,500 | 가정 |
| 피크 때 매장당 손님 요청 | 분당 30건(테이블당 2건) | 가정 |
| 전체 피크 알림 | 50 × 30 / 60 = 초당 25건 | 가정 |
| 알림 지연 허용치 | 2초 이내 | 가정 |
| 알림 1건 크기 | 200바이트 이하(종류 + ID만) | 설계값 |

읽는 법: 요청 처리량(초당 25건)은 동기 구조로도 충분하다. ADR-014의 계산으로 워커 하나가 초당 약 300건이다(이것도 가정). 문제는 처리량이 아니라 **오래 열려 있는 연결 수**다. 동기 라우트는 연결 하나가 스레드 하나를 잡는다. 스레드풀 기본값은 40이라 연결 150개를 동기로 들 수 없다. 긴 연결만은 async여야 한다.

## 선택지

### (a) 전면 async 전환
라우트·서비스·repository·테스트를 전부 `AsyncSession`으로 바꾼다. 웹소켓도 같은 구조 안에 둔다.
- 장점: 구조가 하나다. lee-start 템플릿과 같아진다.
- 단점: 서비스 약 3,700줄과 테스트 102개를 전부 고친다. 매장 범위를 거는 `after_begin` 훅(`backend/app/db/tenancy.py`)을 async 세션에서 다시 증명해야 한다. 격리 회귀가 가장 큰 위험이다. 지연 로딩이 async에서 에러가 되므로 관계 접근을 전부 찾아야 한다.
- 이 선택이 푸는 문제: 긴 연결. 그런데 그건 (b)로도 풀린다. 일반 요청의 처리량은 지금 문제가 아니다.

### (b) 동기 API 유지 + 웹소켓 경로만 async + PostgreSQL LISTEN/NOTIFY
기존 라우트는 그대로 둔다. 웹소켓 엔드포인트 하나와 알림 수신기 하나만 async로 새로 만든다. 알림은 DB가 나른다.
- 장점: 바꾸는 범위가 작다(새 파일 몇 개). 새 인프라가 없다(Redis 없음). 알림이 **DB 트랜잭션이 commit될 때만** 나간다. rollback된 변경은 알리지 않는다. 워커가 여러 개여도 모두 같은 DB를 듣는다.
- 단점: 한 프로세스에 동기와 async가 같이 있다. 규칙이 필요하다("async 코드는 `app/realtime/` 안에만"). LISTEN 전용 DB 연결이 워커마다 1개 든다. 알림은 유실될 수 있다(아래 "끊김과 재연결"에서 다룬다).

### (c) SSE(서버 → 브라우저 단방향)
웹소켓 대신 `text/event-stream`. 서버 쪽 구조는 (b)와 같다(async 경로 + LISTEN/NOTIFY).
- 장점: 일반 HTTP라 쿠키 인증과 nginx 설정이 단순하다. 브라우저 `EventSource`가 재연결을 알아서 한다. 우리 알림은 서버 → 화면 한 방향뿐이다.
- 단점: 사용자가 요구 사항을 "웹소켓"으로 말했다. HTTP/1.1에서는 브라우저가 출처당 연결을 6개로 제한한다(탭을 여러 개 열면 막힌다). 나중에 양방향이 필요해지면 다시 바꾼다.

### 비교
| | (a) 전면 async | (b) 웹소켓만 async | (c) SSE |
|---|---|---|---|
| 고칠 기존 코드 | 전부 | 서비스에 알림 발행 몇 줄 | (b)와 같음 |
| 매장 격리 회귀 위험 | 큼 | 작음(기존 경로 안 건드림) | 작음 |
| 새 인프라 | 없음 | 없음 | 없음 |
| 긴 연결 150~1,650개 | 됨 | 됨 | 됨(HTTP/2 필요) |
| 요구 사항 "웹소켓"과 일치 | 예 | 예 | 아니오 |
| 비용 | 대 | 소~중 | 소~중 |

## 권고: (b)
이유는 하나다. 풀어야 할 문제는 "긴 연결"뿐이고, (b)가 그것만 푼다. (a)는 같은 문제를 풀려고 격리 코드 전체를 다시 증명하게 만든다. (c)는 기술적으로 충분하지만 확정된 요구 사항과 다르다. 사용자가 SSE도 괜찮다고 하면 (c)가 더 단순하다. 서버 구조가 같아서 나중에 서로 바꾸는 비용은 작다.

ADR-014와의 관계: "전면 전환은 하지 않는다"는 유지한다. "긴 연결은 async 경로로 따로 둔다"를 더한다.

## (b)의 설계

### 흐름
1. 손님이 요청한다(동기 라우트, 지금과 같다).
2. 서비스가 같은 트랜잭션 안에서 `SELECT pg_notify('store_events', :payload)`를 실행한다. payload는 `{"store_id": "...", "type": "visit.updated", "id": "..."}`처럼 **종류와 ID만** 담는다. 내용은 담지 않는다.
3. commit되면 PostgreSQL이 듣고 있는 모든 연결에 전달한다.
4. 워커마다 있는 수신기(async 작업 1개, 전용 연결 1개)가 받아서, 그 워커에 붙은 웹소켓 중 **같은 매장** 것에만 보낸다.
5. 브라우저는 알림을 받으면 해당 조회를 무효화하고 일반 API로 다시 읽는다.

핵심: **웹소켓으로는 데이터를 보내지 않는다. "바뀌었다"는 신호만 보낸다.** 데이터는 항상 기존 API(RLS가 걸린 경로)로 읽는다. 그래서 웹소켓 쪽 권한 실수가 데이터 유출로 이어지는 범위가 "어떤 매장에 변화가 있었다"는 사실로 줄어든다.

### 웹소켓 인증과 매장 범위 검사 (RLS 밖)
웹소켓 연결은 DB 세션을 들고 있지 않다. RLS가 지켜 주지 않는다. 그래서 **연결할 때 앱 코드가 직접 검사한다.**

- 경로: `GET /api/v1/stores/{store_id}/events` (웹소켓 업그레이드).
- 인증: 브라우저는 웹소켓 요청에 쿠키를 같이 보낸다. 점주 세션 쿠키([[인증_설계_20261110]] 3장)를 읽어 세션을 확인한다. 토큰을 URL에 넣지 않는다(로그에 남는다).
- 소속 검사: 세션의 사용자가 `store_members`에 그 `store_id`로 있는지 확인한다. 일반 요청과 **같은 함수**를 쓴다(인증 설계 5.2). 없으면 업그레이드 전에 닫는다(코드 1008).
- 출처 검사: 웹소켓에는 CORS가 적용되지 않는다. `Origin` 헤더가 우리 출처인지 직접 확인한다. 안 하면 다른 사이트가 사용자의 쿠키로 연결할 수 있다.
- 보낼 때 한 번 더: 수신기가 알림의 `store_id`와 연결에 묶인 `store_id`가 같은지 비교한 뒤에만 보낸다. 연결을 `dict[store_id, set[연결]]`로 들고 있으므로 다른 매장 연결은 조회 자체가 안 된다.
- 세션 만료·권한 회수: 연결은 한 번 검사하면 계속 열려 있다. 그래서 일정 주기(가정: 5분)로 세션과 소속을 다시 확인하고, 아니면 닫는다. 로그아웃·멤버 삭제 때 `store_events`에 `session.revoked`를 보내 즉시 닫는 것은 뒤로 미룰 수 있다.
- **전제: 인증(⑦)이 먼저다.** 지금은 세션이 없어서 위 검사를 할 수 없다. 인증 없이 웹소켓을 열면 주소를 아는 누구나 모든 매장의 변화를 듣는다. 손님 폰을 연결하는 경우는 손님 기기 쿠키 + 그 기기가 앉아 있는 방문의 매장으로 검사한다(범위는 결정 필요).
- 테스트(구현 때): 다른 매장 세션으로 연결 → 거절. 세션 없음 → 거절. 틀린 `Origin` → 거절. A 매장 알림이 B 매장 연결에 가지 않음. `tests/isolation`에 둔다.

### 워커가 여러 개일 때
- 웹소켓 연결은 워커 하나의 메모리에 있다. 알림을 만든 요청은 다른 워커에서 처리됐을 수 있다. 메모리 안에서만 전달하면 일부 화면에 안 간다.
- LISTEN/NOTIFY가 이를 푼다. 모든 워커가 같은 채널을 듣고, 각자 자기에게 붙은 연결에만 보낸다. 워커 수에 상관없이 동작하고 워커 사이 통신이 필요 없다.
- 비용: 워커당 DB 연결 1개가 풀 밖에서 상시 열려 있다. 워커 4개면 4개다.
- 한계: 채널이 하나(`store_events`)라 모든 워커가 모든 매장의 알림을 받고 버린다. 초당 25건(가정)에서는 문제없다. 수백 건이 되면 Redis pub/sub 등으로 옮기는 것을 그때 정한다.
- 지금은 워커 1개다. 그래도 처음부터 이 구조로 만든다. 워커를 늘릴 때 고칠 것이 없다.
- 수신기는 FastAPI `lifespan`에서 시작하고 종료 때 정리한다.

### 끊김과 재연결
- **알림은 유실될 수 있다고 보고 설계한다.** LISTEN/NOTIFY는 그 순간 듣고 있는 연결에만 전달한다. 저장하지 않는다. 수신기 연결이 끊긴 사이의 알림, 브라우저가 끊긴 사이의 알림은 사라진다.
- 그래서 규칙: **(재)연결에 성공하면 브라우저가 그 매장의 실시간 조회를 전부 무효화한다.** 놓친 것이 있든 없든 서버 상태로 다시 맞춘다. 알림 번호를 매겨 빠진 것을 다시 보내는 방식은 만들지 않는다.
- 브라우저: 끊기면 1초 → 2초 → 4초 … 최대 30초 간격으로 다시 연결한다. 간격에 무작위 값을 섞는다(서버 재시작 때 한꺼번에 몰리지 않게). 탭이 다시 보일 때(`visibilitychange`)도 연결을 확인한다.
- 살아 있는지 확인: 서버가 30초마다 ping을 보낸다. 응답이 없으면 닫는다. 프록시가 조용한 연결을 끊는 것도 막는다.
- 수신기 쪽: LISTEN 연결이 끊기면 다시 연결하고 다시 LISTEN한다. 그 뒤 붙어 있는 모든 웹소켓에 `resync` 신호를 보낸다. 브라우저는 `resync`를 재연결과 똑같이 처리한다(전부 무효화).
- 안전망: 실시간 화면의 조회에 긴 주기 `refetchInterval`(가정: 60초)을 둔다. 웹소켓이 조용히 죽어도 1분 안에 화면이 맞는다.
- 배포: 백엔드를 재시작하면 모든 연결이 끊기고 위 절차로 다시 붙는다. 따로 할 일은 없다.

### 프론트 갱신
- 훅 하나: `useStoreEvents(storeId)`. 연결·재연결·정리를 맡는다. 매장 화면의 최상위에서 한 번만 쓴다.
- 알림을 받으면 종류에 맞는 조회만 무효화한다. 예: `visit.updated` → `queryClient.invalidateQueries({ queryKey: ["stores", storeId, "tables"] })`. 화면은 기존 조회 코드와 zod 검증을 그대로 쓴다.
- 종류 → 조회 키 대응은 표 하나(객체 하나)에 둔다. 모르는 종류는 무시한다(서버가 먼저 배포돼도 안 깨진다).
- 알림 내용으로 캐시를 직접 고치지(`setQueryData`) 않는다. 웹소켓에 데이터를 싣지 않는다는 원칙과 같다.
- 알림이 몰릴 때: 같은 키의 무효화를 짧게(가정: 300ms) 묶는다. TanStack Query가 진행 중인 같은 조회를 합쳐 주지만, 연속 알림마다 새 요청이 나가는 것은 막아야 한다.
- 자기가 한 변경도 알림으로 돌아온다. 무효화가 한 번 더 일어날 뿐이라 따로 걸러내지 않는다.
- 전제: 조회 키가 `["stores", storeId, ...]` 형태로 정리돼 있어야 한다. 지금 키 모양은 이번에 확인하지 않았다.

### 배포에서 바꿀 것 (구현 때)
- `frontend/nginx.conf`: 웹소켓 경로에 `proxy_http_version 1.1`, `Upgrade`·`Connection` 헤더, 긴 `proxy_read_timeout`.
- 앞단(Cloudflare 등)의 웹소켓 허용과 유휴 제한 시간 확인.
- `food_app` 역할이 `pg_notify`를 실행하고 `LISTEN`할 수 있는지 확인(둘 다 별도 권한이 필요 없는 것으로 알지만 확인하지 않았다).
- `uvicorn[standard]`에 웹소켓 구현이 들어 있다(`backend/pyproject.toml`). 새 의존성은 없을 것으로 본다.

## 결정이 필요한 것
1. (b)로 갈지, SSE (c)도 받아들일 수 있는지.
2. 손님 폰도 실시간 연결을 여는지, 매장 화면만인지. 연결 수가 150과 1,650으로 갈린다(가정).
3. 실시간으로 반영할 사건의 목록(착석, 슬롯 변경, 호출, 주문 …). 지금 코드에 있는 것은 방문·슬롯뿐이다.
4. 알림 지연 허용치(가정 2초)와 안전망 주기(가정 60초).
5. 구현 순서: 인증(⑦) 뒤에 한다는 전제를 받아들이는지.

## 확인하지 못한 것
- 아무것도 구현하거나 실행하지 않았다. 지연 시간, 연결 수 한계, 메모리 사용량은 전부 `미검증`.
- PostgreSQL NOTIFY의 payload 크기 제한(기본 8000바이트 미만으로 기억)과 대기열 한도를 이번에 공식 문서로 확인하지 않았다. 설계는 payload 200바이트 이하라 영향이 작다.
- psycopg 3의 async 알림 수신 API를 이 저장소의 버전에서 실제로 돌려 보지 않았다.
