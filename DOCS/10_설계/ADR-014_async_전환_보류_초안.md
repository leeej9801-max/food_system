# ADR-014 (초안) — async 전환은 출시 뒤 부하 측정을 보고 정한다

## 상태
초안. 결정: **이번 범위에서 전환하지 않는다 (U-38).** 이 문서는 전환 비용과 위험만 기록한다.

## 배경
- lee-start 템플릿은 async FastAPI + `AsyncSession`이다. food는 전부 동기다.
- 지금: 라우트 53개 모두 `def`, 동기 `Session`, `psycopg` 동기 드라이버(`backend/app/db/session.py`). 서비스 코드 약 3,700줄. 앱 코드 안의 외부 HTTP 호출 없음(공휴일 수집은 스크립트).
- 동기 라우트는 FastAPI가 스레드풀에서 돌린다(기본 40). 이벤트 루프를 막지 않는다. 그래서 ASYNC-001(async 안의 블로킹 호출)은 지금 해당 사항이 없다.
- 운영: uvicorn 워커 1개, DB 연결 풀은 SQLAlchemy 기본(5 + 넘침 10).

## 지금 구조의 한계 (계산, 측정 아님)
- 동시에 DB를 쓰는 요청은 연결 풀 크기(15)에서 막힌다. 스레드풀(40)보다 풀이 먼저 찬다.
- 요청 하나가 DB에서 50ms를 쓴다고 가정하면 워커 하나가 초당 약 300건까지 처리한다는 계산이 나온다. **가정이고 측정하지 않았다.**
- 1~2인 음식점 대상 서비스에서 이 한계에 닿는 시점은 `미확인`이다.

## 전환하면 바뀌는 것
| 대상 | 작업 | 크기 |
|---|---|---|
| 드라이버·엔진 | `create_async_engine`, `async_sessionmaker`. `psycopg`는 async를 지원하므로 드라이버 교체는 없다 | 작음 |
| 서비스 11개 | 모든 DB 호출에 `await`, 함수 전부 `async def`. 지연 로딩(`visit.slots` 같은 관계 접근)을 전부 명시적 로딩으로 바꿔야 한다 | **큼** |
| 라우트 53개 + 의존성 | `async def`, `AsyncSession` | 중간 |
| 매장 격리 (ADR-013) | `backend/app/db/tenancy.py`가 `after_begin` 이벤트로 `set_config`를 다시 건다. 이 이벤트는 동기 세션 기준이다. async에서 같은 보장이 되는지 다시 설계하고 격리 테스트 22개로 증명해야 한다 | **위험** |
| 테스트 | `TestClient` → `httpx.AsyncClient`, `pytest-asyncio`, fixture 전부 | 큼 |
| 스크립트·Alembic | async 템플릿 또는 동기 엔진 병행 | 작음 |
| SQLite 테스트 | `aiosqlite`가 필요하거나, SEC-001·TEST-001에 맞춰 테스트를 PostgreSQL로 통일 | 중간 |

## 위험
1. **매장 격리 회귀.** 연결이 풀로 돌아간 뒤 다른 요청이 이전 매장 범위를 물려받거나, 범위가 빠진 트랜잭션이 생기면 데이터 누출이다. 지금은 `SET LOCAL` 방식(트랜잭션 단위)이라 구조상 안전하지만, async에서 이벤트 훅이 같은 시점에 도는지는 `미검증`이다.
2. **지연 로딩 오류.** async에서 관계를 암묵적으로 읽으면 `MissingGreenlet`이 난다. 실행해 봐야 드러나므로 테스트가 닿지 않는 경로에서 운영 중 터질 수 있다.
3. **조용한 블로킹.** `async def` 안에 동기 호출이 하나 남으면 워커 전체가 멈춘다. 지금 구조에서는 생길 수 없는 종류의 장애다. ruff `ASYNC` 규칙이 일부만 잡는다.
4. **일정.** 11월 말 점주 대시보드와 겹친다. 인증·UUID·오류 형식 변경과 동시에 하면 회귀 원인을 가릴 수 없다.

## 얻는 것
- 느린 I/O(외부 API, SSE, 긴 연결)가 많을 때 같은 자원으로 더 많은 동시 연결.
- 템플릿과 같은 구조.
- 지금 food에는 느린 외부 I/O가 없다. 얻는 것이 생기는 시점은 **카카오 토큰 교환(로그인 때만), POS Open API 연동, TV 화면 SSE**가 들어올 때다.

## 전환 없이 먼저 할 수 있는 것
- uvicorn 워커 수 늘리기, 연결 풀 크기 조정, `pool_pre_ping`.
- 느린 외부 호출이 있는 라우트만 `async def` + `httpx.AsyncClient`로 쓰고 DB는 `run_in_threadpool`로 감싼다(라우트 단위 혼용).
- SSE가 필요해지면 그 경로만 별도 async 라우터로 둔다.

## 다시 결정할 조건
아래 중 하나가 생기면 이 ADR을 다시 연다.
- 출시 뒤 부하 측정에서 스레드풀 또는 연결 풀 포화가 관측된다.
- SSE·웹소켓처럼 오래 열려 있는 연결이 요구사항으로 확정된다(매장 TV, U-33).
- POS 실시간 연동처럼 요청마다 외부 호출이 붙는다.

## 측정해야 할 것 (출시 뒤)
p50·p95 응답 시간, 동시 요청 수, 연결 풀 대기 시간, 스레드풀 대기. 지금은 수집 수단이 없다(감사 §7 로그 항목).

## 미확인
- 실제 처리 용량과 병목 위치.
- async `Session`에서 `after_begin` 방식 격리가 그대로 성립하는지.
- 전환 작업량의 실제 크기(위 표는 코드 구조에서 추정한 것이다).
