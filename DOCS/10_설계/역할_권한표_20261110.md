# 역할·권한 표 — 2026-11-10

상태: **사용자 승인 대기.** `?` 칸과 §4의 결정 항목은 임의로 정하지 않았다.

## 1. 근거
- 엔드포인트 목록은 `backend/tests/api/snapshots/openapi.json`(브랜치 `08798b7`)에서 뽑았다: **53개**. FastAPI가 자동으로 만드는 문서 경로 4개를 더해 **57개**다.
- "지금" 열은 전부 같다: **누구나**(로그인 없음, U-14). 그래서 열을 따로 두지 않았다.

## 2. 역할
| 역할 | 누구 | 인증 | 범위 |
|---|---|---|---|
| 점주 | 매장 주인 | 카카오 로그인 (U-39) | 자기와 연결된 매장만 |
| 직원 | 매장 직원 | 점주가 승인한 기기 (U-39) | 소속 매장만. 무엇을 할 수 있는지는 D-1 |
| 손님 | 테이블에 앉은 사람 | 없음. QR 토큰 + 익명 기기 쿠키 (P-15) | 그 QR의 테이블 하나 |

| 공개 | 누구나 | 없음 | — |

## 4. 결정 필요
| ID | 질문 | 선택지 | 제안 |
|---|---|---|---|
| D-1 | 직원은 출퇴근만 하는가, 홀 운영(착석·주문·재고 입력)도 하는가 | (a) 출퇴근만 (b) 출퇴근 + 홀 화면(#42, 47~50) (c) (b) + 주문·입고·실사 입력(#22~24, 30~34, 36, 38) | **(a)로 출시.** 요구사항이 "출퇴근 인증이 목적"이다. `?` 칸은 전부 `X`로 시작하고, 필요해지면 (b)를 연다. 권한이 좁을수록 기기 토큰이 탈취됐을 때 피해가 작다 |
| D-2 | 매장은 누가 만드는가 | (a) 운영자만 만들고 점주에게 초대를 준다 (b) 점주가 로그인 후 직접 만든다 | **(a).** "우리가 만들어서 제공"과 맞고, 아무 카카오 계정이나 매장을 만드는 일을 막는다 (S-5, O-6) |
| D-3 | 점주와 매장의 관계 | (a) 점주 1 : 매장 1 (b) 점주 1 : 매장 여럿 (c) 매장 1 : 점주 여럿 | **표 구조는 다대다(`store_members`)로 두고, 화면은 (a)로 시작.** 나중에 바꾸면 마이그레이션이 필요하다 |
| D-4 | `seed-western-demo` | (a) 제거 (b) 운영자 전용 (c) 운영 환경에서만 끔 | **(c).** 로컬·데모에서는 쓰인다. 운영에서는 라우트를 등록하지 않는다 |
| D-5 | 공휴일 수동 추가 | (a) 운영자 전용 (b) 점주도 허용하되 매장별로 저장 | **(a).** 표가 전역이다. 매장별 휴무일은 다른 기능이다 |
| D-6 | 운영자 역할의 구현 | (a) 앱 안의 역할(카카오 로그인 + 운영자 표시) (b) 앱에는 없고 서버에서 스크립트로만 | **(b)로 출시.** 매장 생성·초대 발급·공휴일 적재를 `backend/scripts/`로 한다. 운영자용 HTTP 경로가 없으면 공격 면도 없다. 표의 운영자 `O`는 "스크립트로 가능"을 뜻한다. 이 경우 #7, #12는 HTTP에서 전부 `X`가 되고 라우트를 제거한다 |

## 5. 아직 없는 엔드포인트 (인증 설계에서 확정)
권한표에 반드시 들어가야 하지만 아직 코드가 없다. 경로는 인증 설계 문서에서 정한다.
- 점주 로그인 시작, 카카오 콜백, 로그아웃, 내 정보·내 매장 목록.
- 매장 초대 수락.
- 직원 기기 등록 요청, 점주의 승인·폐기, 등록 기기 목록.
- 출근·퇴근 기록, 기록 조회, 점주의 정정(이력 보존).
- 손님 등록(카카오): 이번 범위 아님(12월 초 이후).

## 6. 빠짐 방지 (⑦에서 구현)
- 모든 라우트는 역할 의존성 하나를 반드시 선언한다. 선언하지 않은 라우트는 기본 거부다.
- 테스트가 `app.routes`를 전부 돌면서 (1) 이 표에 있는지, (2) 로그인 없이 호출하면 `공개` 경로가 아닌 한 401인지 확인한다. 새 엔드포인트를 표 없이 추가하면 CI가 실패한다 (AC-7).
- 역할별 접근 거부, 다른 매장 거부, 만료 세션 거부, CSRF 거부 테스트를 같은 묶음에 넣는다 (AC-6).
