## 6. 제안 순서와 결정이 필요한 것

**동작 변경 없이 바로 가능 (3단계 요청 순서 그대로)**
1. CI 추가(현재 통과하는 검사만 먼저: `ruff check`, pytest + 격리, 프론트 typecheck·test·build).
2. pyright 설정 + 14건 수정.
3. ruff 규칙 확대, `.gitattributes`, 서식 일괄 적용(별도 커밋).
4. `.gitignore` 정리, `conftest.py` 통합.
5. REACT-008 key 수정, REACT-003 Effect 정리.

**사용자 결정 필요 (동작 변경 또는 큰 작업)**
- SEC-001: SQLite 기본 DSN 제거 여부(P-07 종료).
- API-004: 오류 형식을 RFC 9457로 바꿀지. 백엔드·프론트 동시 변경이다.
- DB-001: UUID v7 전환. 운영 데이터가 있어 권하지 않는다. "예외로 둔다"는 결정 기록을 제안한다.

- API-003: 인증·권한. 이번 범위 밖으로 두고 별도 결정으로 남길 것을 제안한다.
- TS-010: 런타임 검증 방식(zod 추가 또는 손으로 쓴 가드). 의존성 추가 여부가 걸린다.
- async 전환: 요청대로 제외. 별도 결정.

| 배포 자동화 | 수동(`docker compose --env-file .env.deploy up -d --build --wait`, PowerShell). CI는 이미지를 빌드만 하고 올리지 않는다. 이미지 태그는 `food-backend:local`, `food-web:local` 고정 | CD 없음. 이미지에 버전 태그가 없어 "어느 커밋이 떠 있는지" 알 수 없다 | 중간 | 결정 필요(D-R4) |
| 롤백 | 문서에 0006 전환 때의 되돌리기 한 줄만 있다. 일반 절차 없음. 태그가 `local` 하나라 다시 빌드하면 이전 이미지가 덮인다 | 커밋 SHA 태그, 직전 이미지 보존, 롤백 명령 문서 | 높음 | 배포 자동화와 같이 |
| 헬스체크 | `GET /health`가 있다. compose에 db·backend·web healthcheck와 `depends_on` 조건이 있다. nginx는 `/food/health`를 백엔드로 넘긴다 | `/health`가 DB에 닿는지 확인하지 않는다(`backend/app/main.py:27`, 고정 값만 돌려준다). `pos_mode`를 밖에 보여 준다. 준비 상태(readiness)와 생존(liveness) 구분 없음 | 중간 | ⑥ |
| 외부 감시 | 없음(`미확인`: Cloudflare 쪽) | 밖에서 주기적으로 `/food/health`를 찌르는 감시 | 중간 | 오류 알림과 같이 |
| 마이그레이션 절차 | `migrate` 서비스가 기동 때마다 `alembic upgrade head` + `ensure_runtime_role`을 소유자 계정으로 돌리고, 성공해야 backend가 뜬다. CI가 `alembic upgrade head`와 `alembic check`를 돈다(② 조치) | 적용 전 자동 백업 없음. 되돌릴 수 없는 마이그레이션 표시 규칙 없음. 새 코드와 옛 스키마가 잠깐 같이 도는 구간의 호환 규칙 없음. downgrade는 CI에서 `미검증` | 높음 | ⑤(UUID 전환) 전에 절차 문서 |
| 실행 환경 | Windows PC + Docker Desktop + Cloudflare 터널(`deploy/README.md`). PC 절전·재부팅·회선에 의존. uvicorn 워커 1개. DB 연결 풀은 SQLAlchemy 기본(5 + 넘침 10), `pool_pre_ping` 없음 | 단일 장애점. 처리 용량 `미검증`. 출시용 호스팅 결정 필요 | **높음** | 결정 필요(D-R5) |
| 컨테이너 | backend는 uid 10001 비루트(`backend/Dockerfile`). 내부 네트워크 분리. web만 `127.0.0.1`에 포트 공개 | 읽기 전용 루트, 자원 제한 없음 | 낮음 | 뒤로 |
| CI 보안 검사 | 없음 | 의존성 취약점 검사, 시크릿 유출 검사, 오탐 목록(U-37 지시) | 중간 | ④ 앞. 아래 제안 |

### 7.1 결정 필요
| ID | 질문 | 제안 |
|---|---|---|
| D-R1 | 오류 알림 도구 | 제안 없음(비용·계정이 걸린다). 선택지: Sentry(호스팅), 자체 호스팅, 로그 + 외부 감시만 |
| D-R2 | 백업 보관 장소와 주기 | 매일 1회 + 마이그레이션 직전. 장소는 사용자 결정(다른 기기 또는 객체 저장소). 손님 개인정보가 들어가면 암호화가 필요하다 |
| D-R3 | 호출 제한 위치 | nginx `limit_req`(구성 요소 추가 없음)를 기본으로, Cloudflare 규칙은 확인 뒤 추가 |
| D-R4 | 배포 방식 | 11월은 수동 유지 + 커밋 SHA 태그·롤백 문서만. CD는 호스팅(D-R5)이 정해진 뒤 |
| D-R5 | 출시용 호스팅 | 제안 없음. 지금 구성(개인 PC)은 실사용 서비스의 가용성을 보장하지 못한다. 인증 설계 D-A7(호스트 분리)과 함께 정해야 한다 |

### 7.2 CI 보안 검사 위치 제안
- 의존성: 백엔드 `pip-audit`(`requirements.deploy.txt` 대상), 프론트 `npm audit --omit=dev --audit-level=high`. 
- 시크릿: `gitleaks`로 전체 이력 검사.
- 오탐·예외는 저장소의 파일 하나(예: `.github/security-allowlist.md` + 각 도구의 설정 파일)로 관리하고 항목마다 이유와 재검토 날짜를 적는다.
- 넣는 시점: ④ 앞의 독립 커밋. 첫 실행에서 무엇이 걸릴지는 `미검증`이다. 걸리면 고치기 전에 목록으로 보고한다.

### 7.3 미확인
라이브 응답 헤더·TLS·HSTS, Cloudflare의 WAF·호출 제한·캐시 설정, 운영 PC의 접근 통제·디스크 암호화, 로그 실제 보관 기간과 크기, 백업이 실제로 있는지와 마지막 날짜, 복구 가능 여부, 처리 용량.
