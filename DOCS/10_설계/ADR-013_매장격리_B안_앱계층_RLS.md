# ADR-013 — 매장 간 데이터 격리: B안 (앱 계층 강제 + PostgreSQL RLS)

> 상태: **코드·마이그레이션 적용 완료 ([[WO-20261104-002_매장격리_운영스키마_적용]], Alembic 0006), 라이브 데모 배포 대기.**

## 1. 배경

- 영역 B(손님 캐릭터) 추가로 캐릭터·손님 ID를 **전역 ID**로 두고(U-21), 데이터 모델은 처음부터 다중 매장으로 간다.
- 매장 A가 매장 B의 방문·매출·고객 데이터를 보면 안 된다. 기존 ADR-010(전 엔티티 `store_id`)은 앱 코드가 필터를 빠뜨리면 막을 장치가 없다.
- 기준(사용자): 성능, 보안 정도, 비용. 테스트로 확인할 것.

## 2. 비교

| 방식 | 보안 | 성능 | 비용·복잡도 | 전역 캐릭터와 궁합 |
|---|---|---|---|---|
| A. 앱 계층 필터만 (공용 스키마 + `store_id`) | 중: 코드 실수 하나면 샘 | 최상 | 최저 | 좋음 |
| **B. A + PostgreSQL RLS** | **상: 앱이 빠뜨려도 DB가 막음** | **A와 측정 차이 없음** (§4) | 낮음 | 좋음 |
| C. 매장별 스키마 | 상 | 좋음 | 중~상: 마이그레이션 × 매장 수 | 나쁨: 매장 간 조회 복잡 |
| D. 매장별 DB | 최상 | 좋음 | 최상: 운영비 | 나쁨: 매장 간 조인 불가 |

## 3. 결정

**B안.** 구성 규칙:

1. **두 영역 분리.** 전역(플랫폼) 테이블(손님 프로필, 캐릭터, 공통 아이템, 플랫폼 동의)은 `store_id` 없음, RLS 없음. 매장 테이블은 모두 `store_id`를 **직접** 가진다(부모를 거치는 조인 정책은 쓰지 않음).
2. **RLS 정책은 fail-closed.** `store_id = nullif(current_setting('app.current_store_id', true), '')::uuid`. 범위가 없으면 0행. `USING` + `WITH CHECK` 둘 다 건다.
3. **`ENABLE` + `FORCE ROW LEVEL SECURITY`.** 앱 런타임 DB 계정은 테이블 소유자·슈퍼유저가 아니고 `BYPASSRLS`가 없다. 마이그레이션은 별도 소유자 계정으로 실행한다.
4. **범위는 트랜잭션 단위.** `SELECT set_config('app.current_store_id', :id, true)`(= `SET LOCAL`). 커넥션 풀에서 다음 요청으로 새지 않는다.
5. **요청 컨텍스트 하나로.** `app/db/tenancy.py`의 `RequestContext(store_id, actor)`를 서비스·리포지토리가 받고, `apply_store_scope`가 권한 검사(`authorize`) 후 범위를 건다. 베타(P-05, U-14)는 `authorize`가 모두 허용하고 actor는 고정값이다. 인증 도입 시 `authorize`와 컨텍스트 생성부만 바꾼다.
6. **손님 API는 클라이언트의 `store_id`를 믿지 않는다.** QR 토큰 → 서버가 테이블·매장을 찾아 컨텍스트를 만든다.
7. **앱 계층 필터도 유지한다** (WHERE `store_id`). RLS는 안전망이고, 앱 필터는 인덱스를 확실히 타게 한다.

## 4. 검증 결과 (스파이크, 2026-11-04)

- 격리 테스트 8건 통과: [[TEST-20261104-001_매장격리_RLS_스파이크_및_손님영역_설계]]. RLS를 끈 변형에서는 7건이 실패해 테스트가 실제로 격리를 잡는 것도 확인했다.
- 성능: 100만 행(50개 매장 × 2만), 한 매장 30일 시간대별 집계, 30회 중앙값. 로컬 Docker 2회 실행.

| 경우 | 1회차 | 2회차 |
|---|---|---|
| A안 (RLS 없음 + 앱 필터) | 39.09 ms | 36.35 ms |
| B안 (RLS + 앱 필터) | 39.05 ms | 36.59 ms |
| RLS만 (앱 필터 누락) | 42.35 ms | 35.51 ms |

측정 오차 안에서 차이가 없다. 운영 환경 성능을 보장하는 수치는 아니다.

## 5. 결과와 남은 일

- **SQLite로는 검증 불가.** 기존 자동 테스트(P-07)는 SQLite로 두고, 격리 테스트는 PostgreSQL에서만 돈다(`RLS_TEST_DATABASE_URL` 없으면 skip).
- **적용 결과 ([[IR-20261104-002_매장격리_운영스키마_적용]]):** 아래 항목 처리됨. 운영 ID는 `String(36)` 그대로 두고 정책을 text 비교로 적용.
- **(당시) 적용 전 정리할 것:**
  - `recipe_items`처럼 `store_id`가 없는 자식 테이블에 `store_id` 추가.
  - 지금 운영 스키마의 ID는 `String(36)`이다. 스파이크는 `uuid` 컬럼으로 검증했으므로, 적용 시 정책을 text 비교로 바꾸거나 컬럼을 `uuid`로 이행한다.
  - 앱 런타임 DB 계정과 마이그레이션 소유자 계정 분리 (지금 `db/docker-compose.yml`은 계정 1개).
  - 서비스·라우트가 `RequestContext`를 받도록 점진 이행, 요청마다 `apply_store_scope` 호출하는 DB 의존성.
  - 테스트 컨테이너의 소유자는 슈퍼유저라 "비슈퍼유저 소유자 + FORCE" 경우는 이번에 확인하지 못함.
