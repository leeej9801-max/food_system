## 1. 기술스택

### 1.1 FastAPI 동기 + SQLAlchemy 동기 세션
- **현재 선택**: 모든 라우트가 `def`이고 동기 `Session`을 쓴다. uvicorn 프로세스는 1개다.
- **판정**: **적합**
- **근거**
  - [확인] `backend/app/db/session.py:12`는 동기 `create_engine`이고 풀 설정은 기본값이다. `pool_pre_ping`은 없다.
  - [확인] `compose.yaml:51`의 uvicorn 실행에 `--workers`가 없다.
  - [확인] `backend/pyproject.toml`의 운영 의존성에 HTTP 클라이언트가 없다. 앱 코드가 요청 중에 외부 서버를 부르지 않는다.
  - [문서] ADR-014는 라우트 53개, 연결 풀 한도 15, 스레드풀 40으로 적고 있다. 처리 용량 수치는 가정이고 측정값이 아니라고 문서가 스스로 밝힌다.
  - [확인] 매장 격리가 동기 세션의 `after_begin` 이벤트에 걸려 있다(`backend/app/db/tenancy.py:55-60`). async로 바꾸면 이 보장을 다시 증명해야 한다.
- **대안과 장단점**
  - 전면 async: 긴 연결(SSE, 웹소켓)과 느린 외부 호출이 많을 때 유리하다. 지금은 그런 경로가 없다. 서비스 11개와 테스트 전부를 고쳐야 하고, 매장 격리 회귀 위험이 생긴다.
  - 경로 단위 혼용: 매장 TV용 SSE가 확정되면 그 라우터만 async로 둔다. 나머지는 그대로 둔다.
  - 워커 수와 풀 크기 조정: 설정 두 줄이다. 부하가 보이면 이것이 먼저다.
- **전환 비용**: 전면 async는 **대**. 워커·풀 조정은 **소**.
- **시기**: 전면 async는 하지 않는다. `pool_pre_ping=True` 한 줄은 지금 넣을 만하다(DB 재시작 뒤 죽은 연결로 첫 요청이 실패하는 일을 막는다). 나머지는 출시 후 측정을 보고 정한다.
- **주의**: 카카오 토큰 교환은 동기 라우트에서 동기 HTTP 호출로 해도 된다. 로그인 때만 일어나고 스레드풀에서 돈다. 다만 **타임아웃을 반드시 건다**. 카카오가 느려지면 스레드가 묶인다.

### 1.2 PostgreSQL 17 + Alembic
- **판정**: **적합**
- **근거**: [확인] `compose.yaml`의 `postgres:17-alpine`. 마이그레이션 8개가 순서대로 이어지고 모두 `downgrade`가 있다(`backend/alembic/versions/0001`~`0008`). CI가 `alembic upgrade head`와 `alembic check`를 PostgreSQL에서 돌린다(`.github/workflows/ci.yml`).

- **시기**: 엔진은 유지한다.

### 1.3 React 19 + Vite SPA (Next.js 대비)

  - [확인] `frontend/vite.config.ts`에 청크 분리 설정이 없고, 코드에 `lazy(`나 `Suspense`가 없다. 모든 화면이 한 번들로 나간다.

- **시기**: Next.js는 하지 않는다. `lazy` 분리는 손님 화면을 만들 때 같이 한다.

### 1.4 zod 응답 검증 + 손으로 쓴 타입
- **판정**: **적합, 보완 여지 있음**

- **시기**: 출시 후. 인증으로 응답 형식이 바뀌는 지금은 손대지 않는 편이 낫다.

## 3. DB

### 3.1 매장 격리: RLS 한 가지 방식
- **판정**: **적합. 스키마 분리나 DB 분리로 바꾸지 않는다.**
- **근거**
  - [확인] 매장 테이블 15개에 `ENABLE` + `FORCE ROW LEVEL SECURITY`와 `store_isolation` 정책이 걸려 있다(`backend/alembic/versions/0006_store_isolation_rls.py:22-38`). 0007이 `table_qr_tokens`, `session_slots`에 같은 정책을 건다(`0007_guest_sessions_slots.py:141-148`).
  - [확인] 범위가 없으면 0행이 나오는 fail-closed 구조다(`0006:41-45`). 범위는 트랜잭션 단위로 건다(`backend/app/db/tenancy.py:32-35`).
  - [확인] 런타임 역할은 `NOSUPERUSER NOBYPASSRLS`다(`backend/scripts/ensure_runtime_role.py`).
  - [확인] 격리 테스트가 PostgreSQL에서 돌고(`backend/tests/isolation/` 22개), CI가 skip을 금지한다(`.github/workflows/ci.yml:55-59`).
  - [문서] ADR-013의 측정에서 RLS 유무의 차이가 오차 범위 안이었다(100만 행, 로컬 2회).
- **대안과 장단점**
  - 매장별 스키마: 격리가 눈에 보인다. 마이그레이션이 매장 수만큼 돌고, 손님 전역 계정이 여러 매장을 넘나드는 조회가 복잡해진다.
  - 매장별 DB: 격리가 가장 강하다. 운영비와 연결 풀이 매장 수만큼 늘고 매장 간 조인이 안 된다. 손님 캐릭터가 전역이라는 제품 방향과 맞지 않는다.
- **전환 비용**: 둘 다 **대**
- **시기**: 하지 않는다.

### 3.2 RLS의 실제 구멍: 범위를 누가 정하는가
- **판정**: **보완 (가장 급함)**
- **근거**
  - [확인] `bind_request_scope`가 URL의 `store_id`를 검사 없이 RLS 범위로 건다(`backend/app/db/session.py:16-20`). `authorize()`는 비어 있다(`backend/app/db/tenancy.py:24-25`).
  - [확인] `GET /stores`가 모든 매장을 돌려주고(`backend/app/api/v1/endpoints/stores.py:14-16`), `POST /stores`와 `POST /{store_id}/seed-western-demo`가 열려 있다(`:19-22`, `:39-43`).
  - [확인] 운영은 Cloudflare Access 없이 공개다(`deploy/README.md:68`, U-14).
  - 뜻: RLS는 "코드가 필터를 빠뜨리는 실수"는 막는다. "남의 매장 ID를 주소에 넣는 사람"은 막지 못한다. 지금은 주소를 아는 누구나 모든 매장 데이터를 읽고 쓸 수 있다.
- **대안**: `인증_설계_20261110.md` §5의 `owned_store` 의존성이 올바른 해법이다. 5장에서 다룬다.
- **임시 대안**: 인증이 들어가기 전까지 점주 경로(`/food/` 중 손님 경로 제외)에 Cloudflare Access를 건다. 설정만으로 되고 코드 변경이 없다. 무료 한도와 경로 단위 예외 설정은 이번에 확인하지 않았다 [미확인]. 현재 데이터가 전부 임시라는 전제라면 생략할 수 있다. **실제 매장 데이터가 들어가는 날이 기한이다.**

### 3.3 RLS 밖에 있는 테이블

- **근거**

  - [확인] "모든 매장 테이블에 정책이 있다"를 검사하는 테스트는 테스트 이름 목록에서 찾지 못했다. 새 테이블을 만들 때 정책을 빠뜨려도 CI가 잡지 못한다고 본다 [추정].

- **전환 비용**: **중** (인증 작업에 포함)
- **시기**: 인증과 같이.

### 3.4 `audit_events`

- **시기**: 인증과 같이.

### 3.5 인덱스와 조회 방식
- **판정**: **보완 (급하지 않음)**
- **근거**

- **시기**: 11월 말 점주 대시보드 작업 때. 대시보드가 이 조회를 더 자주 부르게 되기 때문이다.

### 3.6 ID: `String(36)` + UUID v4 → UUID v7
- **판정**: **보완. 한다면 지금이 가장 싸다.**
- **근거**
  - [확인] PK가 `String(36)`이고 `uuid.uuid4()` 문자열이다(`models/__init__.py:27-28`, `:34`). RLS 정책도 text 비교다.
  - 문자열 36바이트는 네이티브 `uuid` 16바이트보다 인덱스가 크다. v4는 무작위라 삽입 위치가 흩어진다. 매장 하나 규모에서는 체감되지 않는다 [추정].
  - 사용자가 "지금 데이터는 전부 임시"라고 확인했다. 데이터를 지키지 않아도 되면 타입 변경은 마이그레이션 재작성으로 끝난다. 실데이터가 들어온 뒤에는 모든 PK·FK 컬럼을 변환하는 무거운 작업이 된다.
  - [미확인] PostgreSQL 17에는 `uuidv7()` 내장 함수가 없고 18에 들어갔다고 기억한다. 파이썬 표준 라이브러리의 `uuid7`도 3.12에는 없다고 기억한다. 둘 다 이번에 공식 문서로 확인하지 않았다. 맞다면 앱에서 생성하는 작은 함수나 의존성이 필요하다.
- **대안**
  - 네이티브 `uuid` 타입 + v7(앱 생성): 표준에 맞고 인덱스가 작다.
  - 지금 그대로: 동작에 문제는 없다. 표준(DB-003)과의 차이가 남는다.
- **전환 비용**: 지금 **중**, 출시 후 **대**
- **시기**: 인증 테이블을 만들기 **전에** 한다. 새 테이블 6개가 옛 타입으로 생기면 바꿀 것이 늘어난다.

### 3.7 백업과 복구
- **판정**: **교체 검토 (지금 방식으로는 실데이터를 받으면 안 된다)**
- **근거**
  - [확인] 백업은 사람이 직접 `pg_dump -Fc` 후 `docker cp` 하는 절차뿐이다(`deploy/README.md:81-87`). 일정, 자동 실행, 다른 기기 보관, 복구 연습이 문서에 없다.
  - [확인] DB는 Windows PC의 Docker 볼륨 `pgdata` 하나에 있다(`compose.yaml`). 그 PC가 꺼지면 서비스가 멈춘다(`deploy/README.md:89`).
  - [확인] `backend/scripts/prepare_deployment.py`의 백업은 예전 SQLite 이행용이다. 지금 운영 DB와 관계없다.
  - 뜻: 디스크가 고장 나거나 볼륨을 실수로 지우면 **전부 사라진다**. 점주의 매출과 재고 기록이다.
- **대안과 장단점**
  - 예약 `pg_dump` + 외부 저장소 업로드: 하루 1회 덤프를 다른 곳(오브젝트 저장소 등)에 올린다. 하루치까지 잃을 수 있다. 가장 싸고 단순하다.
  - 관리형 PostgreSQL: 시점 복구가 된다. 월 비용이 생긴다. 금액은 이번에 조사하지 않았다 [미확인].
  - WAL 보관(pgBackRest 등): 분 단위 복구가 된다. 1인 운영에 설정과 감시 부담이 크다.
- **전환 비용**: 예약 덤프 **소**. 관리형 이전 **중**.
- **시기**: **실제 매장 데이터를 넣기 전에.** 복구 연습(덤프를 빈 DB에 올려 앱이 뜨는지 확인)을 한 번은 해야 백업이라고 부를 수 있다.

### 3.8 마이그레이션 운영
- **판정**: **적합, 보완 두 가지**
- **근거**
  - [확인] `migrate` 서비스가 소유자 계정으로 `alembic upgrade head`와 역할 스크립트를 돌리고(`compose.yaml:39`), 백엔드는 런타임 계정으로 붙는다. 계정 분리가 되어 있다.
  - [확인] 0007은 데이터가 조건에 안 맞으면 추측하지 않고 멈춘다(`0007:39-50`). 좋은 방식이다.
  - [확인] CI는 `upgrade head`만 돌린다. `downgrade`는 CI에서 돌지 않는다. 배포 문서의 롤백 절차(`alembic downgrade`)가 실제로 되는지 자동 검증이 없다.
  - [확인] 마이그레이션 직전 자동 백업이 없다.
- **대안**: CI에 `upgrade head → downgrade -1 → upgrade head` 한 줄. 배포 절차에 "마이그레이션 전 덤프" 한 줄.
- **전환 비용**: **소**
- **시기**: 지금.

### 3.9 테스트 DB가 운영과 다르다
- **판정**: **교체 검토 (인증 전에 해야 한다)**
- **근거**
  - [확인] API 테스트가 메모리 SQLite에서 `Base.metadata.create_all`로 돈다(`backend/tests/conftest.py`). 마이그레이션을 거치지 않는다. RLS, 역할 권한, `SECURITY DEFINER` 함수가 SQLite에는 없다.
  - [확인] `tenancy.py`가 PostgreSQL이 아니면 범위 설정을 건너뛴다. 즉 API 테스트 대부분은 격리 장치가 꺼진 상태로 돈다.
  - [확인] 위 2.2의 시각 비교 오류처럼 SQLite에서만 다르게 동작하는 지점이 이미 한 번 나왔다.
  - 인증 설계는 세션 조회 함수(`app_resolve_session`), 사용자 단위 정책, 역할 3개에 의존한다. 이것들은 SQLite에서 **시험할 수 없다**.
- **대안과 장단점**
  - 모든 API 테스트를 PostgreSQL로: 운영과 같은 조건이다. CI에는 PostgreSQL 서비스가 이미 떠 있다. 로컬에서 Docker가 필요하고 테스트가 조금 느려진다.
  - 두 벌 유지: 지금 방식이다. 인증이 들어가면 SQLite 쪽에서 가짜 경로가 계속 늘어난다.
- **전환 비용**: **중**
- **시기**: 인증 구현 **직전에**. 순서를 바꾸면 인증 테스트를 두 번 쓰게 된다.

## 4. 개발·배포 과정

### 4.1 CI
- **판정**: **적합**
- **근거**: [확인] `.github/workflows/ci.yml`에 ruff, pyright, 마이그레이션 검사, pytest(skip 금지), 배포용 의존성 잠금 대조, Docker 빌드, 프론트 타입검사·vitest·빌드가 있다. `permissions: contents: read`다.
- **보완**: 프론트 lint 없음(2.3). 액션이 태그(`@v4`)로 고정되어 있고 커밋 해시가 아니다. 1인 저장소에서 위험은 낮다. 해시 고정은 출시 후에 해도 된다.

### 4.2 보안 검사
- **판정**: **적합**
- **근거**: [확인] `pip-audit --require-hashes`, `npm audit --omit=dev --audit-level=high`, gitleaks 전체 이력 검사가 CI에 있다. 예외 목록이 비어 있다(`.github/security-allowlist.md`). 설정에 기본 비밀값이 없다(`backend/app/core/config.py:13`).
- **보완**
  - [확인] 응답 보안 헤더가 두 개뿐이다(`frontend/nginx.conf:9-10`). CSP, HSTS, `frame-ancestors`가 없다. 로그인 화면이 생기면 클릭재킹과 XSS 피해 범위에 직접 관계된다.
  - [확인] 호출 횟수 제한이 nginx에도 앱에도 없다. 손님 경로는 로그인 없이 쓰기가 되는 유일한 경로다. QR 토큰은 192비트라 추측은 현실적으로 불가능하다(`backend/app/services/guest.py:83-106`). 제한이 필요한 이유는 추측이 아니라 남용(슬롯 생성 반복, 부하)이다.
  - [확인] CORS가 운영에서도 `allow_credentials=True`, 메서드·헤더 `*`로 켜져 있다(`backend/app/main.py:17-23`). 운영은 같은 출처라 필요 없다. 인증 설계 §3.3이 제거를 이미 적었다.
- **전환 비용**: 헤더와 nginx `limit_req`는 **소**.
- **시기**: 인증과 같이.

### 4.3 배포와 호스트
- **판정**: **교체 검토**
- **근거**
  - [확인] 운영 호스트가 개인 Windows PC + Docker Desktop이다. LCI 앱의 Cloudflare 터널을 같이 쓴다(`deploy/README.md`, `compose.yaml`의 외부 네트워크 `lci-prod_edge`).
  - [확인] 이미지를 그 PC에서 직접 빌드한다(`food-backend:local`). 레지스트리가 없고 CI에 배포 단계가 없다.
  - [확인] 운영 환경 하나뿐이다. 스테이징이 없다.
  - [문서] D-A7에서 LCI와 호스트를 분리하기로 확정했다. 전환은 사용자가 한다.
  - 뜻: PC 절전, Windows 업데이트 재시작, 정전, 가정 회선이 모두 서비스 중단이다. 식당 영업시간(저녁, 주말)에 손님 QR이 안 열리면 제품의 핵심이 멈춘다.
- **대안과 장단점**
  - 소형 VPS 1대 + 같은 Compose: 설정을 거의 그대로 옮긴다. 24시간 켜져 있다. 월 비용이 생긴다(금액은 조사하지 않았다 [미확인]). 서버 보안 업데이트를 직접 해야 한다.

- **전환 비용**: VPS 이전 **중**
- **시기**: 호스트 분리(D-A7)를 할 때 같이 정하는 것이 가장 싸다. 도메인과 Cloudflare 설정을 어차피 그때 만진다. 실제 매장이 쓰기 전에는 끝나야 한다.
- **스테이징**: 별도 서버를 둘 필요는 없다. 같은 Compose를 다른 프로젝트 이름과 포트로 한 벌 더 띄워 마이그레이션을 먼저 돌려 보는 정도면 충분하다 [추정].

### 4.4 환경 분리와 비밀값

### 4.5 장애 감지와 로그
- **판정**: **보완 (출시 전 필수)**
- **근거**
  - [확인] 백엔드의 로그는 500 처리기의 `logger.error` 한 곳뿐이다(`backend/app/core/errors.py:131-134`). 요청 로그, 요청 ID, 느린 요청 기록이 없다.
  - [확인] `/health`가 DB를 보지 않고 고정 값을 돌려준다(`backend/app/main.py:28-34`). DB가 죽어도 정상으로 나온다.
  - [확인] 오류 수집(Sentry 등), 가동 감시, 알림이 의존성과 설정에 없다.
  - 뜻: 지금은 점주가 연락해야 장애를 안다. ADR-014가 "출시 후 측정을 보고 정한다"고 한 결정들도 측정 수단이 없어 판단할 수 없다.
- **대안(최소 세트)**
  1. 요청마다 한 줄 구조화 로그(경로, 상태, 걸린 시간, 요청 ID). 토큰이 들어간 경로는 가린다(인증 설계 §9).
  2. `/health`와 별도로 DB에 `SELECT 1`을 하는 준비 상태 경로.
  3. 외부 가동 감시(무료 서비스로 충분하다)가 그 경로를 1~5분마다 부르고 실패 시 알림.
  4. 500 오류 알림(오류 수집 서비스 무료 구간 또는 로그 기반).
- **전환 비용**: **소~중**
- **시기**: 1~3은 인증과 같이 또는 직후. 4는 출시 전.

### 4.6 문서 흐름(작업지시서 → 구현 → 리뷰)
- **판정**: **적합, 가볍게 할 여지 있음**
- **근거**
  - [확인] `DOCS/05_운영/개발_워크플로.md`가 WO → 구현 → IR → REV → 인수인계를 정한다. WO 17개, IR 16개, REV 16개, TEST 16개가 쌓여 있다. 결정 로그와 ADR이 코드 근거를 줄 번호로 인용한다.

- **전환 비용**: **소**
- **시기**: 지금 정해도 되고, 불편해질 때 정해도 된다.

## 5. 인증 방향

### 5.1 카카오 로그인 + 서버 세션 쿠키
- **판정**: **적합. 지금 구조와 충돌하지 않는다.**
- **근거**
  - [문서] `인증_설계_20261110.md`가 서버 측 code 교환, 일회용 `state`, 고정 리다이렉트 URI, 세션 ID 해시 저장, 로그인 시 세션 재발급, `Origin` 검사를 정했다. 내가 아는 OAuth 안전 수칙과 어긋나는 곳을 찾지 못했다.
  - [확인] 프론트가 API와 같은 출처다(`frontend/nginx.conf`의 `/food/api/` 프록시). `fetch`는 같은 출처에 쿠키를 기본으로 싣는다. `frontend/src/api/client.ts`에 `credentials` 설정이 없어도 운영에서는 동작한다.
  - [확인] 세션을 PostgreSQL 테이블에 두므로 새 구성 요소(Redis)가 없다. 동기 구조와 잘 맞는다.
- **대안과 장단점**
  - JWT를 브라우저 저장소에: 서버 조회가 없다. 즉시 폐기가 어렵고 XSS에 토큰이 노출된다. 이 서비스에 맞지 않는다.
  - 인증 서비스(Auth0, Supabase Auth, Clerk 등): 구현이 줄어든다. 카카오 연동 지원 여부와 비용, RLS 범위 설정과의 연결을 확인해야 한다 [미확인]. 세션과 매장 소속 검사가 한 DB 트랜잭션 안에 있어야 하는 지금 설계와 결합이 어색하다.
- **시기**: 계획대로 진행한다.
- **[미확인]** 카카오의 현재 요구 사항(동의 항목, 비즈니스 인증, 심사, 리다이렉트 URI 등록 규칙)은 공식 문서로 확인하지 않았다. 설계 문서도 같은 점을 미확인으로 적고 있다. 구현 전에 확인해야 한다.

### 5.3 사용자가 말한 방향과 설계 문서가 다른 곳 (결정이 필요하다)
사용자가 대화에서 정한 방향과 `인증_설계_20261110.md` §12.1의 승인 결과가 세 군데에서 다르다. 구현 전에 한쪽으로 맞춰야 한다.

| 항목 | 사용자가 말한 방향 | 설계 문서 (승인됨) | 내 의견 |
|---|---|---|---|
| 점주가 되는 방법 | 첫 로그인이 점주가 된다 | 운영자가 발급한 일회용 초대 코드로만 점주가 된다(D-2, §3.1의 6) | **초대 코드가 안전하다.** "첫 로그인 = 점주"는 "새 매장을 만든 사람이 그 매장의 점주"라는 뜻으로만 써야 한다. 기존 매장에 처음 로그인한 사람이 점주가 되면 탈취다. 자유 가입을 원하면 "로그인 → 새 매장 생성 → 생성자가 점주"를 따로 설계한다 |
| 동시 세션 수 | 3~5개 | 제한 없음 + "다른 기기 로그아웃"(D-A9) | 둘 다 가능하다. 제한을 두면 가장 오래된 세션을 폐기하는 규칙이 필요하다. 구현은 조회 한 번 차이다. 하나로 정하기만 하면 된다 |
| 직원 출퇴근 | QR 출석, 로그인 없음 | 개인 폰 기기 등록 + 점주 승인(D-A4). "매장에 있다는 증거는 따로 필요"라고 적음(§6.1) | **두 방식은 합쳐진다.** 기기 등록은 "누구인가"를, 매장 QR은 "매장에 있는가"를 증명한다. QR은 고정 그림이면 사진으로 찍어 집에서 쓸 수 있으므로, 짧은 시간마다 바뀌는 서명된 값이어야 한다 |

### 5.4 손님: 익명 → 카카오 연결
- **판정**: **보완. 구조상 미리 정해야 할 것이 하나 있다.**
- **근거**
  - [확인] 손님은 지금 점주와 같은 DB 역할, 같은 RLS 정책을 쓴다(`backend/app/services/guest.py:173-187`).
  - [문서] 설계 §7.2는 손님 계정을 전역 테이블(`guest_profiles`)에 두고, §8.4는 손님 전용 DB 역할을 따로 둔다. 방향이 맞다.
  - **미리 정할 것**: RLS 범위는 "매장 하나"다. 로그인한 손님이 "내 캐릭터와 내 쿠폰을 여러 매장에 걸쳐 본다"는 화면은 이 범위에 들어가지 않는다. 설계 문서에 이 경우의 정책이 없다.
- **대안**
  - 전역 테이블(캐릭터, 손님 프로필)에는 `app.current_guest_id` 기준의 사용자 단위 정책을 건다. 설계 §5.3이 점주에게 쓰는 방식과 같다.
  - 매장에 속한 데이터(쿠폰, 방문 기록)는 `store_id`와 `guest_profile_id`를 둘 다 갖게 하고, 매장 정책 **또는** 본인 정책으로 읽히게 한다. 정책이 둘이 되면 "점주는 자기 매장 것만, 손님은 자기 것만"을 격리 테스트로 증명해야 한다.
- **전환 비용**: 지금 정하면 **소**(문서 한 절). 쿠폰 테이블을 만든 뒤에 바꾸면 **중**.
- **시기**: 손님 등록 구현(12월 초 이후) 전에 설계 문서에 한 절을 추가한다.
- **익명 손님의 임시 캐릭터**: 기기 쿠키가 지워지면 사라진다. 쿠키 수명은 1년이다(`backend/app/api/guest/router.py:19-41`). "임시"의 기한(언제 지우는가)이 정해져 있지 않다 [미확인]. 개인정보 처리 설계와 함께 정해야 한다.

### 5.5 빠진 정책
- **계정 복구**: 점주가 카카오 계정을 잃으면 매장에 들어갈 방법이 없다. 설계상으로는 운영자가 새 초대 코드를 발급하면 된다. 이 절차를 운영 문서에 한 줄로 적어 둔다.
- **점주 교체와 폐업**: 소속 해제 스크립트는 설계에 있다. 매장 데이터를 언제 지우는지는 미확인으로 남아 있다.

## 6. 우선순위 5개

실행 순서대로 적었다. 1~3은 서로 의존하므로 이 순서가 가장 싸다.

1. **API 테스트를 PostgreSQL로 통일한다 (3.9).** 인증의 핵심 장치가 SQLite에서 시험되지 않는다. 인증보다 먼저 해야 테스트를 두 번 쓰지 않는다. 비용 중.
2. **ID를 네이티브 `uuid` + v7로 바꾼다 (3.6).** 데이터가 임시인 지금이 가장 싸다. 인증 테이블 6개를 만들기 전에 끝낸다. 비용 중. 하지 않기로 정해도 된다. 그 경우 "출시 후에는 하지 않는다"까지 같이 정한다.
3. **호스트 분리 + 인증·소속 검사 + 열린 경로 닫기 (3.2, 5.2).** 지금 가장 큰 보안 문제다. 주소를 아는 누구나 모든 매장을 읽고 쓴다. `audit_events` 불변, 역할 권한 정리, 보안 헤더, CORS 제거를 같은 묶음으로 한다. 비용 대.
4. **백업 자동화 + 복구 연습 1회 + 호스트 결정 (3.7, 4.3).** 실제 매장 데이터가 들어가는 날이 기한이다. 비용 소~중.
5. **요청 로그 + DB를 보는 상태 경로 + 외부 가동 감시 (4.5).** 장애를 점주보다 먼저 알기 위한 최소 세트다. 출시 후 결정(async, 인덱스)의 근거 자료도 여기서 나온다. 비용 소~중.

그다음: 분석 조회의 기간 조건과 SQL 집계(3.5), 프론트 ESLint와 손님 화면 번들 분리(2.3, 1.3), CI의 downgrade 검사(3.8).

## 7. 하지 말아야 할 과한 변경 3개

1. **전면 async 전환.** 느린 외부 호출과 긴 연결이 없다. 매장 격리 회귀 위험과 서비스·테스트 전면 수정 비용만 생긴다. ADR-014의 보류 결정이 맞다.
2. **Next.js 이전.** 검색 노출이 필요 없는 운영 화면이다. 서버 프로세스와 인증 경유 지점이 늘어난다. 손님 첫 화면 속도는 번들 분리로 해결된다.
3. **매장별 스키마·DB 분리, 또는 도메인 패키지로의 전면 재배치.** RLS는 테스트로 증명되어 있고 손님 전역 계정과 맞는다. 폴더 재배치는 기능을 하나도 더하지 않으면서 모든 import와 문서의 경로 인용을 깬다. 큰 파일 두 개를 나누는 것으로 충분하다.

같은 이유로 Redis 세션, 쿠버네티스, 감사 기록의 외부 저장소 반출도 지금은 넣지 않는다.
