## 목업과 차이·계산 기준

- 목표의 매출/이익 토글과 이익 추이 목표선은 사용자 지시대로 생략. 현재 선행 구현 API/GoalDialog에는 이미 `profit_target`이 있으므로 기존 편집 흐름은 보존하고 이번 KPI에서 사용하지 않는다.
- 매장 기본 목표 API는 없다. 월별 실제 목표만 표시하며 툴팁에 기본 목표 미지원 사실을 설명한다. 기본 목표가 있는 것처럼 쓰지 않았다. 목표 0/null이면 기존 목표 편집을 여는 빈 상태.
- 추이는 예시의 고정 max 대신 실제 매출/이익/목표에 맞게 축 범위를 계산한다. 적자는 0선 아래, 지난 적자는 빨강, 이번 달은 해칭과 진행 중 표기. 목업의 음수 없는 예시와 다른 실제 데이터도 보존한다.
- 전월 동기 비교는 기존 API대로 날짜가 있는 판매·입고·카드수수료 기준이며 날짜 없는 월 수기 비용을 포함하지 않는다. 월 전체 hero/지출과 비교 기간의 기준 차이는 툴팁에 명시했다. 과거 월은 지난달 전체와 비교하되 카드의 비교 캡션은 승인 문구를 유지한다.
- 이익률/지난달/차이는 월 전체 기준, 차이는 부호 있는 %p. 객단가=매출÷완료 주문 수, 원 단위 반올림. 주문 0건은 미산출.
- 영업일은 `store.business_days`의 요일로 계산. 경과=오늘 포함, 잔여=내일부터. 예상 매출%=경과/전체 영업일. 하루 필요=잔액/잔여일(원 단위 올림); 잔여0이고 미달이면 미산출. 평소 하루는 지난달 매출/영업일, 지난달 기록 없으면 이번 달/경과 영업일. 영업일 미설정은 미산출. 임의 공휴일·휴무일 예외는 추가하지 않았다.
- xl 미만 지출을 전체 폭으로 두어 sm 2열에서 옆 빈 칸을 없앴다. 작은 화면에서는 겹침 없이 읽히도록 쌓는다. 목업 상시 열린 툴팁 대신 Astryx의 hover/focus/tap Tooltip을 사용한다.

## 브라우저 검증과 미확인

- 개발 `/pnl`의 실제 API 데이터로 1280/1024/390px DOM 측정: 페이지 가로 넘침 없음. 1280 목표340px·첫 행248px·추이238px. 1024 2열/지출·추이·목표 전체 폭. 390 1열. 주요 숫자·미니 바 영역 넘침 없음. hero scrollWidth 초과는 의도적으로 잘리는 장식 wave다.
- 이익 탭 DOM 클릭 후 선택 true·이익 목표선 없음·적자 막대 있음. 브라우저 포인터 자동화는 뷰포트 불일치로 실패하여 DOM click을 사용했다.
- 목표 빈 상태의 버튼으로 실제 기존 GoalDialog가 열리며 입력2개를 유지함을 확인하고 취소로 닫았다(저장 없음). `document.fonts.check`는 Pretendard Variable 800/30px 로드 true. 네이티브 `<dialog>`는 명시적 role 속성이 없어 최초 `[role=dialog]` 대기 검사는 시간 초과했고 `dialog[open]`으로 수정하여 확인했다.
- API 쓰기 없이 별도 브라우저 root에 승인 목업 값으로 격리 표본 렌더: 목표70.4%, 잔액7,410,000원, 목표2,500만, 유리 효과 `blur(14px) saturate(1.4)`, hero pill `rgba(255,255,255,.16)` 확인. 1280/1024/390의 주요 숫자 넘침 없음. 이익 목표 값이 표본에 있어도 이익선 없음.
- 표본은 실제 날짜·영업일 계산을 사용하므로 목업의 임의 진도65%/잔여12일과 달랐다. 테스트 표본은 서버에 저장하지 않았으며 종료 시 제거한다.
- 원본 PNG는 열어 확인했지만 **구현 화면의 최종 시각 일치·픽셀 비교는 미확인**. T3 preview snapshot은 시간 초과, ego screenshot도 Page.captureScreenshot 시간 초과, 직접 capture는 검정 화면, Computer Use는 native pipe unavailable. 정상 캡처로 오인하지 않았다. 실기기, 생산 빌드 브라우저, Tooltip 터치 조작은 미검증.
- 전체 백엔드 pytest는 실행하지 않았고 관련29개만 실행. 실제 POS A/B 및 실장비 연동·실시간성·운영 배포는 검증하지 않았다.
