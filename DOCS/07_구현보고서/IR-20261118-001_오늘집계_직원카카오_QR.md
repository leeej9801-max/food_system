# 오늘 집계 · 직원 카카오 · 회전 QR 구현

## 범위와 결과

사용자 확정 지시 A/B, U-24, ADR-014에 따라 `C:/Users/leeej/.t3/worktrees/food/feature-attendance`, `feature/attendance`에서만 작업했다. `C:/dev/food`는 접근·수정하지 않았다. stage/commit/push/운영 배포/운영 DB 변경은 하지 않았다. 선행 근태 변경과 Antigravity의 동시 변경은 보존했다.

- 오늘 집계는 매장 `Store.timezone`의 오늘 자정부터 다음 자정 전까지다. 방문은 `VisitSession.seated_at` 기준 팀 수·`party_size` 합, 매출은 기존 `sales_orders.sum_completed_sales_between`을 사용한다. 취소 주문·취소 품목은 제외하고 주문 시각 누락은 수신 시각으로 집계한다. 기존 누적 API·설정 화면 계약은 유지했다. 헤더는 새 집계로 30초마다 갱신한다.
- 관리 화면의 출근/퇴근 버튼은 회전 QR 모달을 연다. 매장별 256비트 secret과 `store_id:30초 epoch window`의 HMAC-SHA256을 사용한다. QR 토큰은 DB에 저장하지 않고 직원/창/원본 이벤트 연결만 추가 전용 표에 보존한다. 현재/이전 창 1개만 허용한다.
- 본인 카카오 세션이 있으면 직원 모바일 페이지가 바로 기록한다. 세션이 없으면 로그인 버튼으로 카카오에 이동한다. 서버가 유효 원본+정정의 마지막 상태로 IN/OUT을 결정하며 클라이언트가 종류·시각·직원 ID를 선택할 수 없다.
- UUID 멱등성과 직원 행 잠금·기존 이벤트 검증을 재사용했다. 같은 직원/같은 창에서 새 UUID는 409, 같은 UUID 재시도는 창이 만료되어도 원본을 반환한다. QR 이벤트와 창 사용 기록은 한 트랜잭션이다. 기존 owner-direct의 60초 같은-kind 병합은 기본값으로 보존하고, QR은 별도 창 재사용 방지가 있으므로 해당 병합만 끈다. 그렇지 않으면 빠른 IN→OUT→IN이 이전 IN으로 합쳐진다.
- QR 모달은 서버 응답의 남은 시간을 기준으로 카운트다운하며 만료 시 재발급한다. 2.5초 폴링으로 모달을 연 뒤 해당 매장에서 기록한 직원의 QR 이벤트를 찾으면 완료 상태로 바뀌고 근태 query를 무효화한다. QR은 특정 직원에 묶이지 않으며 인증한 직원 본인을 기록한다. 웹소켓은 추가하지 않았다.
- 직원 등록 모달 아래에 직원별 카카오 연결 상태, 초대 링크 생성, 닉네임 확인 후 승인 UI를 제공한다. 초대는 7일/1회용이고 새로 만들면 이전 미사용 링크를 만료시킨다. 연결은 PENDING, 승인 후 ACTIVE다. 카카오 계정당 매장별 직원 1명, 직원당 연결 1개를 DB UNIQUE와 잠금으로 검증한다.
- `/staff/*`는 매장 선택/사이드바를 거치지 않는 모바일 경로다. URL fragment로 받은 QR/초대 값을 즉시 주소에서 제거하며 탭 sessionStorage에 최대 10분만 보관한다. 완료·PENDING 확인 후 보관값을 지운다. 재스캔 시 fragment 변경으로 페이지를 다시 초기화한다.

모든 경로 앞에 `/api/v1`을 붙인다. 점주 항목은 권한이 없는 공개 데모 **PROVISIONAL**이다.

| refresh | 48바이트 난수, SHA-256만 저장. 최초 세션 60일 절대 만료 유지, 매 사용 rotation. 이전 값 재사용은 해당 직원의 모든 세션 폐기 |
| 즉시 폐기 | 매 요청 DB 세션/직원 상태 검사. 퇴사 비활성화도 모든 세션 폐기. PostgreSQL 동시 재사용 검사 |
| 쿠키 | 직원 전용 이름과 매장별 staff-access Path, Domain 미설정, SameSite=Lax, HttpOnly. HTTPS는 Secure, 개발 loopback HTTP만 예외 |
| Origin/제한 | 신규 변경 API는 허용 Origin 필수. 로그인 10회/분·변경 60회/분 등. 프로세스별 메모리 제한에 shortcut 주석 |
| QR | 매장 secret별 HMAC, 현재/이전 창만, 형식 검증·상수시간 비교. 직원/창 복합 PK, QR 토큰 DB 미저장 |
| 불변/멱등 | 원본·정정 보존, QR 사용 추가 전용. PostgreSQL 직원 행 잠금·UUID·원본과 QR 사용 원자 commit 검사 |
| 로그/캐시 | OAuth 접근 로그 query 제거, 민감 SQL/HTTP 예외 traceback 출력 제한, 응답 no-store/referrer no-referrer. 토큰·QR·code를 앱 로그/문서에 기록하지 않음 |
| 점주 인증 | 미구현, 신규 점주 화면·응답·OpenAPI 설명에 PROVISIONAL. 점주 카카오 로그인은 범위 밖 |

서명 키는 선택 설정 `STAFF_AUTH_SIGNING_KEY`(32바이트 이상)를 사용한다. 미설정이면 기존 `KAKAO_CLIENT_SECRET`에서 `food/staff-jwt/v1` 용도로 HMAC 유도한다. 임의 기본 키나 재기동마다 바뀌는 개발 키를 쓰지 않는다. client secret을 바꾸면 유도 키도 바뀌어 기존 access/OAuth가 무효화되므로 독립 서명 키 설정을 권장한다. 비밀값은 출력하거나 문서에 적지 않았다.

## 브라우저 및 스크린샷

T3 preview에서 실제 Vite/FastAPI를 **5175/8002만** 실행했다. 카카오 외부 HTTP를 fake 프로필로 대체한 격리 SQLite QA다. 실제 카카오 로그인·실기기 확인으로 주장하지 않는다.

- 헤더는 오늘 QA 방문 1팀/3명, 오늘 매출 39,000원이다. 다른 날 QA 방문/125,000원 주문은 헤더에 합산되지 않는다.

- 390px 로그인 안내와 출근 완료, 가로 넘침 없음·사이드바 없음 확인. 가짜 카카오 callback이 만든 실제 HttpOnly 세션으로 QR 기록을 수행했다. 단순 화면 상태 주입 캡처가 아니다.
- 직원 관리에서 QA 민서 PENDING→ACTIVE 승인과 QA 서준의 초대 링크 생성/1회용·7일 안내를 확인했다. 실제 링크를 외부로 보내지 않았다.
- 같은 모바일 경로에서 다시 스캔해도 fragment를 제거하고 새 컨텍스트로 기록하는 것을 확인했다. 이 검증에서 초기 state가 재사용되는 문제를 발견해 라우트 key 초기화를 추가했다. preview의 가짜 callback fetch는 redirect CORS 제한으로 한 번 실패했지만 쿠키 발급을 확인하고 실제 페이지 이동으로 완료했다. 실 카카오 왕복 성공으로 보고하지 않는다.

## 마이그레이션·실행 설정

- 새 head `0016_staff_kakao_qr`, 부모 `0015_attendance_integrity`. 이전 0014/0015 파일은 변경하지 않았다. 0016 downgrade는 직원·기존 원본/정정/스케줄을 보존하지만 초대/카카오 연결/세션/QR secret·사용 메타데이터를 제거한다. rollback 전에 이 메타데이터를 백업해야 한다.
- 다른 손익 브랜치의 `0014_monthly_goals`와 번호/분기 정리는 **미해결**, 병합 담당자 후속 작업이다.
- backend: `uv sync --extra dev`, 권한 있는 소유자 연결로 `alembic upgrade head`, 런타임 역할 설정. 이번에는 격리 테스트 DB만 적용했다.
- 기존 `.env`의 `KAKAO_REST_API_KEY`, `KAKAO_CLIENT_SECRET`을 사용한다. `KAKAO_REDIRECT_URI`와 `STAFF_FRONTEND_URL`, `CORS_ALLOWED_ORIGINS`를 실제 주소로 맞춘다. 운영은 HTTPS 전용 호스트/루트 경로를 기준으로 한다.
- 로컬 callback 설정: `http://localhost:8001/api/v1/auth/kakao/callback`. 운영 설정: `https://food.leejblab.site/api/v1/auth/kakao/callback`. 이 에이전트는 8001/5174를 실행하거나 변경하지 않았다. 8002는 callback 등록값과 달라 실 왕복을 수행하지 않았다.
- 브라우저 QA 서버/프론트는 검증 후 종료했다. 실제 서비스에는 `.qa-attendance-impl3/server.py`를 사용하지 않는다.

## 사용자가 할 실제 카카오 수동 확인

1. 병합 시 migration 분기를 정리하고 테스트/개발 DB를 백업한다. 소유자로 0016까지 적용하고 런타임 권한을 설정한다. 운영 배포는 별도 승인 작업이다.
2. 카카오 콘솔에서 로그인 활성화, REST API 키/Client Secret 사용, 닉네임(`profile_nickname`)만 동의하도록 설정한다. 위 로컬/운영 Redirect URI를 정확히 등록한다. 비밀값을 문서·채팅에 보내지 않는다.
3. 실제 로그인용 개발 서버는 사용자가 직접 등록된 **8001** callback과 연결한다. 프론트는 `STAFF_FRONTEND_URL`·CORS·`VITE_API_BASE_URL`을 같은 개발 주소로 맞춘다. 휴대폰은 `localhost`로 PC에 접속할 수 없으므로 실제 폰 왕복은 사용자가 마련한 HTTPS 접근 주소와 해당 Redirect URI 설정이 필요하다.
4. 직원 등록 화면의 해당 직원 행에서 초대 링크를 만든다. 직원이 자기 폰에서 링크를 열고 카카오 로그인한다. 닉네임만 동의하는지, PENDING 대기 화면이 나오는지 확인한다.
5. 점주 화면에서 닉네임과 직원을 대조하고 승인한다. 직원 폰에서 승인 상태를 확인한 뒤 매장 QR을 스캔한다. 미승인 직원은 기록이 거부되는지도 확인한다.
6. 모달의 30초 카운트·QR 교체를 확인하고, 직원 폰의 `OOO 님 출근 확인되었습니다`와 관리 모달 완료/근태 반영을 대조한다.
7. 다음 창에서 다시 스캔해 퇴근을 확인한다. 같은 창을 다른 요청으로 재사용하면 거부되고 네트워크 재시도는 원본 하나인지를 확인한다. 로그인 중 현재·이전 시간창 범위를 벗어나면 새 QR을 재스캔한다.
8. 로그인 유지/새로고침, 15분 access 만료 뒤 자동 refresh, 로그아웃, 직원 비활성화 즉시 세션 폐기를 확인한다. 개발자 도구에서 HttpOnly/SameSite와 HTTPS Secure를 확인하되 쿠키값·code·토큰을 캡처·공유하지 않는다.

## 미확인·후속

- 실제 카카오 앱 설정·동의 화면·왕복·직원 폰 카메라·HTTPS 운영 쿠키는 미검증이다. 실제 직원 개인정보는 사용하지 않았다.
- 점주 인증·승인 주체 신원·점주 재인증은 PROVISIONAL이다. 공개 데모의 점주 endpoint를 실운영 권한 검증으로 해석하면 안 된다.
- QR 촬영본을 60초 허용 창 안에 전달하는 대리 기록은 막지 못한다. 위치/매장 Wi-Fi 검증은 이번 확정 범위가 아니다.
- refresh의 같은 이전 값 동시 사용도 재사용으로 보아 전 세션을 폐기한다. 같은 탭의 401은 합치지만 여러 탭/기기에서 쿠키를 복사해 병행 사용하는 것에 유예 창을 두지 않았다.
- 인메모리 레이트 제한은 다중 프로세스 공유 제한이 아니다. 보관 기간·열람·정정·탈퇴·폐기·급여 법적 요건은 기존 인증 설계 §6.5와 같이 미확인이다.
- 전체 일반 backend 회귀, 독립 보안 리뷰, 실제 기기/스크린리더 QA, 운영 배포와 실데이터 migration은 미실행이다.

공식 구현 근거: [카카오 REST API](https://developers.kakao.com/docs/ko/kakaologin/rest-api), [카카오 설정](https://developers.kakao.com/docs/ko/kakaologin/prerequisite), [PyJWT 사용법](https://pyjwt.readthedocs.io/en/latest/usage.html). 기존 인증 설계의 기기등록 가정은 이번 사용자 확정안으로 대체했으며 원문을 덮어쓰지 않고 결정 로그에 기록했다.

## 최종 보강 확인

전체 49개 통과 뒤 QR 형식 제약과 schema 분리를 반영하고, 하루 뒤 refresh를 회전해도 최초 만료가 유지되는 검사를 강화했다. 보강 focused는 **5 passed, 1 warning in 32.61s**, QR 비ASCII 입력·퇴사 폐기, refresh 고정 만료/전 세션 폐기, Seoul/뉴욕 DST 집계 2종, OpenAPI 정확 일치를 다시 확인했다. 전체 ruff와 전체 pyright도 재실행해 exit 0 / 0 errors를 확인했다. 프론트 최종 build는 **1m 44s**, 청크 경고를 유지하며 exit 0이다.

마지막 자체 검토에서 민감 경로의 예상치 못한 예외가 Starlette ServerErrorMiddleware에서 재전파되어 uvicorn traceback에 포함될 수 있는 경계를 차단했다. 비밀을 포함한 가짜 예외가 응답/로그에 없고 TestClient 기본 예외 전파도 넘지 않는 회귀 검사를 추가했다. callback의 실제 303 응답도 OpenAPI에 명시했다. 이후 전체 ruff/pyright와 근태 전체를 다시 실행하여 **50 passed, 4 warnings in 163.51s**를 확인했다. 이 결과가 앞선 전체 49개 결과를 대체한다. 공용 QR 모달은 특정 직원 필터를 제거해 실제 스캔한 직원의 완료를 표시하며, PENDING 화면의 승인 상태 확인은 매장 query를 보존한다. 해당 프론트 변경 뒤 tsc·ESLint·Vitest 100 및 최종 build를 재검사했다(승인 상태 링크의 마지막 한 줄은 별도 ESLint/tsc 포함 build 확인).

`git diff --check`는 통과했다. Vault 최종 검사는 **118개 파일/995개 wikilink, 기존 깨진 링크 1개, 중복 이름 0개**다. 새 문서 링크 오류는 없다. 기존 깨진 링크는 `WO-20261110-002_lee-start_표준정렬_리팩토링`의 `WO-20261110-001_손님_모바일웹_및_매장TV_시안`이다. 이 작업과 무관한 기존 문서는 변경하지 않았다.
