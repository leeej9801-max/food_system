# 재고·입고 작업 화면 개선

S05 / REQ-008·REQ-009. 기준 브랜치 `design/astryx-menu`, 기준 커밋 `b10afa0`.
작업 브랜치 `t3/6dd90303`, 작업 폴더 `C:\Users\leeej\.t3\worktrees\food\t3-6dd90303-50e0f13e41cffc6e`.

## 구현과 상단 카드 최종안

- 파란 카드: **입고 필요(부족+점검) 수**, **안전재고 대비 부족률 상위 3개**. 카드 전체를 클릭하거나 Enter/Space로 활성화하면 표의 입고 필요 segmented 선택과 실제 필터가 함께 바뀐다. `role=button`, `tabIndex`, `aria-label`, `aria-pressed`를 제공한다.
- 부족률은 `(안전재고 − 예상 재고) / 안전재고`. g·ml·개가 다른 항목을 단순 부족량으로 비교하지 않도록 비율로 정렬한다. 양수 안전재고가 있는 항목만 순위에 넣고, 안전재고가 없거나 0이면 비율을 만들지 않는다. 음수 예상 재고의 비율은 100%를 넘을 수 있다. 카드 합계에는 순위에 없는 점검 항목도 포함한다.
- 넓은 카드: **입고 등록 / 폐기·보정 / 실사 입력** 버튼과 **최근 입고일 / 최근 7일 입고 건수 / 최근 7일 입고액**. 기존 모달을 열고 모달에서 식자재를 선택한다. 최근 7일은 입고 데이터 조회 완료 시각부터 앞선 168시간의 실제 입고 기록이다. 새 입고 저장 후 재조회 시 기준 시각도 갱신한다. 합계는 입고 금액의 소수 둘째 자리까지 합산한다. 입고가 없으면 0·없음, 조회 중/실패는 대시로 구분한다.
- 이유: 다음에 해야 할 재고 기록을 상단에 놓고, 기존 데이터로 확인 가능한 구매 상황을 함께 보여준다. 기존 단가 변동 정보는 삭제하지 않고 이력 모달로 이동했다. 새 서버 기능이나 가짜 숫자는 추가하지 않았다.

## 상태 탭·표·실사 날짜

- 메뉴 관리와 같은 Astryx `SegmentedControl`·`Pagination`, 같은 테마를 사용한다. **전체 / 입고 필요 / 정상 / 부족 / 점검**. 입고 필요는 기존 `LOW_STOCK`·`NEGATIVE_WARNING`의 합집합이며 서버 상태 종류는 바꾸지 않았다.
- 클라이언트에서 20행씩 페이지를 나눈다. 필터 변경은 1페이지, 조회 결과 축소는 유효한 마지막 페이지로 보정한다. 매장이 바뀌면 페이지·모달 상태를 새로 시작한다.
- 필터·페이지가 바뀔 때 스크롤 영역도 새로 시작해 이전 페이지의 맨 아래 위치가 남지 않는다.
- 너비 768px 이상·높이 600px 이상에서는 메뉴 관리와 같은 `calc(var(--app-viewport-height) - var(--app-header-height, 56px) - 3rem)`을 사용한다. `3rem`은 App 래퍼의 위·아래 여백이다. 제목·상단 카드·툴바·하단 페이지 탐색은 고정하고 표가 남은 높이를 사용한다. 표 영역만 가로·세로 스크롤, 헤더·첫 식자재 열 고정. CSS 원본 끝에 재고 전용 블록만 추가했다.
- 폰·낮은 화면은 메뉴 관리와 동일하게 문서 스크롤을 허용하고 재고 표 높이를 360px로 유지한다. 이력 모달은 화면 높이를 넘지 않는 고정 높이, 내부 표 스크롤이다.
- 마지막 실사 수량은 값만 표시한다. 옆 ⓘ 버튼의 Astryx Tooltip에 `최근 실사: 날짜`를 표시한다. `touchTrigger=tap`, `focusTrigger=always`, 호버 기본 동작과 날짜가 포함된 aria-label을 사용했다. 날짜는 매장 시간대로 표시한다. 버튼 없는 셀에도 동일 폭을 확보해 수량 끝을 맞춘다.

## 폐기·보정 매핑

사유 드롭다운 → 같은 줄의 방향 토글과 양수 수량 입력 → 메모 순서로 바꿨다. 기존 접근성 이름 `사유`·`단위`를 유지했다.

| 사유 | 방향 | API 전송 |
|---|---|---|
| 조리 폐기 `WASTE` | 감소만, + 비활성 | `quantity_delta = -수량`, reason 그대로 |
| 유통기한 경과 `SPOILAGE` | 감소만, + 비활성 | `quantity_delta = -수량`, reason 그대로 |
| 수량 보정 `CORRECTION` | + / − | 선택한 부호 × 수량, reason 그대로 |
| 기타 `OTHER` | + / − | 선택한 부호 × 수량, reason 그대로 |

사유를 폐기로 바꾸면 방향도 감소로 돌아간다. 수량은 유한한 양수만 허용한다. 빈 값·0·음수·NaN·Infinity는 전송하지 않는다. 단위는 기존처럼 식자재 기본 단위이며 API 필드·형식은 동일하다. 입고의 양수 수량·0 이상 금액, 실사의 0 이상 수량 검증은 유지했다. 실패 시 입력·오류를 보존한다.

**서버 계약 자체는 사유별 부호를 강제하지 않는다.** `InventoryAdjustmentCreate`는 Decimal delta와 사유 enum을 받고 서비스는 0을 거부한다. 감소 전용 제약은 기존 프론트의 `-Math.abs(q)` 동작이며 이번 UI에서도 보존했다. 서버를 수정하지 않았다.

## 이력 모달과 메뉴 필터

- 재고 현황 제목 옆 보조 문구를 **입고 · 단가 이력 >** 버튼으로 교체하고 아래 아코디언은 제거했다.
- 전체 / 식자재별 / 메뉴별 필터를 구현했다. 식자재 선택에는 입고 이력에 있는 식자재를 사용하므로 비활성 식자재의 과거 기록도 볼 수 있다.
- 메뉴는 기존 `fetchMenus(store.id, {status: 'all'})`, 선택한 메뉴의 연결 식자재는 `fetchMenuRecipe(store.id, menuId)`로 조회한다. 기존 RecipeEditor와 같은 `menu-recipe` 캐시 키를 사용한다. 레시피의 ingredient_id 집합에 포함된 이력만 표시한다. 현재 레시피 연결 기준이며 과거 레시피 버전을 복원하는 기능은 아니다.
- 메뉴 조회·선택 레시피 조회는 메뉴 필터일 때만 활성화한다. 미선택·조회 중·실패·빈 레시피·입고 없음 상태를 구분하며, 실패나 빈 결과를 전체 이력으로 대체하지 않는다.
- 기존 입고 일시·식자재·수량·금액·단가·공급처 열을 유지했다. 기존 50건 표시 제한은 제거했다. 전체 API 반환 이력을 모달 내부에서 스크롤한다.
- 단가 변동은 기존처럼 식자재별 최근 기본 단위 단가 대 입고 단가 단순 평균이다(2건 이상·평균 0 제외·절대 변동률 상위 3개). 최신 기록은 날짜로 찾으며 현재 이력 필터에 맞춰 계산한다.

## 실사 로직 조사 — 변경 없음

확인한 코드: `frontend/src/pages/InventoryPage.tsx`, `frontend/src/api/inventory.ts`, `backend/app/services/inventory.py`, `backend/app/schemas/__init__.py`, `backend/app/repositories/inventory.py`.

1. 사용자는 **식자재 기본 단위**의 실제 수량을 입력한다. 기본 단위는 g/ml/ea이며 개 단위도 가능하다. 실사에는 구매 단위 선택·자동 환산·반 남음 단계 입력이 없다. 0도 허용한다. 저울 사용을 코드가 강제하는 것은 아니지만, g/ml 재료에는 수치를 알아야 입력할 수 있다.
2. `createCount`는 `actual_quantity`와 메모만 전송한다. 서버는 식자재 기본 단위를 붙이고 소수 셋째 자리 수량, 현재 시각, 새 실사 이력으로 저장한다. 과거 실사 기록은 지우지 않는다. 실제 수량과 예상 수량의 차이를 별도 조정 이벤트로 자동 생성하지는 않는다.
3. 가장 최근 실사 수량이 기준량, 실사 시각이 기준 시점이 된다. 실사 없는 식자재는 0부터 시작한다. **예상 재고 = 최근 실사 수량 + 기준 이후 입고 − 이론 소모 + 기준 이후 부호 있는 폐기·보정**. 새 실사는 이후 계산의 기준을 바꾸지만 입고·조정 이력을 덮어쓰지 않는다.
4. 이론 소모는 현재 연결 레시피 수량 × 완료된 주문 항목의 판매 수량이다. 기준 이전에 수집한 주문은 제외하고, 기준보다 과거 UTC 날짜에 주문된 지연 업로드도 제외한다. 같은 UTC 날짜 안에서는 주문 발생 시각 전체가 아니라 수집 시각과 날짜 조건을 사용한다. 당시 레시피 버전을 재현하는 계산은 아니다.
5. 예상 재고가 음수면 점검, 아니면 안전재고가 설정되어 있고 예상량 ≤ 안전재고면 부족, 나머지는 정상이다. 실사 기록 자체의 필수 주기나 전 품목 매일 입력 강제는 없다. 빈도는 기존 미결정 항목으로 남겨 둔다.

**의견:** 모든 재료를 매일 g/ml로 확인하는 방식은 1~2인 매장에 입력 부담이 크다. 아래는 구현하지 않은 검토 대안이다.

- **구매 단위로 개수·반 개:** 예: 1kg 봉지 2.5개, 병 1.5개. 저울 없이 기존 구매 단위와 연결하기 쉽다. 다만 박스/병별 내용량·개봉 상태가 달라 환산량과 포장 규격 관리가 필요하다. 현재 구매 단위 enum은 kg/g/L/ml/ea여서 임의 포장 단위 지원은 별도 설계가 필요하다.
- **다 썼음 / 조금 / 반 / 충분함:** 빠르게 확인하고 우선 입고할 품목을 고르기 좋다. ‘반’의 기준 용기/최대량이 없으면 정확한 g/ml로 환산할 수 없으며 원가·예상 재고의 확정 수치로 취급하면 안 된다. 참고 상태로 다루는 것이 적합하다.
- **자주 쓰거나 비싼 핵심 재료만 주기 확인:** 기존 실사 기준 계산을 유지하면서 입력 대상을 줄일 수 있다. 제외 품목은 예상량 오차가 누적될 수 있어 주기적 전체 확인 또는 큰 오차가 난 품목을 따로 확인할 필요가 있다. 파일럿에서는 이 방식과 구매 단위 입력을 먼저 비교하는 것이 현실적이다.
