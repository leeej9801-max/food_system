# 근태 1차 보안·무결성

## 범위와 결과

사용자 지시 1~7, ADR-014, 인증 설계 §6.4에 따라 동기 3계층에서 보강했다. 지정 worktree `C:/Users/leeej/.t3/worktrees/food/feature-attendance`의 `feature/attendance`에서만 작업했다. 본 저장소, Antigravity의 근태 화면·공통 헤더·CSS·컴포넌트, manifest/lock은 수정하지 않았다. 커밋·push·운영 DB 변경·배포는 하지 않았다.

- 요청 `client_event_id`는 클라이언트 UUID 필수다. DB의 `UNIQUE(store_id, staff_id, client_event_id)`와 PostgreSQL 직원 행 잠금을 함께 사용한다. 같은 키는 시간·이후 기록·비활성화와 무관하게 기존 원본을 그대로 HTTP 200으로 반환한다. 새 기록만 201이다.
- 같은 직원·kind의 서버 시각 기준 최근 60초(경계 포함)는 기존 원본을 반환한다. 60초를 넘으면 기존 출근/퇴근 순서 검증을 적용한다. 중복 키 비교는 원본을 대상으로 하며 정정 이력으로 원본을 바꾸지 않는다.
- 60초 중복을 다른 UUID로 요청한 경우에도 나중에 같은 키를 재시도할 수 있도록 `attendance_event_retries`에 키→원본 연결만 보존한다. `attendance_events` 행은 늘리지 않는다. 동일 키 재요청은 연결 행도 추가하지 않는다. 이 보조 표 역시 추가 전용·매장 RLS다.
- 기존 원본·정정 불변 트리거를 유지하고 `audit_logs`에 동일한 PostgreSQL UPDATE/DELETE/TRUNCATE 차단을 적용했다. SQLite에는 UPDATE/DELETE 동등 트리거가 있다. 런타임 역할 설정 재실행 시에도 두 새 표의 UPDATE/DELETE/TRUNCATE 권한을 회수한다.
- `audit_logs(id, store_id, actor, action, entity, entity_id, before JSON, after JSON, created_at)`를 추가했다. 직원 CREATE/UPDATE/DEACTIVATE, 스케줄 CREATE/UPDATE/DELETE, 정정 CORRECT를 업무 변경과 같은 트랜잭션에 기록한다. 생성 전·삭제 후는 SQL NULL이다. 정정의 before는 지목한 원본/이전 정정의 스냅샷이며 누락 추가는 NULL이다.
- 스냅샷은 명시적인 응답 스키마 허용 필드만 직렬화한다. actor는 기존 RequestContext를 보존하고 인증 전 기본값 `beta-staff`를 사용한다(**PROVISIONAL**, 실제 사용자 신원 증명 아님).
- 직원 DELETE는 status=INACTIVE로 바꾼다. 재삭제는 새 감사 행을 만들지 않는다. 기본 직원/근태 목록은 ACTIVE만 표시한다. `include_inactive=true`로 비활성 직원의 이력·집계를 조회할 수 있다. 기존 스케줄·원본·정정은 보존하며 비활성 직원의 신규 출퇴근은 409 `STAFF_INACTIVE`다. 기존 키 재요청은 새 기록이 아니므로 200이다.
- 직원 GET/PUT/DELETE 경로를 추가했다. 수정은 이름·역할·색의 전체 PUT이며 상태를 임의로 재활성화하는 API는 추가하지 않았다.

## 마이그레이션과 호환성

- revision **`0015_attendance_integrity`**, down_revision **`0014_attendance`**. 기존 0014 파일은 변경하지 않았다.
- 기존 직원은 ACTIVE, 기존 이벤트는 `client_event_id=id`로 backfill한다. 원본의 id·시각·kind와 정정은 보존한다. backfill 동안만 기존 불변 UPDATE 트리거를 해제하고 즉시 복원한다. PostgreSQL에서는 FORCE RLS도 소유자 backfill 동안만 해제·복원하며 전체가 마이그레이션 트랜잭션 안이다.
- 복합 인덱스: events(store_id, occurred_at), events(store_id, staff_id, occurred_at), shifts(store_id, work_date). 감사 표에는 (store_id, created_at), 재요청 키에는 복합 PK가 있다.
- PostgreSQL은 NOT NULL/UNIQUE/CHECK를 사용한다. SQLite는 FK가 있는 기존 표의 재생성을 피하기 위해 client UUID의 NULL INSERT 거부와 staff 상태 검증을 동등 트리거로 적용하고 고유 인덱스를 사용한다. SQLite RLS·행 잠금·TRUNCATE·역할 권한을 PostgreSQL과 같다고 주장하지 않는다.
- 적용은 소유자 연결로 `alembic upgrade head` 후 런타임 역할 스크립트를 실행한다. 이번 실행은 독립 테스트 DB만 대상으로 했다. 새 클라이언트와 backend를 함께 전환해야 한다. 이전 요청 형식(client_event_id 없음)은 422다. frontend의 기본 UUID 생성은 보안 컨텍스트의 Web Crypto를 사용한다.
- `alembic downgrade 0014_attendance`는 기존 원본·정정·스케줄·직원을 보존하지만 **새 감사 로그·재요청 키 표·client_event_id·status·새 인덱스를 제거한다.** 롤백 전 새 감사 이력과 키·상태를 별도로 백업해야 한다. 내려갔다 재적용하면 직원은 ACTIVE, 이벤트 키는 id로 다시 채워지므로 기존 멱등 키/비활성 상태 복원을 뜻하지 않는다.
- **병합 미해결:** 본 저장소 `design/pnl-ux`의 미커밋 `0014_monthly_goals`는 이 worktree의 `0014_attendance`와 같은 부모에서 분기하고 번호 접두사가 겹칠 수 있다. 이번 0015는 attendance 다음에만 연결했다. 병합 담당자가 선형 연결 또는 merge revision을 결정해야 하며 이번에 다른 브랜치는 확인·수정하지 않았다.

## 미확인·다음 단계

- QR·카카오 로그인·기기 등록은 이번 범위 밖이다. 다음 카카오/QR 작업에서는 로그에 토큰·QR값·쿠키·인증 코드·민감 요청 본문을 남기지 않고 경로/오류 출력도 가리는 원칙을 적용해야 한다. 이번에는 로깅 계층을 변경하지 않았다.
- 로그인·점주 권한·직원 기기/위치·재인증은 여전히 PROVISIONAL이다. 실제 계정/장비와 법정 보관·열람·정정·급여 요건(인증 설계 §6.5)은 검증하지 않았다.
- DB 소유자/슈퍼유저가 트리거를 끄는 행위는 막지 못한다. 외부 추가 전용 감사 저장소는 이번 범위 밖이다.
- 운영 DB 배포·실데이터 마이그레이션·Alembic 브랜치 통합·독립 보안 리뷰는 미실행이다. SQLite 동시 쓰기 보장은 PostgreSQL 직원 행 잠금 검증으로 대체하지 않는다.
