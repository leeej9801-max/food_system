## 1. 구현한 요구사항 / 화면 / 결정 ID
- 테이블당 열린 방문 세션 최대 1개를 DB 제약으로 보장 (U-17 계열, 흐름 정의 "동시 시작 → 먼저 저장된 쪽이 연다").
- 1명 단위 세션 슬롯(`session_slots`): 실루엣 생성, `+`/`-`, "이 자리가 나예요"(가져가기), 화면 표시 거부.
- 테이블 QR 토큰 발급·회전(직원 API), 손님 QR API(`/api/guest/v1`): 조회·열기·합류·새 손님(케이스 H).
- 인원수 출처 `party_size_source`(GUEST_QR/STAFF), 연 주체 `opened_by`, 닫힌 이유 `closed_reason`(NEXT_PARTY/CLEARED) (U-18, U-19).
- 익명 기기 토큰만 사용, 개인정보 없음 (U-23). 원문 토큰은 쿠키에만, DB에는 SHA-256 해시.
- 새 매장 테이블은 `store_id` 직접 보유 + RLS ENABLE/FORCE + `store_isolation` 정책 (ADR-013).

### 설계 선택: QR 토큰으로 매장 찾기
손님 요청은 매장 범위가 없을 때 토큰을 읽어야 한다. 그런데 `table_qr_tokens`는 RLS FORCE라 런타임 계정이 범위 없이 읽으면 0행이다.
- A (채택): 토큰 1개만 받아 (매장, 테이블)만 돌려주는 SECURITY DEFINER 함수. 토큰 목록은 여전히 못 읽음.
- B: 토큰에 매장 ID를 넣기(`<store_id>.<비밀>`). 매장 ID가 QR에 드러남.
- C: 토큰 표를 전역(RLS 없음)으로. ADR-013 "매장 데이터는 store_id + RLS" 위반.
- 함수 소유자가 FORCE 정책에 막히지 않도록 `qr_resolve_owner`(마이그레이션 실행 계정만, SELECT만) 정책을 하나 더 둔다.

## 5. 미구현 요구사항 / 차이 / 이유
- **AC-1 일부 차이**: `ruff format --check .`는 이번 작업 전부터 29개 파일이 미서식이라 실패한다. 새 파일만 서식을 맞췄고, 요청 범위 밖이라 기존 파일은 다시 서식하지 않았다.
- 캐릭터·연령대 입력·전광판 API·프론트 화면·QR 이미지 출력: WO 범위 밖.
- 시간 초과(TIMEOUT)·영업 종료(END_OF_DAY) 자동 닫기 미구현. 지금은 케이스 H(새 손님 확인)와 직원 퇴점으로만 닫힌다.
- 슬롯 상태 `EDITING`·`CUSTOM`은 값만 정의, 쓰는 곳 없음(캐릭터 단계에서 사용).
- 케이스 E(등록자가 인원보다 많으면 자동 증가)는 캐릭터 등록이 없어 해당 없음. 지금은 `+`로만 늘린다.

## 7. 알려진 오류 / 기술 부채 / TODO
- 요청 수 제한 없음. 유효한 QR로 쿠키 없이 반복 호출하면 `guest_devices` 행이 계속 생긴다.
- 가져가기 경쟁: 두 기기가 같은 슬롯을 동시에 가져가면 마지막 저장이 이긴다(행 잠금 없음).
- 한 기기가 여러 슬롯을 가져갈 수 있다. 대리 꾸미기와의 관계가 정해지지 않아 막지 않았다(사용자 결정 필요).
- `qr_resolve_owner` 정책은 마이그레이션을 실행한 계정에 묶인다. 소유 계정을 바꾸면 정책도 다시 만들어야 한다.
- 스파이크 테스트(`test_rls_isolation.py`)는 슈퍼유저 소유자가 필요하다(기존 전제).
