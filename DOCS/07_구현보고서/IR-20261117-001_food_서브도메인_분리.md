## Cloudflare 실제 상태

Wrangler 캐시의 `whoami`로 로그인 상태를 확인한 뒤, 기존 OAuth 토큰을 메모리에서 읽어 알려진 account ID의 터널 configurations endpoint를 직접 GET했다. `/accounts` 목록 조회를 선행할 필요가 없었다. 터널·zone 조회는 HTTP 200이었으나 DNS records API는 HTTP 403, code 10000 `Authentication error`였다. 토큰은 출력·별도 파일·문서에 저장하지 않았다.

터널 `lci-prod`, ID `3cbebf65-3f0a-4f1b-bbd8-42a55068dbda`의 실제 원격 config는 **version 4**였다. 이전 실행이 추가한 규칙을 확인했으므로 **이번 이어하기에서는 PUT하지 않았다.**

## 승인 후 운영 재배포 절차 — 이번에는 실행하지 않음

1. **백업:** 승인된 배포 대상 체크아웃과 커밋을 확정한다. 현재 실행 이미지 ID를 `docker inspect --format '{{.Image}}' food-web-1` 및 `food-backend-1`로 확인하고 고유 rollback 태그로 보존한다. Compose·nginx·Dockerfile과 운영 `.env.deploy`는 접근 제한된 백업 위치에 보관하고 비밀 내용을 화면·IR에 출력하지 않는다. 위 Cloudflare before/current 사본도 보관한다.
2. **DB 백업:** 운영 배포 폴더에서 아래처럼 PostgreSQL custom dump를 만든다. PowerShell 바이너리 리다이렉션을 사용하지 않는다. 백업 파일의 존재·크기와 `pg_restore --list` 가능 여부를 확인한다.

   ```powershell
   docker compose --env-file .env.deploy exec -T food-db pg_dump -U food -d food -Fc -f /tmp/food-before-subdomain.dump
   $foodDbContainer = docker compose --env-file .env.deploy ps -q food-db
   docker cp "${foodDbContainer}:/tmp/food-before-subdomain.dump" '.deploy/food-before-subdomain.dump'
   ```

3. **빌드 전 확인:** 현재 운영 Alembic revision과 배포 코드의 migration head를 비교한다. 이번 URL 변경 자체에는 스키마 migration이 없다. 그 외 미적용 migration이 있다면 별도 승인·검증 없이 함께 반영하지 않는다. `food-web`과 cloudflared의 기존 `lci-prod_edge` 연결을 유지한다. DNS와 ingress는 이미 준비됐으므로 기존 규칙을 변경하지 않는다.
4. **빌드:** 승인된 배포 코드에서 `docker compose --env-file .env.deploy config --quiet` 후 `docker compose --env-file .env.deploy build`를 실행한다. Vite base `/`, API `/api/v1`, dist 루트 복사 및 nginx 설정이 포함된 이미지인지 확인한다.
5. **up:** 백업과 migration 검토를 끝낸 뒤에만 `docker compose --env-file .env.deploy up -d --wait`를 실행한다. `ps`, health, backend/nginx 로그를 확인하되 비밀·사용자 데이터를 출력하지 않는다.
6. **확인:** 새 호스트 `/`·`/home`·`/menus` 새로고침, `/assets/...`의 JS/CSS 200, `/api/v1/stores`의 JSON 응답, `/health` 및 실제 브라우저 API 연결을 확인한다. HTTPS에서 mixed content·잘못된 `/food/assets`·localhost API 참조가 없는지 확인한다.
7. **구 주소 301 유지:** `curl -I 'https://lci.leejblab.site/food/menus?store=<확인용ID>&q=a%20b'`의 301과 Location `https://food.leejblab.site/menus?store=<확인용ID>&q=a%20b`를 확인한다. `/food`, `/food/`도 새 `/`로 301해야 한다. **기존 lci `/food` ingress를 계속 유지해야 nginx의 301에 도달한다.** 기존 lci 루트 서비스도 정상인지 확인한다.
8. **실패 시 롤백:** 저장해 둔 이전 web/backend 이미지와 이전 Compose 설정(구 base·API·CORS·root-path·healthcheck)을 함께 복원하고 승인된 절차로 재시작한다. 기존 `/food` DNS·ingress는 그대로 두어 기존 서비스로 복귀한다. URL 변경에는 DB downgrade가 필요 없으며, 실제 데이터·migration 변경이 발생했다면 검증된 별도 복구 계획을 적용한다. 새 호스트는 이전 이미지에서 다시 404일 수 있다.

백업·build·up·운영 확인·롤백 명령은 모두 후속 수동 단계다. 이 구현 작업에서는 실행하지 않았다. 커밋·push·main 병합도 사용자 지시 전까지 하지 않는다.

## 미확인·후속 작업

- 운영 재배포 후 새 루트 UI·실제 backend/DB·자산·health·구 URL 301의 전체 동작, 실제 브라우저·태블릿, 카카오 인증은 미검증이다.

- POS A/B 실연동·실시간·장비 검증은 이 작업 범위가 아니다.
- 남은 수동 단계는 위 백업→빌드→up→확인 및 카카오 콘솔 등록이다. Cloudflare DNS·ingress 추가 작업은 남아 있지 않다.
