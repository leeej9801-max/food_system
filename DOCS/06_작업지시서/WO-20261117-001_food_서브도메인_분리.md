# 음식점 서비스 서브도메인 분리

> 2026-11-17 이어하기 완료: 코드·사전 검사·Cloudflare ingress 확인 및 DNS 추가, IR·self-review REV 작성. 운영 재배포는 하지 않았다. 최신 사용자 지시에 따라 커밋도 금지하며, 검사·실제 변경·후속 수동 절차는 IR을 따른다.

## 목적·범위

사용자 지시로 배포 주소를 `https://lci.leejblab.site/food/`에서 `https://food.leejblab.site/`로 분리한다. main `f216e9b` 기준 로컬 브랜치 `feature/food-subdomain`에서 작업한다. S00~S07 공통 배포 경로, ADR-001·002·014 관련이며 제품 기능·데이터 모델은 바꾸지 않는다.

- Dockerfile의 Vite base·API 주소·정적 파일 위치, Nginx SPA·API 프록시, Compose CORS·root-path·healthcheck를 함께 전환한다.
- 구 호스트의 `/food` 및 `/food/...` 요청은 새 호스트로 301하고 쿼리를 유지한다. 다른 호스트·경로는 이 리다이렉트에 포함하지 않는다.
- 기존 하드코딩 경로의 실제 호출자·검사·현행 안내를 점검한다. 과거 DOCS 기록은 수정하지 않는다.
- Cloudflare는 기존 lci-prod 규칙을 보존하면서 새 hostname·DNS만 추가한다. PUT 전 원본 config를 저장소 밖 scratch에 백업한다. OAuth 토큰은 메모리에서만 사용하며 출력·별도 저장하지 않는다.
- IR, self-review REV, 현행 인수인계를 작성한다. 카카오 콘솔의 추후 설정값과 승인 후 재배포 절차를 IR에 남긴다.

## 수용 기준·검증

1. Vite base `/`, API `/api/v1`, BrowserRouter `BASE_URL` 연동 확인.
2. tsc, vitest, 배포 API 환경변수로 vite build 실행, dist assets가 `/assets/`를 사용하는지 확인.
3. 가능하면 격리된 임시 Nginx에서 문법·SPA fallback·API URI·301·쿼리 보존 검사. 운영 컨테이너는 재시작하지 않는다.
4. Cloudflare API로 터널·zone 조회 후 기존 규칙을 그대로 유지하고 catch-all 앞에 새 규칙 삽입. DNS가 이미 있으면 그대로 둔다. 권한 부족 시 지정 브라우저 대안, 실패 시 정확한 수동 절차 보고.
5. 두 공개 URL의 실제 HTTP 헤더 결과를 기록한다. 새 주소의 배포 전 오류는 성공으로 과장하지 않는다.

## 예상 변경 파일·영향

`frontend/Dockerfile`, `frontend/nginx.conf`, `compose.yaml`, 필요 시 경로 회귀 검사, `README.md`, `deploy/README.md`, 현재 인수인계, 이번 WO·IR·REV. Vite의 기본 base가 이미 `/`이면 불필요한 설정·라우터 수정은 생략한다. 기존 로컬 개발 API·origin은 유지한다.

## 비범위·위험·완료 조건

push·main 병합·운영 재배포(`compose up` 등)·운영 DB 변경·기존 Cloudflare lci 규칙 변경·카카오 콘솔 변경은 하지 않는다. 사용자의 이어하기 지시(2026-11-17)에 따라 로컬 커밋도 하지 않는다. 신규 호스트는 현재 운영 이미지가 `/food` 기반이므로 재배포 전 404/깨진 화면일 수 있다. 새 호스트에는 기존 호스트 쿠키·localStorage가 자동 이전되지 않는다. 모든 실행 결과와 미실행 항목, 남은 승인 후 작업을 IR에 구분하면 구현 인계 완료다.
