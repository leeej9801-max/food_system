# WO-20261104-002 — 매장 격리(ADR-013 B안) 운영 스키마 적용

## 1. 목적
스파이크로 검증한 B안을 실제 스키마·API·배포 구성에 적용한다 (사용자 지시: "격리 적용 진행").

## 2. 범위
### 포함
- `recipe_items.store_id` 추가·기존 데이터 채움 (모든 매장 테이블이 `store_id`를 직접 가짐).
- Alembic `0006`: 매장 테이블 15개에 `ENABLE`+`FORCE ROW LEVEL SECURITY`, fail-closed 정책(text 비교, 운영 ID가 `String(36)`). PostgreSQL에서만 실행, SQLite는 컬럼 추가만.
- 요청마다 매장 범위: `get_db`가 경로의 `store_id`로 `RequestContext`를 세션에 묶고, 트랜잭션 시작마다 `set_config(..., true)` 재적용 (서비스 중간 `commit()` 대응). 매장 생성 시 새 매장 범위로 전환.
- 앱 런타임 DB 계정(비소유자·비슈퍼유저·BYPASSRLS 없음) 생성·권한 스크립트, `compose.yaml`에서 마이그레이션(소유자)과 API(런타임) 계정 분리, 비밀번호는 `.env.deploy`에 생성.
- PostgreSQL에서 API 수준 격리 테스트 (다른 매장 ID로 조회·수정 시 404, 목록 혼입 없음, 주요 흐름 동작).

### 제외
- `stores` 테이블 자체(매장 목록·생성)는 RLS 대상 아님: 앱이 첫 매장을 고르는 `GET /stores`가 필요하고, 매장 권한은 인증 도입 시 `authorize`에서 제한.
- 실행 중인 공개 데모(`/food`) 재배포: 사용자 확인 후 진행. 이 작업은 코드·구성·검증까지.
- 로그인·인증.

## 3. 수용 기준
- [ ] AC-1 기존 SQLite 테스트 전부 통과, `ruff` 통과.
- [ ] AC-2 PostgreSQL + 런타임 계정으로 API 격리 테스트 통과 (매장 A 경로로 매장 B 리소스 접근 불가, 목록 혼입 없음, 매장 생성·시드·CSV 반영·분석 동작).
- [ ] AC-3 `alembic upgrade head`가 기존 데이터(데모 SQLite를 이전한 PostgreSQL)에서 성공하고 `recipe_items.store_id`가 레시피와 일치. `downgrade -1`도 성공.
- [ ] AC-4 별도 compose 프로젝트(라이브 데모와 분리)로 migrate → 런타임 계정 → API health 확인.

## 4. 위험
- FORCE RLS 이후 매장 범위 없이 실행되는 코드 경로가 있으면 0행/INSERT 거부로 깨진다 → API 격리 테스트로 주요 흐름 확인. 일회성 `scripts.import_sqlite`는 소유자 계정(`migrate` 서비스 환경)으로 실행하도록 문서 변경.
- 라이브 데모 전환 시 `.env.deploy`에 런타임 비밀번호 추가와 재빌드 필요.
