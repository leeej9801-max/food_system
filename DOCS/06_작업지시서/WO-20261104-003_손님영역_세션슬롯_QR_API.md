# WO-20261104-003 — 손님 영역 B 1단계: 세션 슬롯 + 손님 QR API

| ID | 상태 | 작성일 | 관련 문서 | 관련 작업 | 관련 결정 |
|---|---|---|---|---|---|
| WO-20261104-003 | REVIEW | 2026-11-04 | [[손님영역_흐름정의_및_ERD_초안]] | 선행 [[WO-20261104-002_매장격리_운영스키마_적용]] | ADR-013, U-16~U-20, U-23 |

## 1. 목적 / 문제
손님 영역(B)의 첫 백엔드 조각을 만든다 (사용자 지시: "세션 슬롯 + 손님 QR API, 개인정보 없이 익명 기기 토큰만").
손님이 테이블 QR을 찍으면 서버가 토큰으로 매장·테이블을 찾아 그 테이블의 방문 세션을 열거나 합류하고, 1명 단위 슬롯을 관리한다. 캐릭터 꾸미기·TV 화면·등록은 다음 단계다.

## 2. 범위
### 포함
- 새 매장 테이블 2개 (`store_id` 직접 보유, RLS 정책 포함):
  - `table_qr_tokens`: 테이블당 활성 토큰 1개, 추측 불가 토큰(`secrets.token_urlsafe`), `rotated_at`.
  - `session_slots`: `session_id`, `slot_no`, `state`(EMPTY/SILHOUETTE/EDITING/CUSTOM), `created_by_device_id`, `claimed_by_device_id`, `display_opt_out`. (`character_id`, `age_band`은 캐릭터 단계에서 추가)
- 새 전역 테이블 1개: `guest_devices` (익명 기기, 토큰 원문은 저장하지 않고 SHA-256 해시만). 개인정보 없음.
- `visit_sessions` 컬럼 추가: `party_size_source`(GUEST_QR/STAFF/CSV_BACKFILL), `opened_by`(GUEST_QR/STAFF), `closed_reason`(NEXT_PARTY/CLEARED/TIMEOUT/END_OF_DAY). 기존 행은 `STAFF`로 채운다.
- 테이블당 열린 세션 1개를 DB에서 강제: `visit_sessions(table_id)` 부분 유니크 인덱스 (`status IN ('SEATED','PAID')`).
- 직원 API: QR 토큰 발급·재발급(회전)·조회. 직원이 세션을 열면 인원수만큼 `SILHOUETTE` 슬롯 생성, 직원이 `LEFT` 처리하면 `closed_reason=CLEARED`.
- 손님 API `/api/guest/v1/qr/{token}`: 테이블·세션 조회, 세션 열기/합류, 새 손님으로 열기(이전 세션 `NEXT_PARTY`로 닫기, 케이스 H), 슬롯 추가(+), 빈 슬롯 제거(−), 슬롯 가져가기("이 캐릭터가 나예요"), 표시 거부 토글(케이스 L).
- QR 토큰 → 매장 찾기: PostgreSQL에서 `SECURITY DEFINER` 함수 `app_resolve_table_qr(token)` (아래 §5 결정).
- 테스트: SQLite API 테스트 + PostgreSQL 격리 테스트(`backend/tests/isolation`)에 새 테이블·손님 API 케이스 추가.

### 제외 (비범위)
- 캐릭터(외형, `characters` 테이블), 꾸미기, 사진 카드, 보상·쿠폰, 회원 등록(카카오/네이버, U-23), 동의 화면.
- 매장 TV 화면 API(`/api/display/v1`), 손님 모바일 프론트엔드, QR 이미지 출력.
- 타임아웃·영업 종료 자동 닫기(`TIMEOUT`/`END_OF_DAY`는 값만 정의), `CSV_BACKFILL` 맞춤.
- 요청 빈도 제한(rate limit). 위험 §8에 남긴다.
- 라이브 `/food` 재배포: 사용자 확인 후.

## 5. 구현 요구사항

### 5.1 결정: QR 토큰으로 매장을 찾는 방법
RLS가 켜진 상태에서 런타임 계정은 매장 범위 없이 `table_qr_tokens`를 읽을 수 없다. 범위를 정하려면 매장을 알아야 하고, 매장을 알려면 토큰 행을 읽어야 한다.

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A (채택) | 소유자 권한으로 도는 `SECURITY DEFINER` 함수 `app_resolve_table_qr(token)`이 토큰 하나에 맞는 `store_id, table_id`만 돌려줌 | 토큰이 불투명(매장 ID 노출 없음), 전체 목록 조회 불가 | PostgreSQL/SQLite 코드 경로 2개 |
| B | 토큰에 매장 ID를 넣고(`<store_id>.<secret>`) 그 매장 범위에서 비밀값 대조 | 코드 경로 1개 | QR URL에 매장 ID 노출, 토큰 형식이 스키마에 묶임 |
| C | `table_qr_tokens`를 RLS 없는 전역 테이블로 | 가장 단순 | 런타임 계정이 모든 매장 토큰을 읽을 수 있음 (ADR-013 규칙 위반) |

함수는 `search_path`를 고정하고 런타임 계정에 `EXECUTE`만 준다. SQLite(테스트·로컬)는 RLS가 없으므로 ORM으로 직접 조회한다 (P-07).

### 5.2 손님 요청 범위
- 토큰을 풀어 얻은 `store_id`로 `RequestContext(store_id, actor="guest-device")`를 만들어 `bind_store_scope`. 손님 API에는 경로·본문에 `store_id`가 없다.
- 이후 조회는 앱 계층에서도 `store_id`·`table_id`로 거른다 (RLS와 이중).
- 없는 토큰·비활성 테이블은 404 `QR_TOKEN_NOT_FOUND` (존재 여부 구분 안 함).

### 5.3 익명 기기
- 쿠키 `food_guest_device` (HttpOnly, SameSite=Lax, 1년). 없거나 모르는 값이면 새로 발급.
- 서버는 토큰의 SHA-256만 저장. 기기 행에는 `id`, `token_hash`, `created_at`, `last_seen_at`만.

### 5.4 세션·슬롯 규칙 (설계 초안 기준)
- 열기: 열린 세션이 없으면 `party_size`(1~20)만큼 `SILHOUETTE` 슬롯과 함께 연다. `party_size_source=GUEST_QR`, `opened_by=GUEST_QR`.
- 합류: 열린 세션이 있으면 새로 열지 않고 그 세션을 돌려준다. 직원이 연 세션에 손님이 처음 들어오면 `party_size_source`를 `GUEST_QR`로 올린다(손님 > 직원). 보낸 인원수가 다르면 덮어쓰지 않고 응답에 `party_size_mismatch=true`.
- 동시에 열기: 부분 유니크 인덱스 위반 시 롤백하고 이미 열린 세션에 합류.
- 새 손님(케이스 H): `new_party=true`면 열린 세션을 `LEFT`·`NEXT_PARTY`로 닫고 새로 연다.
- 슬롯 추가: 맨 뒤 번호로 `SILHOUETTE` 1개, `party_size` +1. 좌석 수를 넘으면 응답 `over_seats=true`(막지 않음, 확인은 프론트).
- 슬롯 제거: `SILHOUETTE`/`EMPTY`이고 가져간 기기가 없는 슬롯만, 남는 슬롯이 1개 이상일 때. `party_size` −1. 아니면 409.
- 가져가기: 가져간 기기가 없으면 요청 기기로 설정. 이미 다른 기기면 409. 같은 기기는 그대로.
- 표시 거부: 본인 기기가 가져간 슬롯만 토글. 아니면 403.
- 응답의 슬롯에는 기기 ID를 내보내지 않고 `is_mine`만 준다.

### 5.5 직원 API
- `POST /api/v1/stores/{store_id}/tables/{table_id}/qr-token`: 발급 또는 회전(기존 토큰 무효). 
- `GET .../qr-token`: 현재 토큰 (없으면 404).
- 기존 세션 생성: `party_size_source=STAFF`, `opened_by=STAFF`, 슬롯 생성. `LEFT` 변경 시 `closed_reason=CLEARED`.

### 5.6 마이그레이션 `0007_guest_sessions_slots`
- 테이블·컬럼 추가, 기존 `visit_sessions`에 `STAFF` 채움, 열린 세션 중복이 있으면 마이그레이션 실패(메시지로 안내, 데이터 임의 수정 안 함).
- PostgreSQL: 새 매장 테이블 2개에 `ENABLE`+`FORCE` RLS, `store_isolation` 정책(0006과 같은 형식), `app_resolve_table_qr` 함수.
- `downgrade` 가능.
- 런타임 계정 스크립트에 함수 `EXECUTE` 권한 추가.

## 8. 위험 / 미결정 / PROVISIONAL
- **PROVISIONAL:** 익명 기기 토큰으로 재방문을 잇는 것이 개인정보인지 법률 검토 미완(인수인계 열린 이슈). 이번 단계는 재방문 연결 기능을 만들지 않고 기기 ID를 손님 응답에 내보내지 않는다.
- QR 토큰이 사진으로 퍼지면 매장 밖에서도 세션을 열 수 있다. 대응(회전, 위치·시간 제한, rate limit)은 다음 단계. 이번에는 회전 API만.
- `SECURITY DEFINER` 함수는 소유자 권한으로 돈다. 토큰 일치 1행만 돌려주고 `search_path` 고정으로 범위를 좁힌다.
- 열린 세션 부분 유니크 인덱스: 라이브 데이터에 같은 테이블 열린 세션이 2개 이상이면 마이그레이션이 멈춘다. 재배포 전 확인 필요.
- 슬롯 상태 `EDITING`·`CUSTOM`은 캐릭터 단계에서 쓴다. 이번에는 값만 정의.
