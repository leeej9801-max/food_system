# WO-20261110-002 — lee-start 표준 정렬 리팩토링 (출시용 서비스 뼈대)

## 1. 목적
food를 MVP가 아니라 **출시용 서비스 뼈대**로 만든다 (U-37). lee-start 표준에 맞추고, 보안·인증 설계를 먼저 문서로 승인받은 뒤 구현한다.
운영 데이터와 사용자가 아직 없으므로 계약 변경(오류 형식, PK, 설정) 비용이 지금 가장 낮다. 그래서 동작이 바뀌는 표준 항목도 전부 진행한다.

## 2. 일정 제약
- 점주 대시보드는 **11월 말** 출시.
- 손님 캐릭터 앱은 12월 초 이후이고 **이번 범위가 아니다**. 캐릭터 화면·에셋도 범위 밖.

## 3. 단계
끝난 단계마다 멈추고 보고한다. 다음 단계는 사용자가 사용량을 보고 정한다.

## 4. 규칙
- CI에서 RLS 격리 테스트가 skip이면 실패한다(유지).
- 라이브 `/food` 재배포는 사용자 확인 후에만 한다. 라이브 DB는 건드리지 않는다.
- async 전환은 이번 범위에서 제외한다. 출시 후 부하 측정을 보고 따로 결정한다. 전환 비용·위험은 ADR 초안 한 장으로만 남긴다 (U-38).
- `backend/requirements.deploy.txt`는 배포 필수 파일이므로 지우지 않는다.
- 실행하지 않은 검증은 `미검증`, 확인하지 못한 사실은 `미확인`으로 적는다. 추측으로 채우지 않는다.

## 5. 보안·인증 문서 요구사항 (③, 구현 전에 사용자 승인)
작성 순서: 위협 분석 → 역할·권한 표 → 인증 설계.

**위협 분석 (가벼운 수준)**
- 자산별 표: 매장 데이터, 손님 개인정보, 출퇴근 기록, 점주 계정. 열은 "누가 무엇을 어떻게 악용할 수 있나 / 지금 방어 / 부족한 것".
- 개인정보 저장 항목 목록, 로그에 개인정보가 남는지 점검.
- 기준: OWASP ASVS Level 1. 적용한 항목과 적용하지 않은 항목을 목록으로 남긴다.

**역할·권한 표**
- 역할: 점주 / 직원 / 손님.
- 모든 엔드포인트를 역할에 대응시킨다. 빠지는 엔드포인트가 없어야 한다.

**인증 설계 (확정된 사실, U-39)**
- 점주: 카카오 로그인, 매장 계정과 연결.
- 손님: 기본 익명. 캐릭터를 저장하려는 경우에만 카카오 로그인. 개인정보는 등록 시에만 저장 (U-23).
- 직원: 출퇴근 인증이 목적. 기기 등록이 기본, 필요하면 카카오. 장단점을 비교해 추천안을 낸다.
- 세션: 서버 세션 쿠키(HttpOnly, Secure, SameSite 명시)를 기본안으로 검토. 토큰을 localStorage에 두지 않는다.
- CSRF: SameSite + Origin 검사 또는 토큰.
- 카카오 OAuth: state 검증, 리다이렉트 URI 고정, 로그인 직후 세션 ID 재발급.
- 직원 기기 등록: 점주 승인, 기기 폐기, 토큰 탈취 대응, 출퇴근 기록의 수정 이력 보존.
- 매장 격리: 세션에서 `store_id`를 어떻게 주입해 ADR-013 RLS와 연결하는지 반드시 포함.
- `미확인`으로 따로 적을 것: 카카오 앱 등록·동의 항목·심사 조건, 직원 출퇴근 기록의 법적·운영 요건.

## 6. 출시 준비 점검 (③과 함께, 코드 변경 없음)
감사 문서에 "출시 준비" 섹션을 추가한다. 항목: 로그와 request_id, 오류 알림, DB 백업과 복구, 시크릿 관리, 호출 횟수 제한, CORS, 배포 자동화와 롤백, 헬스체크, 마이그레이션 적용 절차. 확인하지 못한 항목은 `미확인`.
