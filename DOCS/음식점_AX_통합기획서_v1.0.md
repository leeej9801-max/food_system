## 0. 한 페이지 요약

### 0.1 서비스 정의

**1~2인 운영 음식점에서 데이터 수집에 필요한 노동과 중복 입력을 최소화하고, POS·파일·간편 기록으로 수집한 정보를 표준화해 재고·원가·운영 분석에 연결하는 음식점 AX 데이터 파이프라인 서비스.**

핵심은 AI 기능을 많이 넣는 것이 아니라, 매장을 운영하는 사람이 별도 데이터 담당자 없이도 데이터가 지속적으로 쌓이는 환경을 만드는 것이다.

### 0.2 가장 중요한 제품 원칙

1. **자동 수집 우선:** POS에 이미 기록되는 판매·상품 데이터는 가능한 한 다시 입력하지 않는다.
2. **같은 사실은 한 번만 기록:** 주문, 입고, 실재고 확인 등 실제 발생 이벤트를 기록하고, 판매량 합계·예상 재고·원가 등 파생 값은 시스템이 계산한다.
3. **현장 입력은 최소화:** 영업 중에는 큰 버튼, 기본값, 최근 항목, 짧은 폼으로 몇 번의 조작만 요구한다.
4. **수집 방식과 제품 기능을 분리:** 토스플레이스 Open API, POS Plugin SDK, CSV/Excel의 데이터 수집 방식이 다르더라도 내부 데이터 모델과 주요 화면은 공통으로 유지한다.
5. **실제와 추정을 구분:** POS에서 가져온 값, 사용자가 직접 기록한 값, 시스템 계산값, 모델 예측값을 구분한다.
6. **불완전한 데이터가 전체 업무를 막지 않음:** 레시피 미등록·연령대 미기록·테이블 매핑 실패가 있어도 가능한 판매 기록 수집은 계속한다.
7. **원본과 이력 보존:** 주문 수정·취소, 모드 변경, 파일 재업로드, 레시피 변경이 과거 기록을 조용히 덮어쓰지 않게 한다.
8. **먼저 계측하고 나중에 AI를 고도화:** 초기에는 결정론적 계산과 간단한 리포트부터 제공하며, 예측 모델은 실제 데이터에서 단순 기준 모델보다 개선이 확인될 때 확장한다.

### 0.3 첫 MVP에서 해결할 문제

- 메뉴별 판매량을 POS 또는 파일에서 가져와 시간 단위로 집계한다.
- 방문 인원과 선택적 연령대 정보를 현장에서 간단히 기록할 수 있게 한다.
- 메뉴·레시피·식자재를 연결한다.
- 식자재 입고와 구매가격 이력을 기록한다.
- 판매량과 레시피를 바탕으로 이론상 식자재 소비량 및 예상 재고를 계산한다.
- 실재고와 예상 재고를 구분하고, 기준 재고량 기반 알림을 제공한다.
- 식자재 구매가격 변경이 메뉴별 식재료 원가에 미치는 영향을 시뮬레이션한다.
- 데이터가 최신인지, 메뉴가 매핑되었는지, 어떤 정보가 수기로 보완되어야 하는지 표시한다.

### 0.4 첫 MVP에서 보류할 것

- 카메라 기반 연령대 추정
- 카메라 기반 음식물·잔반량 자동 인식
- 테이블별 음식물 폐기량의 자동 추적
- 모든 POS 업체의 실시간 연동
- 완전자동 구매 발주 및 결제
- 데이터가 부족한 상황에서의 고정밀 수요예측
- 다중 매장용 복잡한 권한·청구·조직 기능
- 별도 Android/iOS 네이티브 앱 출시

## 1. 기획 히스토리와 결정 기록

이 절은 다른 에이전트가 과거 논의와 최신 결정을 혼동하지 않도록 작성한다. 이후 변경은 변경 이력에 기록한다.

### 1.1 초기 방향: 일반 음식점에 AX 적용

처음에는 로봇을 제외한 음식점 AX 적용 후보를 탐색했다. 매출 예측, 메뉴별 수익성 분석, 식자재·재고 관리, 음식물 폐기 분석, 고객 리뷰 분석 등 여러 영역을 검토했다.

**현재 의미:** 위 영역 중 1차 제품은 로봇이나 범용 AI 비서가 아니라, 현장에서 생기는 운영 데이터를 덜 번거롭게 수집·연결하는 기반 서비스에 집중한다.

### 1.2 오픈 전후 서비스 모델 검토

개업을 1~2개월 앞둔 음식점을 대상으로 개업 전에는 메뉴·레시피·식자재 구매가격·운영 기본값을 구축하고, 개업 후에는 실제 POS·재고 데이터를 바탕으로 분석과 예측을 단계적으로 확장하는 로드맵을 검토했다.

**결정:** 오픈 전 매장에도 가치가 있어야 한다. 과거 매출이 없는 시점에는 과거 실적 기반 예측을 약속하지 않고, 설정·마스터 데이터·원가 계산·구매 기록을 먼저 제공한다.

### 1.3 핵심 사용자와 UX 제약 구체화

목표 매장은 주로 1~2명이 운영하는 음식점이다. 한 사람이 조리, 주문 응대, 손님 안내, 청소, 재고 업무를 병행할 수 있으므로 별도 데이터 입력 담당자가 있다는 가정을 하지 않는다.

**결정:**
- 기본 서비스는 웹이며, 태블릿에서 앱처럼 쓸 수 있도록 PWA를 우선 검토한다.
- 현장에서 필요한 기록은 최소 터치로 처리한다.
- POS에서 확보할 수 있는 데이터는 수기 입력하지 않는다.
- 데스크톱은 초기 등록·대량 수정에, 태블릿은 영업 중 빠른 확인·기록에 최적화한다.

### 1.4 목표 데이터 정의

초기 목표 데이터로 다음 항목이 제안되었다.

1. 메뉴별 일간·시간 단위 누적 판매량
2. 일별·시간대별 방문 인원수와 추정 연령대
3. 테이블/메뉴별 음식물 폐기량
4. 레시피와 식자재를 연결한 예상 재고·발주 알림
5. POS 연결 어댑터
6. 식자재 구매가격 변경에 따른 메뉴별 원가 변동 시나리오

**최신 조정:** 3번의 카메라 기반 자동 인식과 테이블별 폐기량 자동화는 초기 MVP에서 보류한다. 모든 고객이 잔반을 남기는 것은 아니고, 셀프 반납구 영상만으로 음식 출처와 메뉴를 정확하게 식별하기 어렵기 때문이다. 폐기 데이터 구조는 향후 확장을 고려할 수 있지만, 초기 개발 범위에서 카메라·폐기 자동 분석은 제외한다.

### 1.5 POS 연동 방식 검토

POS 데이터 자동 수집 가능성에 따라 다음 세 가지 시나리오를 함께 고려하기로 했다.

- **A. 토스플레이스 Open API**: POS와 서버 간 API·웹훅 기반 연동
- **B. 토스플레이스 POS Plugin SDK**: POS 내부 플러그인에서 데이터와 이벤트를 활용해 서비스 서버로 전달
- **C. CSV/Excel**: 판매 파일을 가져와 수집. 파일에 없는 항목은 필요한 범위에서 간편 입력

**결정:** 화면과 내부 데이터 모델은 공통으로 유지한다. 세 방식은 데이터 수집 어댑터만 다르게 구현한다. 단, 실제 지원 필드·권한·실시간성·설치 조건은 개발 전에 공식 문서와 테스트 환경에서 확인한다.

CSV/Excel 모드는 “실시간 연동”이라고 표현하지 않는다. 파일에 들어있는 마지막 시각까지만 확인 가능하며, 파일 업로드 주기에 따라 데이터 최신성이 달라진다.

### 1.6 데이터 모델 및 화면에 대한 현재 방향

- 매장 생성은 프로젝트 생성과 유사한 단계형 흐름으로 제공한다.
- HOME은 도트 스타일 매장 배치도를 중심으로 한다.
- 테이블 배치도는 초기 자동 배치 후 사용자가 좌석 수·위치를 수정할 수 있도록 한다.
- POS에서 주문/테이블 정보를 받을 수 있으면 자동 표시하고, 불가능한 정보만 수기로 기록한다.
- 결제 완료와 실제 퇴점은 같은 이벤트로 간주하지 않는다.
- 메뉴와 식자재는 각각 마스터 목록으로 관리하지만, 양쪽에서 편집하는 메뉴-식자재 관계는 하나의 공통 레시피 데이터로 저장한다.
- 식자재 입고 및 실재고 기록은 메뉴·레시피 마스터와 분리된 기능으로 둔다.
- 웹/PWA로 파일럿 매장 1곳을 먼저 구현한다. 네이티브 앱 출시는 후속 단계다.

### 1.7 현재 미확정 사항

다음은 결정된 요구사항이 아니다.

- 방문 기록은 착석 시, 첫 주문 발생 시, 또는 최소 선택 기록 중 어떤 방식으로 시작하는가?
- 방문 인원수 입력을 항상 필수로 할지, 상황에 따라 건너뛸 수 있게 할지?
- 연령대는 일행의 대표 연령대 하나를 기록할지, 연령대별 인원수를 각각 기록할지?
- 첫 파일럿 매장의 실제 POS 제품과 연결 권한은 무엇인가?
- 시간대별 판매량의 시각 기준을 POS에서 어떤 필드로 확보할 수 있는가?
- 실제 재고 실사는 매일 모든 품목을 대상으로 할지, 핵심 품목만 대상으로 할지?
- 구매 원가는 최근 구매 단가, 기간별 가중평균, 또는 다른 기준 중 무엇을 기본으로 할지?

이 항목들은 구현자가 임의로 결정하지 말고, 인터뷰·POS 검증·파일럿 결과에 따라 확정한다.

## 2. 제품 목표, 비목표 및 성공 기준

### 2.1 제품 목표

**주목표:** 1~2인 매장의 운영 부담을 늘리지 않으면서 재사용 가능한 운영 데이터가 지속적으로 축적되도록 한다.

세부 목표:

- 판매 데이터의 중복 수기 입력 제거
- POS·CSV·Excel 데이터를 공통 형식으로 변환
- 메뉴·레시피·식자재 데이터 연결
- 구매·재고 기록을 가능한 한 단순화
- 추정값·실측값·원본값을 구분해 데이터 신뢰도 확보
- 초기 데이터가 쌓인 뒤 원가·재고 분석으로 확장할 수 있는 구조 확보

### 2.2 비목표

초기 제품은 다음을 목표로 하지 않는다.

- 기존 POS를 대체하는 완전한 POS
- 회계·급여·세무·예약·배달 플랫폼 전체를 대체하는 ERP
- 사장님 승인 없이 발주·결제·메뉴 가격을 자동 변경하는 시스템
- 카메라나 얼굴 분석을 필수로 요구하는 시스템
- 모든 음식점 업종을 동시에 최적화하는 범용 제품
- 근거 데이터가 없는 매출 전망이나 수요예측을 제공하는 것

### 2.3 파일럿 성공 지표

초기에는 AI 정확도만으로 성공을 평가하지 않는다.

| 영역 | KPI 후보 | 측정 목적 |
|---|---|---|
| 현장 편의성 | 하루 수기 입력 횟수·입력 소요 시간 | 기록 부담이 실제로 낮은가 |
| 데이터 자동화 | POS/파일에서 자동 수집된 필드 비율 | 자동 수집 범위를 측정 |
| 데이터 최신성 | 마지막 성공 수집 시각, 누락 건수 | 데이터가 운영 결정에 쓸 만큼 최신인가 |
| 데이터 정합성 | 미매핑 메뉴 수, 중복 이벤트 수, 오류율 | 집계 신뢰성 확인 |
| 레시피 관리 | 판매 메뉴 중 레시피 등록률 | 재고·원가 계산 가능 범위 확인 |
| 재고 관리 | 예상 재고와 실재고 차이 | 이론 소비량 계산의 한계 파악 |
| 활용성 | 주간 재방문·기능 사용률, 알림 확인률 | 기능이 실제 업무에 쓰이는가 |
| 가치 | 원가 파악 시간·발주 준비 시간 변화 | 고객에게 실질 가치가 있는가 |

초기 수치 목표는 파일럿 전 임의로 높게 설정하지 않는다. 첫 1~2주 기준선을 측정한 뒤 고객과 합의해 정한다.

## 3. 사용자 및 운영 컨텍스트

### 3.1 기본 페르소나

- 매장 소유주 또는 매장 운영자 1명
- 필요 시 직원 1명 추가
- 조리·홀·정산·구매·청소를 직접 수행할 수 있음
- 별도 데이터 입력 담당자가 없음
- PC에서 설정·대량 등록을 할 수 있지만, 매장 운영 중에는 태블릿을 더 자주 사용할 수 있음
- 기술 숙련도가 높다고 가정하지 않음

### 3.2 운영 중 UX 제약

- 손님 응대 중 장시간 입력을 요구하지 않는다.
- 같은 매출 데이터를 POS와 서비스에 중복 입력하게 하지 않는다.
- 필수 입력 항목은 초기 설정 외에는 최소화한다.
- 선택 정보가 비어 있어도 저장·업무 진행이 가능해야 한다.
- 조작이 길어질 경우 “나중에 입력”할 수 있어야 하며, 미완료 상태를 명시한다.
- 자동 수집이 지연되면 숫자를 숨기거나 실제 값처럼 표시하지 말고 최신 수집 시각을 보여준다.
- 테이블 비우기·입고 저장 등 주요 동작에는 성공 피드백과 되돌리기 또는 수정 기록을 제공한다.

### 3.3 지원 환경

- 데스크톱/노트북 웹: 매장 초기 설정, 메뉴·레시피 대량 등록, 분석
- 태블릿 PWA: HOME, 테이블/방문 기록, 빠른 입고·실재고 기록
- 모바일 브라우저: 최소한의 조회·간편 입력을 지원할 수 있도록 반응형으로 설계
- 네이티브 iOS/Android 앱: 첫 MVP 범위 밖

## 5. 공통 사용자 시나리오

### 5.1 최초 매장 개설

1. 사용자가 매장 생성 화면에서 매장명·영업일·운영시간·테이블 구성을 입력한다.
2. 시스템이 매장 레코드와 기본 테이블을 생성한다.
3. 사용자가 판매 데이터 수집 방식 A/B/C를 선택한다.
4. A/B를 선택한 경우 실제 자격 증명·앱 승인·플러그인 설치 등 전제 조건을 확인한다. 조건이 충족되기 전에는 “연동 준비 중”으로 표시한다.
5. C를 선택한 경우 샘플 파일을 내려받거나 기존 POS 매출 파일을 업로드한다.
6. POS에서 상품 목록을 가져올 수 있으면 내부 메뉴와 매핑을 시작한다. 그렇지 않으면 메뉴를 수동 또는 Excel로 등록한다.
7. 사용자가 식자재와 레시피를 등록한다. 비워둔 값은 미완료로 표시하되 다음 단계 진행을 막지 않는다.
8. HOME에서 데이터 수집 상태와 미완료 설정을 확인한다.

### 5.2 영업 중 판매 데이터 수집

1. A/B 모드에서는 검증된 연동 경로로 주문/주문 항목/상태 이벤트를 수집한다.
2. C 모드에서는 사용자가 내보낸 판매 파일을 업로드한다. 파일 업로드 시점 이후의 판매는 반영되지 않았다는 점을 표시한다.
3. 수집 계층이 원본 데이터를 보존하고 공통 판매 데이터 모델로 변환한다.
4. 동일 이벤트 또는 주문이 중복 전송되면 한 번만 반영한다.
5. 취소·환불·수정은 원본 이력과 상태를 반영해 집계한다.
6. 시간대별 판매량은 확보된 시각 필드에 따라 계산하고, 사용한 시각 기준을 데이터 품질 메타데이터로 보존한다.
7. 메뉴 미매핑이나 데이터 오류가 있으면 예외 목록으로 표시하고, 오류가 있는 데이터만 사용자 확인을 요청한다.

### 5.3 방문 인원 기록

방문 기록 UX의 정확한 시작 시점은 미결정 사항이다. 구현 시 아래 후보 중 하나를 임의로 고정하지 않는다.

- **옵션 A — 착석 시 기록:** 테이블을 누르고 인원수를 기록한 뒤 착석 세션을 시작한다.
- **옵션 B — POS 주문 발생 후 기록:** POS에서 테이블/주문을 감지한 후 인원수가 없을 때만 간편 입력한다.
- **옵션 C — 선택적 방문 기록:** POS 판매 수집은 별도로 계속하고, 방문 인원 기록은 필요할 때만 간편 입력한다.

최종 UX 결정 전에도 데이터 모델은 `visit/table session`을 지원할 수 있게 설계하되, 불필요하게 고객 개인을 식별하는 정보는 수집하지 않는다.

### 5.4 식자재 입고 및 재고 기록

1. 사용자가 기존 식자재를 선택한다.
2. 입고 수량, 구매 금액/단가, 구매일, 공급업체(선택)를 입력한다.
3. 시스템은 입고 거래를 새로 기록하고 과거 구매가격 이력을 보존한다.
4. 예상 재고를 입고량만큼 증가시킨다.
5. 사용자가 실재고를 확인하면 측정 수량과 시각을 기록한다.
6. 예상 재고와 실재고의 차이는 별도 조정 이벤트로 기록할 수 있다. 원인을 반드시 입력하게 하지는 않되, 큰 차이가 발생하면 선택형 사유를 제시한다.

### 5.5 메뉴 원가 변경 시나리오

1. 사용자가 식자재 상세 또는 분석 화면에서 기준 구매가격을 확인한다.
2. 가격 상승/하락 시나리오를 선택하거나 새 단가를 입력한다.
3. 시스템이 레시피 단위 변환을 적용해 영향 메뉴의 1인분 원가를 재계산한다.
4. 변경 전/후 원가와 식재료비 비율을 표시한다.
5. 필요하면 판매가격 고정 시 공헌이익 변화도 계산하되, 기타 비용 정보가 없으면 전체 순이익이라고 표현하지 않는다.

## 6. POS 연결 전략 및 A/B/C 모드

### 6.1 공통 원칙

- A/B/C는 **판매 데이터 수집 어댑터**의 차이다. 내부 판매 데이터 구조와 분석 로직은 공통으로 한다.
- 파일 import는 POS 모드와 별개로 구매 거래명세서·메뉴·레시피 등의 일괄 등록에도 계속 활용할 수 있다.
- 실제 API 권한과 필드 범위가 확인되기 전에는 연동이 구현된 것처럼 표시하지 않는다.
- POS에서 제공되지 않는 값은 선택적 수기 입력 또는 미지원 상태로 표현한다.
- POS 연결이 성공하더라도 모든 데이터가 자동으로 확보된다고 가정하지 않는다.

### 6.2 모드 A — 토스플레이스 Open API

**개념:** 우리 백엔드 서버가 토스플레이스 Open API를 호출하고, 지원되는 웹훅 이벤트를 받아 외부 POS 데이터를 동기화한다.

**기대되는 데이터 후보:** 매장 기본정보, 상품/카테고리/옵션, 주문, 주문 상태, 결제 내역 및 관련 이벤트. 실제 사용 가능한 범위는 앱 권한과 승인, API 스키마 및 계약 조건에 따라 검증해야 한다.

**필요 작업:**
- 개발자 앱 등록 및 인증 정보 발급
- 테스트 매장 연결
- 주문/상품/결제 API 필드와 시간 의미 확인
- 웹훅 서명 검증 및 중복 방지
- 과거 주문 backfill 범위 테스트
- 취소·수정·환불 집계 규칙 검증
- 테이블 ID와 방문 인원 필드 제공 여부 검증

**주의:** 서버 간 Open API에서 테이블 정보가 제공되지 않을 수도 있다. Plugin SDK에서 제공되는 테이블 데이터와 Open API의 기능을 같은 것으로 취급하지 않는다.

### 6.3 모드 B — 토스플레이스 POS Plugin SDK

**개념:** POS 안에서 실행되는 플러그인이 지원되는 주문·상품·테이블 API와 이벤트를 활용하고, 필요한 데이터를 우리 백엔드로 전달한다. PWA가 POS SDK를 직접 호출하는 구조가 아니다.

**기대되는 데이터 후보:** POS 내부의 주문·상품·테이블 정보 및 상태 변경 이벤트. 공식 문서에 테이블 조회·이벤트 관련 API가 있으나, 업종/후불형 매장 조건 등 적용 전제가 있으므로 대상 매장의 실제 설정을 확인해야 한다.

**필요 작업:**
- TypeScript 기반 Plugin SDK 개발 환경 구성
- 테스트 매장 및 POS 실행 환경 확보
- 테이블·주문·상품 이벤트 실험
- POS 플러그인 → 우리 서버 통신 구현
- 인증, 재시도, 중복 처리, 장애 상태 표시 구현
- 검수·배포·활성화 절차 확인

**주의:** 테이블 정보가 POS에서 제공되더라도 우리 PWA의 도트 배치 좌표는 별도 관리할 수 있다. POS의 테이블 위치 정보가 UI 위치까지 포함한다고 가정하지 않는다.

### 6.4 모드 C — CSV/Excel 기반

**개념:** 사용자가 POS에서 내보낸 파일을 업로드해 판매 데이터를 가져온다.

**필수 동작:**
- 파일 형식·크기·열 구조 검증
- 열 매핑 UI
- 날짜·시간·수량·가격 단위 검증
- 메뉴/상품 미매핑 검출
- 중복 파일/중복 행 검출
- import batch 및 업로드자·업로드 시각 기록
- 성공/실패 행 수와 오류 파일 다운로드 제공
- 마지막 데이터 시각과 마지막 업로드 시각 표시

**한계:** 파일에 주문 시각이나 메뉴별 시간 정보가 없으면 시간 단위 판매량을 정확히 산출할 수 없다. 업로드 주기 사이의 실시간 변경도 자동 반영되지 않는다. 파일의 필드만으로 가능한 분석을 제공하고, 없는 정보를 추정값으로 위장하지 않는다.

### 6.5 POS 모드 비교 및 검증표

| 검증 항목 | A Open API | B Plugin SDK | C CSV/Excel |
|---|---|---|---|
| 메뉴/상품 가져오기 | 공식 문서와 테스트로 확인 | POS 내부 API로 확인 | 파일에 상품 정보가 있을 때 가능 |
| 주문별 메뉴/수량 | API 필드 검증 필요 | SDK 주문 항목 검증 필요 | 파일에 주문 상세가 있을 때 가능 |
| 시간 단위 판매 | 이벤트/시간 필드 검증 필요 | 주문·항목 시간 필드 검증 필요 | 시간 열이 있을 때만 가능 |
| 테이블 ID | 반드시 실험으로 검증 | 테이블/주문 연결 검증 | 파일에 있을 때만 가능 |
| 방문 인원 | 별도 검증 | 주문 필드 및 실제 입력 여부 검증 | 파일에 있을 때만 가능 |
| 취소·수정 | 이벤트/상태 처리 검증 | 주문 이벤트 처리 검증 | 파일에 취소/상태 데이터가 있어야 가능 |
| 실시간성 | API·웹훅 범위에 따라 다름 | 이벤트 수신/서버 전송에 따라 다름 | 실시간 아님; 업로드 시점 기준 |
| 배포·계약 조건 | 앱 권한/승인 확인 | 플러그인 검수·배포 조건 확인 | 파일 내보내기 권한만 있으면 시작 가능 |

### 6.6 모드 전환 규칙

- 모드 변경은 기존 기록을 삭제하지 않는다.
- 같은 판매 기간을 새 어댑터가 다시 가져올 수 있으므로 외부 식별자/중복 키를 사용한다.
- 전환 전에 마지막 동기화 시각과 재수집 범위를 사용자에게 보여준다.
- 이전 모드의 연결 상태와 원본 수집 기록은 보존한다.
- 데이터 원천은 판매 기록별로 추적 가능해야 한다.
- 판매 데이터 수집 모드와 구매 자료 Excel 업로드 기능은 분리한다. A/B 모드에서도 구매 자료 업로드를 계속 허용한다.

## 7. 데이터 수집 정책 및 공통 데이터 모델

### 7.1 데이터 분류

#### 마스터 데이터

- 매장
- 운영시간/영업일

- 예상 재고량

- 데이터 품질·동기화 상태

### 7.2 데이터 출처 표시

모든 중요한 데이터는 최소한 다음 메타데이터를 추적 가능하게 한다.

- `source_type`: `toss_open_api`, `toss_plugin`, `csv_upload`, `manual`, `system_calculation` 중 적절한 값
- `source_record_id`: 외부 원본 식별자 또는 내부 식별자
- `source_event_time`: 원천 시스템의 사건 시각(제공되는 경우)
- `received_at`: 우리 시스템이 데이터를 받은 시각
- `recorded_by`: 사용자 입력인 경우 사용자/역할(인증 도입 시)
- `import_batch_id`: 파일 업로드에서 생성한 배치 ID
- `quality_status`: 정상, 매핑 필요, 시간 정보 부족, 검토 필요 등

원천 시스템의 시각과 우리 시스템이 수신한 시각을 혼동하지 않는다.

### 7.4 스키마 설계 원칙

- 모든 매장 데이터는 `store_id` 또는 매장 관계로 범위를 제한한다. 파일럿은 1개 매장이지만 향후 확장 시 데이터 분리를 다시 설계하지 않도록 한다.
- 외부 POS ID와 내부 ID를 구분한다.
- 메뉴명/식자재명만으로 외부 데이터를 자동 병합하지 않는다.
- 주문 항목이 내부 메뉴와 연결되지 않아도 원본을 저장하고 “미매핑”으로 표시한다.
- 메뉴/레시피를 비활성화해도 과거 판매·구매·재고 기록을 삭제하지 않는다.
- 레시피 수정은 가능하면 버전 또는 적용 시작일을 남겨 과거 판매량의 이론 소비량을 재계산할 때 어떤 레시피를 적용했는지 추적한다.
- 구매가격을 마스터의 단일 값으로 덮어쓰지 않는다. 가격은 입고 기록으로 저장하고 “최근 가격” 등은 계산된 표시값으로 제공한다.

## 8. 집계·원가·재고 계산 규칙

### 8.1 판매량 집계

기본 집계 차원:
- 매장
- 영업일/날짜
- 시간 버킷(초기 기본값은 1시간 단위로 검토)
- 내부 메뉴 ID(미매핑 항목은 별도 그룹)
- 수량
- 데이터 출처 및 시간 기준

**시간 기준 규칙:**
1. 메뉴 항목별 사건 시각이 있으면 우선 사용한다.
2. 없으면 주문 생성/오픈 시각 등 검증된 대체 필드를 사용하되, `time_basis`를 기록한다.
3. 사용 가능한 시각이 없으면 시간 단위 집계를 만들지 않고 “시간 정보 부족”으로 처리한다.
4. 결제 시각만 제공되는 데이터는 메뉴 주문 시각과 같다고 간주하지 않는다. 필요하면 “결제 시각 기준 판매”로 명확히 표시한다.
5. CSV 파일의 시각 필드도 위와 같은 검증을 적용한다.

### 8.2 취소·수정·환불 처리

- 원본 이벤트 또는 원본 행을 보존한다.
- 최종 집계는 활성/유효 주문 상태와 수량 변화를 반영한다.
- 취소 건을 신규 판매로 집계하지 않는다.
- 수정된 주문 항목을 단순히 추가 행으로 더해 중복 집계하지 않는다.
- 공급자 이벤트 의미가 불분명하면 실제 POS 테스트로 상태 변화를 확인한 뒤 집계 규칙을 확정한다.

### 8.3 중복 방지

- 웹훅 공급자가 제공하는 이벤트 ID가 있으면 이를 중복 방지 키로 사용한다.
- 주문·주문 항목별 외부 ID가 있으면 공급자·매장·외부 ID 조합에 unique 제약을 검토한다.
- 이벤트 ID가 없으면 무리하게 메뉴명+시각만으로 영구 중복 판정하지 않는다. 파일 배치와 행 해시, 주문번호 등 이용 가능한 필드 조합을 기반으로 중복 후보를 확인한다.
- 파일 재업로드 시 기존 배치·행과 대조해 중복을 경고하고 사용자가 안전하게 재처리할 수 있게 한다.

### 8.4 레시피 기반 이론상 소비량

기본식:

`이론상 식자재 소비량 = 유효 판매 메뉴별 수량 × 해당 메뉴 레시피의 식자재 사용량을 합산`

- 취소/환불된 메뉴 수량은 정책에 따라 제외하거나 보정한다. 정책은 POS 상태 의미를 확인한 후 확정한다.
- 옵션/추가 재료가 수량과 원가에 영향을 주는 경우 초기 스키마가 이를 표현할 수 있는지 확인한다. MVP에서 복잡한 옵션을 지원하지 않으면 한계를 문서에 표시한다.
- 레시피 미등록 메뉴의 판매는 매출 집계에는 포함하지만 식자재 소비량 계산에서 제외하고 “레시피 미등록” 목록을 보여준다.
- 실제 소비량과 이론상 소비량을 혼동하지 않는다.

### 8.5 예상 재고

기본식:

`예상 재고 = 기초 재고 + 입고량 - 레시피 기반 이론상 소비량 - 별도 식자재 폐기량 ± 재고 조정량`

MVP에서는 별도 식자재 폐기 입력을 보류할 수 있다. 보류 중에는 해당 항을 0으로 가정하는 것이 아니라, “폐기량 미수집으로 재고 차이가 생길 수 있음”을 상태/도움말에 표시한다.

- 예상 재고와 실재고는 다른 필드/개념이다.
- 실재고 입력은 새로운 실사 이벤트로 저장한다.
- 실사 시점 이후의 거래를 고려해 현재 예상 재고와 비교해야 한다. 단순히 지난 실사 값을 현재 재고로 덮어쓰지 않는다.
- 기본 재고 알림은 기준 재고량 이하 또는 예상 소진 시점이 임박한 경우 제공할 수 있다.

### 8.6 구매가격과 메뉴 원가

- 입고 수량과 구매 금액을 기반으로 단위당 가격을 계산한다.
- 단위 변환을 표준화한다. 예: 구매 kg, 레시피 g.
- 기준 원가 계산 방식(최근 단가/가중 평균 등)은 미결정 사항이다. MVP에서 단순한 최근 구매 단가를 사용할 경우 화면에 “최근 구매 단가 기준”이라고 표시하고, 과거 원가를 소급 변경할지 여부를 명확히 한다.
- 메뉴 식재료 원가 = 레시피 각 항목의 사용량 × 적용 단가를 합산한다.
- 식재료비 비율 = 메뉴 식재료 원가 ÷ 판매가격 × 100.
- 공헌이익을 계산할 경우 포함한 변동비 범위를 표시한다. 식재료비만 제외한 금액을 순이익이라고 부르지 않는다.
- 가격 시나리오는 실제 구매 데이터를 수정하지 않는 별도 계산 결과여야 한다.

- 자동 수집 지연, 미매핑 메뉴, 잘못된 단위 등은 사용자가 해결할 조치와 함께 표시한다.
- 저장 중/성공/실패 상태를 명확히 보여준다.
- 영업 중 자주 쓰는 작업은 키보드 입력을 최소화하고 기본값과 빠른 선택을 활용한다.
- 저장되지 않은 변경이 있는 상태에서 이동하면 확인을 요청한다.
- 메뉴/식자재/레시피의 관계는 하나의 데이터 원천을 사용하며, 어느 화면에서 수정해도 같은 관계가 갱신된다.

### 9.3 HOME의 핵심 요소

- 매장명 및 영업 상태
- POS/파일 데이터 최신성 상태
- 도트 스타일 테이블 배치도
- 수집 가능한 오늘의 주요 현황(판매·방문 등)
- 데이터/재고 알림
- 자주 쓰는 빠른 작업

방문 기록을 시작하는 시점(착석/주문 이후/선택 기록)은 미결정이다. 구현 전에 인터뷰로 확정한다.

### 9.4 결제 완료와 퇴점의 분리

- 결제 완료는 POS가 제공하면 수집하되, 실제 퇴점과 같은 의미로 처리하지 않는다.
- 실제 퇴점은 POS에서 신뢰 가능한 테이블 비우기 이벤트를 받을 수 있거나 사용자가 기록한 경우에 종료 처리한다.
- 테이블 세션을 종료해도 과거 이용·방문 기록은 삭제하지 않는다.

## 10. 기술 구조 제안

**주의:** 아래는 구현 가능성을 고려한 후보 구조이며, 기술 스택은 아직 최종 확정되지 않았다. 실제 개발 저장소의 기존 스택이 있다면 우선 해당 스택을 검토하고, 변경은 합의 후 수행한다.

### 10.1 권장 구조

- **Frontend:** React + TypeScript 기반 반응형 웹/PWA. Next.js 또는 Vite 기반 구성을 기술 검증 후 선택한다.
- **Backend:** Python FastAPI 등 HTTP API 서버 후보
- **Database:** PostgreSQL 후보
- **POS integration:** 별도 adapter 모듈. API/웹훅과 POS Plugin SDK는 서로 다른 실행 환경일 수 있다.
- **File ingestion:** CSV/Excel 파서, 열 매핑·검증·import batch 관리
- **Calculation services:** 판매량 집계, 단위 변환, 원가 및 재고 계산을 결정론적 코드로 구현
- **AI services (later):** 문서에서 구매 항목 추출, 품목 매칭 후보 제시, 리포트 설명 등 선택 기능. 핵심 계산을 LLM 출력만으로 수행하지 않는다.

### 10.2 시스템 경계

```text
[POS Open API] ───┐
[POS Plugin] ─────┼─> [Adapter / Ingestion] -> [Raw Events + Normalizer]
[CSV/Excel] ──────┘                               |
                                                  v
                                         [Canonical Database]
                                                  |
                ┌─────────────────────────────────┼─────────────────┐
                v                                 v                 v
          [Sales Aggregation]              [Inventory/Cost]    [Data Quality]
                └─────────────────────────────────┼─────────────────┘
                                                  v
                                          [Backend API]
                                                  v
                                             [PWA UI]
```

### 10.3 구현 원칙

- POS 인증 비밀키를 브라우저/PWA에 저장하지 않는다. 서버 측에서 안전하게 관리한다.
- 외부 이벤트 수신과 비즈니스 계산을 분리한다.
- 원본 데이터 수집, 정규화, 집계의 처리 상태를 추적 가능하게 한다.
- 수집 실패는 재시도 가능해야 하고, 재처리는 중복 집계를 만들지 않아야 한다.
- 초기에는 마이크로서비스를 나누지 않는다. 모듈 경계를 명확히 한 단일 백엔드로 시작해도 된다.
- PWA 오프라인 저장/재동기화는 필요한 사용자 시나리오를 검증한 다음 구현 범위를 정한다. 단순히 “PWA이므로 오프라인 처리가 된다”고 가정하지 않는다.

### 10.4 API 경계 예시

아래 경로는 구현 계약이 아니라 API 설계 후보이다.

- `POST /api/stores` — 매장 생성
- `GET/PATCH /api/stores/{store_id}` — 매장 조회/수정
- `GET/POST/PATCH /api/stores/{store_id}/tables` — 테이블 관리
- `GET/POST/PATCH /api/stores/{store_id}/menus` — 메뉴 관리
- `GET/POST/PATCH /api/stores/{store_id}/ingredients` — 식자재 관리
- `GET/POST/PATCH /api/stores/{store_id}/recipes` — 레시피 관리
- `POST /api/stores/{store_id}/imports/sales` — 판매 파일 업로드
- `GET /api/stores/{store_id}/imports/{batch_id}` — 업로드 결과
- `POST /api/stores/{store_id}/purchases` — 입고 기록
- `POST /api/stores/{store_id}/inventory-counts` — 실재고 기록
- `GET /api/stores/{store_id}/analytics/sales` — 판매량 집계
- `GET /api/stores/{store_id}/analytics/inventory` — 예상 재고 및 관련 경고
- `GET /api/stores/{store_id}/analytics/cost-scenarios` — 원가 시나리오 조회/계산

API 설계 시 페이지네이션, 검증 오류 응답, 인증·권한, 멱등성, 시간대 처리를 포함한다.

## 11. 데이터 보안, 개인정보, 신뢰성

### 11.1 최소 수집 원칙

- 고객 개인의 이름, 전화번호, 얼굴 식별 정보는 초기 범위에서 수집하지 않는다.
- 연령대는 비식별 집계 정보를 목표로 하고 개인별 프로파일을 만들지 않는다.
- 방문 인원과 연령대는 운영 목적에 필요한 최소 단위로 저장한다.
- 카메라 기반 분석은 초기 범위에서 제외한다. 향후 검토 시 법률·개인정보 요건과 촬영·저장 정책을 별도 검토한다.

### 11.2 비밀정보 관리

- POS API 키/토큰은 서버 측 비밀 저장소 또는 환경변수 기반 비밀 관리로 보관한다.
- 코드 저장소에 실제 키·토큰·매장 개인정보를 커밋하지 않는다.
- 로그에 인증 토큰, 민감한 원본 데이터 전체를 불필요하게 기록하지 않는다.

### 11.3 데이터 정정·삭제·내보내기

- 수집 데이터 오류는 추적 가능하게 수정한다.
- 외부 데이터를 재수집해도 기존 원본과 집계가 중복되지 않도록 한다.
- 사용자가 요청한 데이터 내보내기를 고려해 CSV/Excel 내보내기 구조를 설계한다.
- 실제 보관 기간과 삭제 정책은 파일럿 운영 조건과 관련 법·계약을 확인한 후 정한다.

### 11.4 표시의 신뢰성

- “실시간”이라는 용어는 실제 지원 방식과 지연 수준이 확인된 경우에만 사용한다.
- “예상 재고”와 “실재고”를 분리한다.
- AI가 추출한 거래명세서 정보는 확인 전까지 후보/검토 상태로 표시한다.
- 추정 연령대와 직접 입력값은 실제 확인된 인구통계 정보처럼 표시하지 않는다.
- 데이터가 부족하면 숫자를 임의 생성하지 않고 결측 상태와 이유를 표시한다.

## 12. 검증 계획 및 수용 기준

### 12.1 매장 설정

- 필수값이 없으면 어떤 필드가 필요한지 안내한다.
- 설정 중 이전 단계로 이동해도 작성 값이 유지된다.
- 생성된 테이블 수와 좌석 수가 설정과 일치한다.
- 매장 시간 설정은 집계와 표시에서 일관되게 적용된다.

### 12.2 CSV/Excel 수집

- 정상 파일은 preview 후 import 할 수 있다.
- 필수 열 누락, 날짜 형식 오류, 잘못된 숫자, 빈 메뉴명 등의 오류를 행 단위로 보고한다.
- 같은 파일을 다시 올렸을 때 중복 여부를 검출/경고한다.
- 가져온 판매량과 원본 파일 합계가 검증 가능한 경우 일치한다.
- 시간 열이 없는 파일에서는 시간별 집계를 제공하지 않거나 불충분 상태를 표시한다.

### 12.3 POS 연동

- 테스트 주문 1건이 내부 데이터에 한 번만 생성된다.
- 추가 주문이 별도 항목/이벤트로 올바르게 반영된다.
- 주문 수정·취소가 순 판매량 집계에 올바르게 반영된다.
- 동일 웹훅 재수신이 중복 판매량을 만들지 않는다.
- 연결이 끊긴 상태와 마지막 성공 수집 시각을 표시한다.
- 테이블/인원 정보가 제공되지 않으면 “자동 연동”이라고 표시하지 않고 수기 입력/미지원으로 처리한다.
- 외부 이벤트 시각과 수신 시각을 구분한다.

### 12.4 메뉴·레시피·원가

- 메뉴와 식자재의 기본 단위/사용 단위 변환이 검증된다.
- 같은 레시피 관계를 메뉴 화면과 식자재 화면에서 수정해도 한 번만 반영된다.
- 레시피 미등록 메뉴는 판매 집계에는 포함되며 재고 계산 불가 사유를 표시한다.
- 가격 시나리오는 실제 구매 이력을 변경하지 않는다.
- 원가 계산 결과를 독립적인 수식 또는 테스트 데이터와 비교한다.

### 12.5 재고

- 입고 기록은 재고를 증가시키고 구매가격 이력을 추가한다.
- 판매 수량은 해당 시점에 적용되는 레시피 기준으로 이론상 소비량을 계산한다.
- 실제 재고 기록은 예상 재고를 조용히 덮어쓰지 않는다.
- 재고 조정은 이력으로 남는다.
- 폐기량을 수집하지 않는 상태에서는 예상 재고의 한계를 사용자에게 알린다.

### 12.6 UX 수용 기준

- 영업 중 자주 쓰는 기록은 가능한 한 짧은 조작으로 완료된다.
- POS에서 확보된 메뉴 주문을 사용자가 재입력할 필요가 없다.
- 필수가 아닌 값은 비워도 저장할 수 있다.
- 화면 전환이 실패하거나 저장이 실패하면 입력 내용을 보존하거나 복구 가능하게 한다.
- 테이블을 비워도 이용 세션의 과거 기록은 보존한다.

## 15. 인터뷰·결정 대기 목록

이 목록은 개발 진행 중 계속 업데이트한다. 각 항목에 결정자, 근거, 날짜를 기록하는 것을 권장한다.

### D-01. 실제 파일럿 매장의 POS

- 질문: 매장에서 사용할 POS의 정확한 브랜드/제품/버전은 무엇인가?
- 이유: API/Plugin/CSV 가능 범위와 실제 데이터 스키마가 달라짐.
- 결정 방식: 매장 확인 + 공식 문서 + 테스트 계정/샘플 파일.
- 상태: **미결정**

### D-02. 방문 세션 시작 시점

- 옵션 A: 착석 시 수기 기록
- 옵션 B: POS 주문 감지 후 필요 정보 입력
- 옵션 C: 방문 기록은 선택적으로 수행하고 판매 집계는 독립 수집
- 상태: **미결정 — UI 명세서 인터뷰 항목**

### D-03. 방문 인원 기록 방식

- 옵션 A: 총 인원수만 기록
- 옵션 B: 총 인원수 + 일행의 대표 연령대 1개
- 옵션 C: 연령대별 인원수를 나눠 기록
- 권장 방향: 입력 부담을 고려해 총 인원수를 중심으로 하고 연령대는 선택값으로 시작하되, 실제 결정은 인터뷰 후 확정.
- 상태: **미결정**

### D-04. 메뉴별 시간 집계 시각 기준

- 질문: POS에서 주문 생성 시각과 개별 메뉴 추가 시각 중 어떤 필드를 제공하는가?
- 중요성: 시간대별 판매량의 의미와 정확도를 결정함.
- 상태: **POS 기술 검증 필요**

### D-05. 기본 원가 단가 산정법

- 옵션: 최근 구매 단가, 기간별 가중평균 등
- 권장: MVP는 구현과 설명이 쉬운 하나의 기준을 택하되, 화면에 기준을 명시하고 가격 이력은 모두 보존.
- 상태: **미결정**

### D-06. 실재고 실사 빈도

- 옵션: 매일 전체 품목, 핵심 품목만 매일, 주기별 전체 실사
- 상태: **파일럿 운영 인터뷰 필요**

### D-07. 오프라인 입력

- 질문: 매장 Wi-Fi/인터넷 장애가 발생해도 방문 기록을 남겨야 하는가?

## 16. AI/개발 에이전트 작업 규약

이 절은 이 문서를 받은 에이전트가 기획을 임의로 변경하거나 확인되지 않은 기능을 완료된 것처럼 구현하지 않도록 한다.

### 16.1 먼저 읽을 문서

작업 시작 전에 다음 순서로 읽는다.

1. `음식점_AX_통합기획서_v1.0.md` — 제품 목표·결정·데이터·범위·미결정 사항
2. `음식점_AX_UI명세서_v0.1.md` 또는 사용자가 제공한 최신 UI 명세서 — 화면별 필드·버튼·전환
3. 저장소의 `README.md`, `AGENTS.md`, `.env.example`, 기존 코드 및 테스트 — 현재 구현 상태

더 최신 버전의 문서가 있으면 버전과 변경 이력을 확인하고, 최신 합의 사항을 우선한다.

### 16.2 구현 원칙

- 문서에 P0로 지정된 범위만 우선 구현한다.
- POS 모드 A/B가 실제 연결되지 않았다면 mock 데이터를 실시간 POS 데이터로 표현하지 않는다.
- 테스트용 fixture와 실제 연동 데이터는 화면과 저장소에서 명확히 구분한다.
- 필드가 제공되지 않는 경우 임의로 값을 생성하지 않는다.
- TODO/미연동 상태를 숨기지 않는다.
- 기존 기술 스택이나 코드 구조를 먼저 확인하고, 필요 이상의 재작성·리팩터링을 하지 않는다.
- 핵심 계산은 일반 코드/SQL로 구현하고 LLM 출력에 계산 정확성을 맡기지 않는다.
- 중복 수집, 주문 취소·수정, 단위 변환, 시간대 같은 엣지 케이스에 테스트를 둔다.
- 개인정보 또는 API 비밀 키를 코드·로그·샘플에 넣지 않는다.
- 설계 변경이 필요하면 변경 이유, 영향 범위, 대안, 문서 업데이트를 먼저 제시한다.

### 16.3 미결정 사항 처리

- `D-01`~`D-08` 항목은 합의 전까지 임의로 최종 결정하지 않는다.
- 동작 가능한 프로토타입을 위해 임시 가정이 필요하면 코드와 문서에 `PROVISIONAL`로 명시한다.
- 임시 가정을 실제 사업 요구사항처럼 표현하지 않는다.
- 사용자에게 질문하기 전에 이미 확정된 문서 내용을 다시 질문하지 않는다.

### 16.4 개발 완료 보고 형식

각 작업 후 다음을 보고한다.

1. 구현된 요구사항 ID/화면 ID
2. 변경한 파일
3. 실행·검증 방법
4. 실행한 테스트 및 결과
5. 실제 외부 연동 여부(미연동이면 명시)
6. 남은 제약·TODO
7. 문서에서 갱신한 항목

### 16.5 추천 저장소 문서

프로젝트 루트에 별도 `AGENTS.md`가 있다면 이 절의 작업 규약을 요약해 넣는다. 이 통합기획서와 UI 명세서는 전체 설계 기준으로 관리한다.
